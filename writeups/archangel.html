Archangel: SSRF to local file read to cron privesc

A hidden virtual host, an SSRF that reads arbitrary files through a Python web app's own image-fetching feature, a cracked password hash, and a root shell by abusing a cron job that runs as root but is writable by everyone.

Room: Archangel Category: Web / SSRF / Linux Privesc Tools: Gobuster, Hashcat, Pspy

The setup: a web server hides more than its default page lets on. The job: find the real application behind a virtual host, turn a feature meant for fetching images into a way to read local files, and ride a careless cron job all the way to root.

The Investigation

1
Find the real site behind the virtual host

The default Apache page gives nothing away, but it references a domain name. Adding that to /etc/hosts and re-requesting the site reveals an entirely different application, a Python/Flask app for "Villain Hunters," not the stock Apache page at all.

Why this works

Name-based virtual hosting means the same IP can serve completely different sites depending on the Host header. A default landing page is often a decoy, the real target is one DNS entry away.

2
Spot the SSRF in an image loader

The site has a page that renders an image from a URL parameter, built to pull hero portraits from a remote path. Pointing that same parameter at a local file path instead of a URL:

http://<vhost>/image?filename=/etc/passwd

returns the file's contents rendered back as if it were an image, proving the parameter isn't validated as a URL at all, it's passed straight through to a file read.

Why this works

Any feature that fetches a resource from user-supplied input is a candidate for SSRF. Here it goes one step further: because the backend is a local file read dressed up as a URL fetch, it becomes a full Local File Inclusion primitive, not just a way to reach internal services.

3
Read the application's own source code

Since the app is a Flask project, its own source file is readable the same way:

http://<vhost>/image?filename=/var/www/<app>/main.py

The source reveals a hardcoded database path and, critically, how the app itself handles user records, pointing at a SQLite database file that's worth pulling the same way.

Why this works

An LFI primitive isn't just useful for reading /etc/passwd, it's a way to read the application's own blueprint. Source code tells you exactly what file paths and credentials the app already trusts.

4
Pull the database and crack a password

Fetching the SQLite file through the same LFI and opening it locally turns up a user table with a hashed password. Hashcat makes short work of it against a weak wordlist match, recovering a plaintext credential for SSH.

Why this works

A database file is just another file to an unvalidated path parameter. Once it's local, it's no different from any other credential-cracking exercise, the hard part was getting it off the server in the first place.

5
Watch for root running a world-writable script

With a shell as a low-privilege user, pspy (a process-spying tool that needs no special privileges) reveals a cron job running periodically as root, executing a script sitting in a directory the current user can write to.

./pspy64
Why this works

Static enumeration (checking crontab files) can miss jobs defined elsewhere, like systemd timers or jobs dropped by other scripts. Watching what actually executes over time catches what a one-time file listing won't.

6
Hijack the cron script for a root shell

Appending a reverse shell line to the script root's cron job executes, then waiting for the next scheduled run, lands a shell running as root the moment cron fires.

Why this works

A script's permissions don't change based on who triggers it, cron runs it as whatever user owns the job, root in this case, regardless of who last edited the file. Writable-by-anyone plus run-by-root is a privilege escalation path almost every time.

Full Attack Chain

Apache default page → hidden vhost found via /etc/hosts
  → Flask app's image loader takes a raw file path (SSRF / LFI)
       → app's own main.py read, reveals the SQLite DB path
            → DB pulled, password hash cracked offline
                 → SSH in as a low-privilege user
                      → pspy catches a root cron job on a writable script
                           → script hijacked, root shell on next run

Takeaways

Virtual hosts hide real attack surface

A default Apache page proves nothing about what else the server serves. Always check for named virtual hosts before concluding a target is uninteresting.

An image fetcher is a file-read primitive in disguise

Any "load a resource from this parameter" feature deserves a local-path test, not just a remote-URL test.

Watch what runs, don't just read what's scheduled

pspy-style process monitoring catches privileged jobs that static crontab enumeration can miss entirely.
