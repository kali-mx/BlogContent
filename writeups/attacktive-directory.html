Attacktive Directory: from AS-REP roast to domain admin

A lightly hardened Active Directory domain, cracked open end to end: enumerate valid usernames, abuse a missing pre-auth flag to steal a crackable Kerberos hash, pivot through a leftover credentials file on a file share, and walk out with the domain's NTLM hashes.

Room: Attacktive Directory Category: Active Directory Tools: Kerbrute, Impacket, Hashcat, Evil-WinRM

The setup: a domain controller for spookysec.local is reachable with nothing but an IP. The job: go from zero credentials to a full set of domain NTLM hashes using only what Active Directory exposes to anyone who can talk to it.

No single flag in these notes, the target is domain admin itself.

Background, In Plain Terms

AS-REP Roasting

If a Kerberos account has "Do not require Kerberos preauthentication" set, anyone can request a ticket for it, no password needed, and the ticket comes back encrypted with that account's password hash. Crack the ticket offline and you've got the password.

DCSync

A domain controller will hand over password hashes for any account to another DC, that's normal replication. If an account holds the right replication permissions, a tool can impersonate a DC and pull those hashes directly, no code execution on the DC required.

Pass-the-hash

Windows authentication protocols accept an NTLM hash in place of a plaintext password. Once you have a hash, you don't need to crack it to use it, you can authenticate with the hash itself.

The Investigation

1
Map the domain

A standard service scan lays out the whole picture immediately: this is a domain controller.

nmap -sC -sV -v 10.10.189.184

DNS, Kerberos, LDAP (twice, once unauthenticated on 389 and once over Global Catalog on 3268), SMB, and RDP are all open, and the LDAP banner names the domain outright: spookysec.local. enum4linux against it comes back mostly empty, a dead end worth noting and moving past quickly rather than forcing it.

Why this works

A domain controller's own open ports usually name the domain before you've sent a single authenticated request. Kerberos (88) plus LDAP (389/3268) together is as close to a neon sign reading "Active Directory" as a port scan gets.

2
Enumerate valid usernames

Kerberos itself leaks whether a username is valid, since the server responds differently for a real account than for a nonexistent one. kerbrute automates that check against a wordlist:

kerbrute -users /opt/userlist.txt -dc spookysec.local -domain spookysec.local -t 100

Several valid accounts come back, among them svc-admin, administrator, and backup, and svc-admin is flagged [NOT PREAUTH].

Why this works

That NOT PREAUTH flag isn't incidental, Kerbrute surfaces it because it's the exact precondition for AS-REP Roasting. A username enumeration step just handed over the one account worth attacking next.

3
Steal a crackable hash with AS-REP Roasting

Since svc-admin doesn't require pre-authentication, requesting a Kerberos ticket for it needs no password at all:

python3 GetNPUsers.py spookysec.local/svc-admin -no-pass

The response is a $krb5asrep$ hash, the account's password hash wrapped in a Kerberos ticket, ready to crack offline.

Why this works

Pre-authentication exists specifically to stop exactly this: an attacker requesting a ticket without proving they already know the password. Disable it on one account and that account's hash is handed to anyone who asks.

4
Crack it offline

Hashcat mode 18200 is built for exactly this ticket format:

hashcat -m 18200 TGT.txt passwordlist.txt --force
hashcat -m 18200 TGT.txt passwordlist.txt --show --force

John the Ripper works just as well with --format=krb5asrep. Either way, a dictionary match on a weak service-account password recovers svc-admin's plaintext credential in seconds.

Why this works

AS-REP hashes are only as strong as the account's password, there's no account lockout to slow down offline guessing once you have the hash in hand. A weak password on any pre-auth-exempt account undoes the protection entirely.

5
Walk the file shares with the cracked creds

Valid domain credentials, even for a low-privilege service account, are usually enough to list SMB shares:

smbclient -L spookysec.local -U svc-admin

Alongside the usual SYSVOL/NETLOGON shares sits a non-default one named backup. Mounting it turns up a single file: backup_credentials.txt.

Why this works

A share name that doesn't match any Windows default is worth checking first. Custom shares usually exist because someone put something there on purpose, and "backup" is a very common place for exactly the kind of leftover credentials file this turned out to be.

6
Decode the leftover credentials

The file's contents are a single base64 blob:

smb: \> more backup_credentials.txt
echo '<base64 blob>' | base64 -d

Decoded, it's a second set of domain credentials entirely, a backup account with its own password. (The same file is just as easy to pull with Metasploit's auxiliary/admin/smb/download_file module if a GUI workflow is preferred over the raw SMB client.)

Why this works

Base64 is encoding, not encryption, it was never meant to hide the content from anyone who finds the file, only to make it safe to store as text. A credentials file left in a share called "backup" is almost always exactly what it looks like.

7
DCSync the domain

The backup account turns out to hold replication rights on the domain, which is all secretsdump.py needs to impersonate a domain controller and request every account's hashes:

secretsdump.py backup:<password>@10.10.32.27

The DRSUAPI method pulls the full NTDS secrets, including the Administrator account's NTLM hash.

Why this works

DCSync abuses a legitimate, necessary feature: domain controllers have to replicate credential data to each other to function. Any account holding those replication permissions can request the same data a real DC would get, no foothold on the DC itself required.

8
Pass the hash to full admin

With the Administrator's NTLM hash in hand, there's no need to crack it, Windows authentication accepts the hash directly:

evil-winrm -i spookysec.local -u Administrator -H <ntlm-hash>

That lands an interactive PowerShell session on the domain controller as Administrator, full control over the domain.

Why this works

Pass-the-hash closes the loop on DCSync. The whole chain never required cracking a strong password, it chained together one weak account, one leftover file, and one legitimate replication feature.

Full Attack Chain

nmap: Kerberos + LDAP open → spookysec.local, a domain controller
  → Kerbrute: svc-admin found, flagged NOT PREAUTH
       → GetNPUsers.py: AS-REP hash stolen, no password needed
            → hashcat/john: hash cracked, svc-admin password recovered
                 → smbclient: "backup" share found, backup_credentials.txt inside
                      → base64 decode: a second account's credentials
                           → secretsdump.py (DCSync): Administrator's NTLM hash dumped
                                → evil-winrm (pass-the-hash): domain admin shell

Takeaways

One misconfigured flag can undo Kerberos entirely

"Do not require preauthentication" on a single account turns offline password cracking into a trivial first move, no foothold needed to request the hash.

File shares are an underrated enumeration target

A single leftover credentials file in a non-default share moved this chain from one low-privilege service account all the way to domain replication rights.

Replication rights are as sensitive as domain admin

Any account that can DCSync can retrieve any other account's hash, including Administrator's. That permission should be audited as carefully as actual admin group membership.
