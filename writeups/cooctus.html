Cooctus Stories: an NFS leak and a sudo unmount escape to root

An open NFS export hands over credentials with no authentication at all, git history exposes more than a careless commit, and a narrowly scoped sudo rule over a mount command turns out to be a way to read the entire filesystem as root.

Room: Cooctus Stories Category: Web / Linux Privesc Tools: showmount, git log, sudo -l

The setup: an NFS share nobody locked down, a git repository with history still intact, and a sudo rule that looks harmless in isolation. The job: chain all three into root.

The Investigation

1
Enumerate and mount the open NFS share

NFS is open with no authentication. Listing and mounting the export hands over its contents directly:

showmount -e <target>
mkdir /tmp/nfs && sudo mount -t nfs <target>:/<share> /tmp/nfs
Why this works

NFS exports are often configured by IP/hostname trust rather than credentials. An export with no restriction means anyone who can reach the port can read (or write) its contents as if they were local files.

2
Decode a small cipher puzzle

Among the mounted files sits a short string that isn't quite readable, a classic ROT13 rotation. Decoding it by hand or with a quick tool reveals a hint pointing at where to look next.

Why this works

ROT13 isn't security, it's obfuscation meant to avoid spoiling a hint at a glance, not to resist a determined read. Recognizing the "every letter looks slightly wrong but the word shapes are right" pattern is usually enough to spot it instantly.

3
Pull credentials out of git history

A project directory on the share turns out to be a git repository. The current files look clean, but the commit history tells a different story:

git log --all --oneline
git diff <commit-1> <commit-2>

An earlier commit contains a credential that was later removed from the working tree, but never purged from history.

Why this works

Deleting a secret in a new commit doesn't delete it from the repository, it's still sitting in every prior commit unless history itself is rewritten and force-pushed. git log and git diff across commits are standard first moves whenever a .git directory is reachable.

4
Check sudo rights after logging in

The recovered credentials work over SSH. Once logged in, checking what the account is allowed to run as root is the very next move:

sudo -l

The account can run mount (and its counterpart umount) as root, with no further restriction on arguments.

Why this works

sudo -l is the single highest-value command to run on any freshly obtained shell. A narrowly named command in a sudoers entry can still be a full privilege escalation if that command is powerful enough on its own, mount and unmount absolutely qualify.

5
Abuse mount/umount for a root filesystem view

Unmounting a bind-mounted restricted directory, then remounting the real root filesystem over an accessible mount point, exposes the entire disk, including /root, to the current unprivileged user.

sudo umount /some/restricted/mount
sudo mount --bind / /mnt

From there, a private SSH key sitting in root's home directory grants a direct, fully privileged login.

Why this works

Mount operations don't just attach new filesystems, they can remount or rebind existing ones in ways that bypass whatever restriction put them there in the first place. Sudo access to mount is effectively sudo access to the entire filesystem.

Full Attack Chain

showmount: open NFS export found, no auth required
  → mounted share: a ROT13-encoded hint found
       → decoded hint: points to a git repository on the share
            → git log/diff: a removed credential still sits in history
                 → SSH login with the recovered credential
                      → sudo -l: unrestricted mount/umount rights
                           → remount root filesystem: root's SSH key exposed

Takeaways

NFS exports need the same scrutiny as any network share

An export with no IP or auth restriction is effectively a public read (or write) of whatever it serves.

Git history outlives the files you meant to protect

A secret removed in a later commit is still recoverable from the repository's history unless that history itself is rewritten.

Narrow-sounding sudo rules deserve a second look

sudo -l is step one on any new shell. A single permitted command, if powerful enough, is a full privilege escalation on its own.
