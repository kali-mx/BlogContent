Docker Escape: a hidden port, a sudo bypass, and a stray binary

An SSH login that fails on the obvious port, a second service hiding in the connection table, a sudo rule that allows running as any user except root (which isn't the protection it sounds like), and a leftover docker binary that turns into a straight path out of the container.

Room: Docker Container Category: Linux Privesc / Containers Tools: ssh, sudo, docker

The setup: SSH access with one set of credentials fails outright on the target. The job: find what's actually listening, get in, and climb all the way out of a container to the host.

The Investigation

1
Find the hidden service

SSH to the obvious local address fails outright. Rather than assume the credentials are wrong, checking what's actually listening tells a different story:

cat /proc/net/tcp

The local address column is hex-encoded (host:port), and alongside the expected listeners sits a second one on a non-default port the earlier SSH attempt never touched.

Why this works

A failed login on the obvious port doesn't mean the credentials are wrong, it can just mean the real service is elsewhere. /proc/net/tcp shows every listener on the box, including ones a port scan from outside would never see if they're bound to loopback.

2
Reuse the credentials against the real port

The same credentials that failed before work immediately once pointed at the correct port:

ssh <user>@127.0.0.1 -p<hidden-port>
Why this works

Credentials weren't the problem, the target was. It's worth separating "wrong credentials" from "wrong service" before abandoning a login that looks like it should work.

3
Exploit a sudo rule that looks safer than it is

sudo -l shows the logged-in user can run /bin/bash as any user except root, with no password:

User <user> may run the following commands:
    (ALL, !root) NOPASSWD: /bin/bash

On sudo versions before 1.8.28 (this one is 1.8.21), that exclusion can be bypassed entirely with a crafted user ID:

sudo -u#-1 /bin/bash
Why this works

Passing a numeric user ID of -1 gets interpreted by older sudo versions as UID 0, root, due to how the value wraps during a signed-to-unsigned conversion. The rule technically still says "not root," sudo just doesn't enforce it correctly for that specific input. This is CVE-2019-14287.

4
Escape the container through a leftover docker binary

Root inside this shell is still just root inside a container, not the host. A search turns up a copy of the docker client sitting in a temp directory, along with an existing image:

find / -name docker 2>/dev/null
/tmp/docker images

With a docker client and a valid image reachable, mounting the entire host filesystem into a fresh container and chrooting into it is one command:

/tmp/docker run -it -v /:/host <image-id> chroot /host/ bash

The shell prompt's hostname changes, confirming the new container's root is now the real host filesystem.

Why this works

A docker client with access to the daemon is effectively root on the host, regardless of which container it's launched from, because a container can be configured to mount any host path, including / itself. Finding a stray client binary with working access is as good as finding a host-level credential.

Full Attack Chain

SSH fails on the default port
  → /proc/net/tcp: a second listener hiding on a non-default port
       → same creds, correct port: shell access
            → sudo -l: run as any user except root (NOPASSWD)
                 → sudo -u#-1 /bin/bash: CVE-2019-14287 bypass, root in-container
                      → stray docker client + image found
                           → docker run -v /:/host chroot: full host filesystem access

Takeaways

An exclusion in a sudo rule isn't a guarantee

(ALL, !root) reads like a safe boundary, but on an outdated sudo version it's bypassable with a single crafted argument. The version number mattered more than the rule's intent.

A docker client is as sensitive as a root credential

Any user who can reach the docker daemon can mount the host filesystem into a container they control. Treat access to the docker socket or client the same way you'd treat a root shell.
