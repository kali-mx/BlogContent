Hacker of the Hill: three boxes, three different footholds

One room, three independent machines at increasing difficulty, and three completely different ways in: a CMS edit page that executes PHP it was never meant to, an Active Directory domain cracked with a weak RDP password, and a leaked session hash that only pays off once you notice the second, easy-to-miss SSH port.

Room: Hacker of the Hill Category: Multi-host / Mixed Tools: Hydra, mimikatz, gobuster, CrackStation

The setup: three separate targets, Easy, Medium, and Hard, each its own box with its own services and its own path to root or SYSTEM. No shared foothold between them, each one has to be enumerated from scratch.

No single flag in these notes, each tier's objective is full compromise of that machine.

Easy: a CMS, a PHP sandbox, and a cron job

1
Find the hidden login through robots.txt

An nmap scan turns up three separate web apps on adjacent ports. The first one's robots.txt disallows a directory it was clearly trying to hide: /vbcms, which resolves to a "Very Basic CMS" login page.

Why this works

robots.txt is a request not to index a path, not an access control. It's one of the most reliable places to find a path an application owner considered sensitive enough to hide from search engines but forgot still needs real authentication.

2
Brute-force the login, then turn the editor into a shell

Inspecting the login form in the browser's network tab shows it's a plain POST with username/password fields, enough to build a Hydra command. It cracks a default-looking credential pair in seconds. Logged in, the CMS lets pages be edited directly, and since the pages are plain HTML served by an Apache instance that also runs PHP, pasting in a PHP reverse shell and saving the page gets it executed on save.

Why this works

A content editor that writes files into a path the web server executes is remote code execution by design, whether or not the application intended "page content" to mean "arbitrary PHP." Weak default credentials are what makes that reachable at all.

3
Spot the pivot you can't take yet

From the first foothold, linpeas finds a cron job firing every minute, owned by root but pointing at a script that belongs to a different, so-far-uncompromised user.

Why this works

A root cron job touching a file some other user owns is a privilege escalation path waiting on one missing piece: control of that other account. Finding it early means the rest of the box is just working out how to reach that specific user.

4
A "learn to code" site turns out to execute real PHP

The third web app is an interactive PHP tutorial site, type code into a box, click a button, and it runs server-side and shows the output. Testing it with system('id') confirms it executes as exactly the user the cron job needs. Pasting in the same reverse shell payload and submitting it gets an interactive shell as that user directly.

Why this works

Any "try it live" code execution feature is a sandboxed shell by definition, the only open question is how well it's actually sandboxed. Here, not well at all, it ran as a real, useful system user rather than a throwaway container account.

5
Hijack the cron job for root

With that user's access, the cron-executed script becomes writable. Overwriting it to set the SUID bit on /bin/bash, waiting one minute for the cron to fire as root, then running /bin/bash -p lands a root shell.

Why this works

A cron job is just code that runs with someone else's privileges on a timer. If an attacker can edit what it runs, they've effectively scheduled their own command to execute as root, no exploit required beyond file permissions.

Medium: Active Directory, a weak RDP password, and pass-the-hash

1
Enumerate the domain and its users

Kerberos, LDAP, and RDP all open on a Windows host name the domain outright. A handful of usernames come back from user enumeration, ordinary-looking employee accounts alongside Administrator.

Why this works

Same pattern as any Active Directory target: the open ports name the domain before a single authenticated request, and valid usernames are usually the cheapest thing to enumerate next.

2
Brute-force one account's RDP password

Rather than guess which account might be weak, Hydra runs a password-spray against one user's RDP login with a common wordlist and recovers a working password in minutes.

Why this works

In a domain with several human user accounts, only one needs a weak, wordlist-guessable password for the whole enumeration effort to pay off. RDP in particular rarely has the same lockout tuning a web login does.

3
Pass-the-hash to Administrator with mimikatz

Once inside via RDP, dropping mimikatz.exe and running three commands in sequence, elevate the current token, dump local SAM secrets, then pass Administrator's NTLM hash directly, authenticates as Administrator without ever needing the plaintext password.

token::elevate
lsadump::sam sam.reg system.reg
sekurlsa::pth /user:Administrator /domain:<dc> /ntlm:<hash>

That lands an nt authority\system shell.

Why this works

Same principle as any pass-the-hash chain: once an NTLM hash is recovered, Windows authentication accepts it in place of a password. One weak RDP credential was the only thing standing between an external attacker and a path straight to SYSTEM.

Hard: a leaked session hash and a second SSH port

1
Map a wide, mismatched set of services

Seven open ports across two SSH services, three different web servers (two Apache instances with different content, one nginx), and a Python Werkzeug app with no visible title at all. Nothing here announces its purpose up front, every service needs its own look.

Why this works

A box exposing this many near-identical-looking services is usually hiding the real way in behind the one that looks least interesting. Treating every port as equally worth enumerating, rather than fixating on the obvious web app, is what this tier is actually testing.

2
Find an API that leaks its own session hash

Directory brute-forcing one of the web apps surfaces an undocumented /api/user path with /login and /session endpoints. Querying the session endpoint directly, no authentication required, returns an active admin session object containing a raw password hash. A quick lookup against an online rainbow-table service cracks it instantly, it's a well-known, extremely common hash.

Why this works

An API endpoint that returns session data without checking whether the caller is authorized to see it is an authorization bug, not an authentication one, the request itself doesn't need credentials to leak someone else's. And any hash common enough to be precomputed in a public rainbow table might as well be plaintext.

3
Pull credentials from a second, separate app

The Werkzeug app on another port turns out to be a simple application launcher with its own API. Enumerating its endpoints the same way, first an /apps listing, then following the pattern to a /users endpoint, returns a username and password pair in plain JSON.

Why this works

Internal-looking admin tools often assume no one outside the team will ever enumerate their API surface, so they skip authentication on "harmless" endpoints like a user directory. That assumption is exactly what directory brute-forcing and endpoint guessing are built to break.

4
The obvious SSH port is a dead end, the second one isn't

The leaked username refuses password authentication on the standard SSH port, key-only. But a second SSH service is listening on a nonstandard port, and it accepts the same leaked password without complaint, landing a shell.

Why this works

Running two SSH daemons with different auth policies on the same host is a common, often accidental misconfiguration, a hardened service on the expected port next to a forgotten, more permissive one on an alternate port. Credentials that fail against the obvious target are worth retrying against every other instance of the same service before being written off.

Takeaways

Content editors are RCE if the server executes what they write

Both Easy-box footholds came from the same pattern: a feature designed to let users submit content, running on a server that doesn't distinguish "content" from "code."

One weak password anywhere undoes the rest of the hardening

The Medium box's entire chain, up to a SYSTEM shell, traced back to a single RDP account with a wordlist-guessable password.

The forgotten second instance of a service is often the real door

A second SSH daemon on a nonstandard port, with looser auth, undid whatever hardening the "real" SSH port had. Enumerate every instance of a service, not just the expected one.
