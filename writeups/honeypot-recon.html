Running a Honeypot: what internet scanners actually try

Stand up a box that looks like a vulnerable, multi-service server, publish it, and wait. No exploitation here, just watching what the open internet actually sends when it finds something that looks interesting.

Category: Threat Intel Tools: Shodan, nmap, Metasploit

The setup: a honeypot emulating a wide spread of services (FTP, SSH, SMTP, HTTP, SMB, RDP, Elasticsearch, and more) on a cloud host, with real vulnerability banners (CVE-2020-1938, MS17-010) baked in to see which scanners actually test for them.

Watching the Actual Probes Come In

1
CVE-2020-1938: Ghostcat probe against Apache JServ

A visitor runs a known Ghostcat proof-of-concept script against the Tomcat/AJP listener:

┌──(root💀kali)-[~/honeypot]
└─# python2 ghost.py <REDACTED>
Getting resource at ajp13://<REDACTED>:8009/asdf
----------------------------
<!doctype html><html lang="en"><head><title>HTTP Status 404 – Not Found</title>...
<h3>Apache Tomcat/9.0.30</h3></body></html>
Why this works

A 404 instead of a file read means the probe didn't land, the honeypot's AJP listener isn't actually vulnerable, it's just advertising the version. What matters here isn't the result, it's that a specific, actively-exploited CVE from the Shodan vulnerability list was tested within range of the scan, proof the listed CVE alone is enough to draw a targeted check.

2
MS17-010: EternalBlue scan against SMB
msf6 auxiliary(scanner/smb/smb_ms17_010) > run

[-] <REDACTED>:445     - Rex::ConnectionTimeout: The connection with (<REDACTED>:445) timed out.
[*] <REDACTED>:445     - Scanned 1 of 1 hosts (100% complete)
[*] Auxiliary module execution completed
Why this works

Same pattern as the Ghostcat probe: MS17-010 was also named in the Shodan listing, and a scanner checked for it directly using the exact Metasploit module built for it, the canonical first move against any box advertising that CVE since EternalBlue became public in 2017.

3
A full credential spray against FTP

Nmap's built-in brute-force script against port 21 isn't just testing if FTP is open, it's running an actual wordlist attack:

nmap --script ftp-* -p21 <REDACTED>

PORT      STATE    SERVICE
21/tcp    open     ftp
| ftp-brute:
|   Accounts:
|     root:root - Valid credentials
|     user:user - Valid credentials
|     web:web - Valid credentials
|     netadmin:netadmin - Valid credentials
|     guest:guest - Valid credentials
|     sysadmin:sysadmin - Valid credentials
|     administrator:administrator - Valid credentials
|     webadmin:webadmin - Valid credentials
|     admin:admin - Valid credentials
|     test:test - Valid credentials
|_  Statistics: Performed 117 guesses in 4 seconds, average tps: 29.2
Why this works

Every single guess in this list succeeded, by design, the honeypot accepts common username/password pairs on FTP specifically to capture which credential lists real attackers carry. Ten valid-looking hits in 4 seconds is a very different signal from a scanner that just checks if port 21 answers: this one came prepared with a credential list and used it immediately.

4
A DNS probe that looks like it's checking for a redirect
nslookup github.com
Non-authoritative answer:
Name:	github.com
Address: 140.82.114.3

nslookup <REDACTED>
** server can't find <REDACTED>.in-addr.arpa: NXDOMAIN

nslookup http://<REDACTED>
** server can't find http://<REDACTED>: NXDOMAIN
Why this works

Resolving a known-good domain (github.com) right before querying the honeypot's own address is a sanity check pattern, confirming DNS itself works before concluding the honeypot's hostname genuinely doesn't resolve a certain way. The malformed http://-prefixed lookup is a common copy-paste mistake when someone's scripting these checks in bulk rather than testing by hand.

Takeaways

Published CVEs draw targeted checks, not just port scans

Both Ghostcat and EternalBlue got tested specifically, not just discovered via a generic port sweep, directly traceable to the same two CVEs Shodan had already listed against the host.

Credential spraying still works because defaults still work

Ten out of ten common username/password pairs "succeeded" against the honeypot's FTP service in under 5 seconds. That ratio is exactly why default-credential sprays remain a cheap, high-yield first move for real attackers.

A convincing honeypot still has tells

The aiohttp server header on the HTTP service is the kind of detail that gives away an emulated service to anyone paying close attention, a reminder that banner fidelity matters as much for defenders building honeypots as it does for attackers fingerprinting real targets.
