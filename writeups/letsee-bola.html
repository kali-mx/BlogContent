LetSee.com: a BOLA in the account endpoint

A straightforward Broken Object Level Authorization finding from a formal assessment: an authenticated account-lookup endpoint accepts any account number in the URL, never checks whether it belongs to the requesting user, and hands over the admin account's email, role, and a live password reset token to anyone who just edits a number.

Target: LetSee.com (practice API) Category: Web / API Security Tools: Burp Suite

The setup: a practice web app with an authenticated API endpoint for viewing account details. The job: confirm whether authentication alone is standing in for authorization, or whether ownership is actually being checked. One finding was selected from the assessment to highlight here.

The Investigation

1
Create an account and capture the request that loads it

With Burp running as the proxy, signing up for a new account and logging in generates ordinary traffic. One request in the HTTP history stands out, a GET for the account page, with the account's own ID directly in the path:

GET /api/accounts/17 HTTP/1.1
Host: 54-153-37-124-letsee.vulnerablesites.net
Cookie: _letsee_api_session=<your own session cookie>
Uid: <your own email>

That ID isn't a token or a UUID, it's a small, visibly sequential integer, exactly the kind of value worth testing.

Why this works

Any identifier that appears directly in a URL, especially a predictable sequential one, is worth testing for authorization separately from authentication. The question isn't "can I reach this endpoint while logged in," it's "can I reach someone else's record through it while logged in as me."

2
Send it to Repeater and swap the ID, still using your own session

Right-clicking the request and sending it to Repeater, then changing the path from /api/accounts/17 to /api/accounts/10, with the exact same session cookie still attached, no new login, no new token, returns a full 200 response:

GET /api/accounts/10 HTTP/1.1
Host: 54-153-37-124-letsee.vulnerablesites.net
Cookie: _letsee_api_session=<your own session cookie, unchanged>
Why this works

This is the core of a BOLA/IDOR finding: the endpoint checks that a valid session exists, but never checks that the session belongs to the owner of the object being requested. Authentication and authorization are two different checks, and only the first one is happening here.

3
The response is the administrator's own account

Account ID 10 turns out to belong to the platform's admin user, and the response hands over its full record, including a live password reset token:

{
  "result": {
    "user": {
      "id": 10,
      "provider": "email",
      "uid": "admin@cmdnctrl.net",
      "name": "all powerful",
      "nickname": "Administrator",
      "email": "admin@cmdnctrl.net",
      "admin": true,
      "balance": "0.0",
      "password_reset_token": "xxSecretTokenxx-admin@cmdnctrl.net-06082022-08",
      "password_reset_sent_at": "2022-06-08T08:04:58.321Z"
    }
  }
}
Why this works

This is what turns "an authorization bug exists" into a concrete, high-severity finding: the leaked data isn't generic profile info, it's the admin flag confirming the account's privilege level and an active password reset token, which on most implementations is directly usable to take over the account outright.

Remediation

Fixing unprotected routes:

Do not rely on the client to enforce access control. Deny all access by default, and only allow an operation once the requesting user is confirmed to belong to the appropriate group or role, or to own the specific object being requested.

Takeaways

Authentication is not authorization

This endpoint correctly rejected requests with no session at all. It still failed completely at checking whether the authenticated session's owner matched the account being requested.

Predictable object identifiers raise the stakes

A BOLA against a small sequential integer ID is trivially scriptable into full account enumeration. The fix isn't switching to UUIDs, that just removes the easy sweep, it's an actual ownership check.

Severity depends on what's actually returned

A BOLA that leaks a display name is a different finding than one that leaks an active password reset token for an admin account. Always read the full response, not just confirm the status code.
