LetSee.com: a BOLA in the account endpoint

A straightforward Broken Object Level Authorization finding: an authenticated account-lookup endpoint accepts any account number in the URL and never checks whether it belongs to the requesting user.

Target: LetSee.com (practice API) Category: Web / API Security Tools: Burp Suite

The setup: a practice web app with an authenticated API endpoint for viewing account details. The job: confirm whether authentication alone is standing in for authorization, or whether ownership is actually being checked.

The Investigation

1
Find the object reference in the request

Logging in normally and viewing an account page sends a request with the account number directly in the path:

GET /api/accounts/<account-number>

That number isn't a session token or an opaque identifier, it's a small, visibly sequential value.

Why this works

Any identifier that appears directly in a URL or request body, especially a predictable one, is worth testing for authorization, not just authentication. The question isn't "can I reach this endpoint," it's "can I reach someone else's record through it."

2
Swap the account number while logged in as yourself

Capturing the request in Burp and changing the account number to a value that isn't the logged-in user's own:

GET /api/accounts/<someone-else's-account-number>
Cookie: session=<your own valid session>

returns a full, valid response, another user's account data, served to a session that was never granted access to it.

Why this works

This is the core of a BOLA/IDOR finding: the endpoint checks that a valid session exists, but never checks that the session belongs to the owner of the object being requested. Authentication and authorization are two different checks, and only the first one is happening here.

3
Confirm the scope by iterating

Since the identifier is small and sequential, a quick sweep across a range of nearby account numbers, still using the same single valid session, confirms the issue isn't a one-off, it's every account on the platform, reachable by any authenticated user.

Why this works

Confirming scope matters for severity, not just existence. "One account leaked" and "every account is enumerable with one valid login" are very different findings to report, even though the underlying flaw is identical.

Takeaways

Authentication is not authorization

An endpoint can correctly reject unauthenticated requests and still fail completely at checking whether the authenticated user owns the resource they're asking for.

Predictable object identifiers raise the stakes

A BOLA against a sequential integer ID is trivially scriptable into full enumeration. UUIDs don't fix the underlying authorization gap, but they do remove the easy sweep.

Always test with two accounts

A single test account can confirm an endpoint works. It takes a second account, and the deliberate attempt to cross the boundary between them, to confirm it's actually secure.

Solved via manual object-ID substitution testing with Burp Suite
