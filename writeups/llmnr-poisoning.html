LLMNR Poisoning and SMB Relay: catching credentials on the wire

A single mistyped share name is enough. Active Directory's fallback name resolution will broadcast for help, and anyone listening can answer first.

Category: Active Directory Tools: Responder, hashcat, ntlmrelayx

Purpose: a working reference for intercepting NTLM authentication via LLMNR poisoning, cracking what's captured, and relaying it instead when the target allows it. Demonstrated in a home AD lab (Windows Server and two enterprise clients).

Background, In Plain Terms

LLMNR

Link-Local Multicast Name Resolution, enabled by default in Active Directory, is the fallback a client uses when DNS can't resolve a name. It broadcasts to the local network asking anyone to answer. Nothing verifies who actually answers.

SMB relay (pass the hash)

Rather than cracking a captured hash, it can be forwarded live to another machine as proof of authentication, as long as that machine doesn't require SMB signing and the relayed account has admin rights there.

The Reference

1
Start listening

Responder masquerades as whatever share a broadcast is asking for, on the correct interface:

ip a
responder -I eth0 -v
Why this works

LLMNR broadcasts don't verify the responder's identity, Responder just has to answer before (or instead of) the real resource, which it can do passively on the right network segment.

2
Trigger a lookup and capture the hash

Any mistyped share, starting with a double backslash and ending in a single one, triggers an LLMNR broadcast on failure. Responder answers, and the client authenticates straight to it, handing over an NTLMv2 hash in the process.

Why this works

This isn't a contrived scenario, it's exactly what happens in a large organization when someone fat-fingers a share path or a stale login script points somewhere that no longer exists. LLMNR fires on any DNS failure, typo or not.

3
Identify and crack the hash

nth (name-that-hash) identifies the format and, usefully, tells you which hashcat and John modes to use:

nth -t '<captured hash>'
hashcat -O -m 5600 hash.txt /usr/share/wordlists/rockyou.txt
Why this works

NTLMv2 cracking is dictionary-dependent, a weak or reused password falls quickly, but a strong one won't crack at all against a wordlist. That's exactly why the relay path below matters as a second option.

4
Check if relaying is viable instead of cracking

Relaying needs SMB signing to be disabled on the target. Nmap checks this directly:

nmap --script=smb2-security-mode.nse -p445 <subnet> | grep "smb2-security-mode" -A2 -B8

A domain controller locked down with signing enforced doesn't rule this out entirely, individual workstations on the same network often aren't configured as strictly.

Why this works

SMB signing cryptographically verifies the sender of each SMB packet, which breaks a relay attack outright. Checking signing status per-host before attempting a relay saves time against hosts where it simply won't work.

5
Relay the hash instead of cracking it

With SMB and HTTP disabled in Responder's own config (so it only poisons, not competes with the relay), ntlmrelayx forwards captured authentication live to a target from the signing-disabled list:

ntlmrelayx.py -tf targets.txt -smb2support

If the relayed account has local admin rights on that target, an interactive session is one flag away:

ntlmrelayx.py -tf targets.txt -smb2support -i

Connecting to the resulting local port with netcat drops into a functional shell-like interface, supporting file upload/download and most Windows commands directly.

Why this works

A relayed hash proves authentication without ever needing the plaintext password, and it works regardless of password strength, since nothing gets cracked. Signing is the only thing standing between a captured hash and a live session.

Remediation

ControlTrade-off
Disable LLMNRCloses the attack outright; enforce via GPO where DNS already covers name resolution
Require SMB signing on all devicesStops relay attacks; roughly 15% file-copy performance cost
Disable NTLM authenticationRemoves the fallback entirely; Kerberos failures then have no fallback either
Account tieringLimits blast radius of any one compromised credential; harder to enforce consistently
Restrict local admin rightsBlocks most lateral movement via relay; more service-desk overhead
