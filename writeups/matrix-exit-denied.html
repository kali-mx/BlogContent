Matrix: Exit Denied, a forum, a cipher chain, and four flags

A forum that leaks its own staff roster, a credential-spray attack built from a vulnerability report nobody secured, a cipher puzzle three layers deep, a stolen session cookie, a time-synced SSH brute force, and a SUID binary that overwrites its way to root.

Room: Matrix: Exit Denied Category: Web / OSINT / Linux Privesc Tools: Burp Suite, Gobuster, John the Ripper

The setup: a Linux-Bay forum, a bug bounty report that was never actually secured, and a trail of puzzles hidden behind each layer of access. The job: work from anonymous forum browsing all the way to root, picking up four separate flags along the way.

Flags intentionally omitted below, this is about the path, not the values.

The Investigation

1
Enumerate the site and the forum's staff list

A directory scan turns up a long list of paths, admin panels, upload folders, an archive directory, far more surface than the front page suggests. The site itself is a MyBB forum, and browsing it without even logging in exposes the full staff roster, super moderators, admins, and regular moderators alike.

gobuster dir -u http://<target> -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt
Why this works

Forum software often exposes its member/staff list by design, for transparency, not realizing it's handing attackers a ready-made target list. Combined with a wide directory scan, this is pure reconnaissance: know who to target before attacking anything.

2
Register an account and dig through a user's posts

One staff member's profile is hinted at elsewhere on the site. Creating a throwaway forum account and searching their post history for clues turns up a reference to an internal bug bounty program, and a path to its report form.

Why this works

A forum's own search feature is a reconnaissance tool once you have an account. Internal programs mentioned casually in old posts are exactly the kind of detail that doesn't show up in an automated scan.

3
Read an unsecured vulnerability report for a credential list

The bug bounty submission form itself is disabled, but its client-side source (viewed via the browser's inspector) references a results page that was never actually locked down. That page lists a backlog of previously reported vulnerabilities, including one flagging that the forum's login has no CAPTCHA or lockout, protecting against password spraying, and a list of common weak passwords the reporter used to prove it.

Why this works

A disabled front-end form doesn't mean the backend page is gone, it just means the usual path to it is hidden. And a security report describing a weakness is itself a roadmap if the report page is reachable by anyone.

4
Spray the staff list against the leaked weak passwords

With a list of staff usernames from step 1 and a list of weak passwords from the vulnerability report, Burp Intruder's cluster bomb attack (every username against every password) against the login endpoint finds valid credentials by comparing response lengths, the real hits stand out immediately from the uniform "invalid login" responses.

Why this works

Credential spraying works precisely because most login failures look identical, a response of a different length or status is a reliable tell for a match, no manual checking of every attempt required.

5
Work through a layered cipher puzzle

Hidden page content leads through several encoding layers in sequence: a numeric string that turns out to be an A1Z26 cipher (numbers mapping to letters) decodes to a hint about "a permutation of letters," a second binary string decodes to ASCII text that turns out to be a directory name, and that directory holds a page whose source contains a long string of Chinese characters, each one secretly representing one of six specific English letters. Extracting just those letters and brute-forcing every arrangement of them (a permutation, following the earlier hint) eventually opens the next door.

Why this works

None of these individual encodings are strong, A1Z26, binary, and a character substitution are all textbook puzzle layers. The challenge is recognizing each one for what it is and chaining the decodes in the right order, exactly the kind of pattern-matching that gets faster with CTF experience.

6
Hijack a session by swapping cookies

A private forum message between two staff members references an internal build directory that seems to be offline. Inspecting the browser's stored cookies for that domain and swapping the session cookie value for a different staff member's session logs the browser in as that user on refresh, no credentials needed at all.

Why this works

A session cookie is the entire proof of identity for most web logins. If a cookie value tied to another account can simply be substituted in and accepted, session management itself is the vulnerability, no password required.

7
Pull an SSH credential out of an OTP scheme and brute-force it under a synced clock

The hijacked account's private attachments include documentation for an SSH login protected by time-based one-time passwords, along with several candidate shared-secret tokens. A small purpose-built script tries each token's generated OTP against SSH, but only succeeds if the attacking machine's clock is tightly synced to UTC first:

TZ=UTC sudo python3 matrixbrute.py --full-time

Once the clock is right, the brute force succeeds within its short validity window and SSH access follows.

Why this works

TOTP codes are only valid for a short rolling window, usually 30 seconds, tied to wall-clock time. A brute-force attempt against a TOTP-protected login has to respect that same clock or every attempt will be rejected regardless of whether the underlying secret is correct.

8
Escalate through a SUID pandoc binary

Hunting for SUID binaries on the box turns up pandoc, document conversion software not normally run with elevated privileges. Pandoc can convert between arbitrary formats, including writing its own output file, which makes it capable of overwriting /etc/passwd with a version that sets a known password hash for root:

cp /etc/passwd .
openssl passwd <new-password>
# paste the resulting hash into the passwd copy, replacing root's x
pandoc passwd -t plain -o /etc/passwd
su root
Why this works

Any SUID binary capable of writing to an arbitrary output path is a privilege escalation risk if that output path can be a sensitive system file. Pandoc was never designed as an attack tool, but "converts and writes files" plus "runs as root" adds up to exactly that.

Full Attack Chain

gobuster + forum browsing → staff roster and wide directory list exposed
  → registered account → post history leaks a bug bounty program
       → unsecured report page → weak-password list leaked
            → Burp Intruder cluster bomb → staff credentials found
                 → multi-layer cipher chain → hidden directory unlocked
                      → cookie swap → session hijacked, no password needed
                           → TOTP brute force (clock-synced) → SSH access
                                → SUID pandoc → /etc/passwd overwritten, root

Takeaways

Disabled front-ends don't mean the backend is gone

A form that's visually turned off is still worth checking for a reachable results page, API, or endpoint behind it.

A vulnerability report is a roadmap if it's exposed

Documentation of a weakness, written for defenders, is exactly as useful to an attacker if it's not access-controlled.

Session cookies need to be bound to more than just a value

If swapping in another valid session's cookie value is enough to become that user, session management itself needs hardening, independent of password strength.

Time-based codes require a correctly set clock, for both sides

Attacking (or defending) a TOTP scheme means respecting the same time window the algorithm does, a wrong clock defeats a correct secret just as surely as a wrong secret does.
