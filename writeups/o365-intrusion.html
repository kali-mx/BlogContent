The O365 Intrusion: tracing a two-account takeover through audit logs

A company's Microsoft 365 tenant gets hit: two employee accounts taken over, a mailbox rule quietly deleting evidence, a lure sent from one victim to the next, and a sensitive file walked out the door. Nothing here is a single flag, it's a full timeline built entirely from Splunk queries against the M365 audit log.

Room: The O365 Intrusion Category: Blue Team / SIEM / M365 Forensics Tools: Splunk, Python, curl

The setup: Vantage Dynamics has had two employee accounts compromised in Microsoft 365. Everything that happened, every sign-in, every email read, every file touched, is sitting in a Splunk index as raw audit log JSON. The job: reconstruct the full intrusion timeline using nothing but SPL queries.

No single flag here, the payoff is the timeline itself.

Background, In Plain Terms

SIEM

Security Information and Event Management: a giant search engine for log files. Splunk collects every M365 event so an analyst can query it with SPL instead of reading raw logs by hand.

M365 audit log

A unified record of every Outlook, Teams, SharePoint, and OneDrive action: who (UserId), what (Operation), when, from where, and on what file or email.

Sign-in errorCode

0 means access was actually granted. 50140 fires a few seconds earlier for the "Keep me signed in?" prompt, same login, earlier timestamp, and an easy trap if you don't filter for it.

MailItemsAccessed

Logged whenever a mailbox is read through Outlook. Each event carries a FolderItems array (one entry per email) and an OperationCount summary for that single event, not the whole session.

Inbox rule

An automated Outlook filter. Attackers write one to silently delete incoming security alerts or replies before the victim ever sees them. Logged as New-InboxRule.

Sensitivity label

An organizational tag (like "Confidential") applied to a file by data governance policy, not by the user. Logged as FileSensitivityLabelApplied.

External sharing link

A SharePoint or OneDrive link that grants access to someone outside the organization. Logged as SharingInvitationCreated.

The Investigation

1
Build a reusable Splunk query helper

The lab's Splunk instance uses a blank password for admin. Rather than fight shell quoting on every query, a small Python wrapper around Splunk's oneshot search API handles authentication once and takes raw SPL as an argument from then on.

# /tmp/sp.py
import subprocess, json, sys, urllib.parse

BASE = "https://<IP-with-dashes>.reverse-proxy.cell-prod-us-west-2a.vm.tryhackme.com"

def search(spl, count=10000):
    csrf = get_csrf()
    encoded = urllib.parse.quote(spl)
    cmd = ['curl', '-sk', '-c', '/tmp/sc.txt', '-b', '/tmp/sc.txt',
           f'{BASE}/en-US/splunkd/__raw/services/search/jobs',
           '-H', 'X-Requested-With: XMLHttpRequest',
           '-H', f'X-Splunk-Form-Key: {csrf}',
           '-d', f'search={encoded}', '-d', 'output_mode=json',
           '-d', 'exec_mode=oneshot', '-d', 'earliest_time=0',
           '-d', 'latest_time=now', '-d', f'count={count}']
    result = subprocess.run(cmd, capture_output=True, text=True)
    return json.loads(result.stdout)
Why this works

Passing SPL through Python instead of a raw shell command sidesteps quoting bugs from special characters in search strings. It also means every later query in this investigation is one function call, not a fresh curl command to get right.

2
Get oriented in the data

Before writing targeted queries, a quick survey of what sourcetypes actually exist in the index:

python3 /tmp/sp.py 'search index=vantage | stats count by sourcetype | sort -count'

Three sourcetypes cover the entire investigation: o365:graph:api for sign-in events with OS and IP, o365:management:activity for email, file, and inbox-rule operations, and o365:reporting:messagetrace for raw email delivery records.

Why this works

A stats count by sourcetype run first tells you the shape of the haystack before you start searching for needles. It's a cheap habit that pays off every time you touch an unfamiliar index.

3
Catch the anomalous sign-in

The first victim's normal device is a Mac, so the first move is filtering sign-in events for anything that isn't macOS, and specifically for errorCode: 0, the fully completed authentication, rather than the 50140 "Keep me signed in?" prompt that fires moments earlier for the same login.

python3 /tmp/sp.py 'search index=vantage sourcetype="o365:graph:api"
  userPrincipalName="<victim>"
  | rex field=_raw "\"operatingSystem\": \"(?P<OS>[^\"]+)\""
  | rex field=_raw "\"errorCode\": (?P<errorCode>[0-9]+)"
  | rex field=_raw "\"ipAddress\": \"(?P<IP>[^\"]+)\""
  | where OS != "MacOs" AND errorCode == 0
  | table _time OS IP errorCode | sort _time'

A single result lands: a non-Mac sign-in from an unfamiliar IP, a few minutes after a management-activity event with the same IP but ErrorNumber: 50140, the KMSI prompt, not the completed login.

Why this works

Microsoft logs two events per interactive sign-in. Whenever a question (or a detection rule) cares about "when did the sign-in happen," filtering for errorCode == 0 specifically avoids reporting a timestamp that's seconds too early.

4
Watch the attacker read the mailbox

Right after the sign-in, a burst of MailItemsAccessed events fires in under two minutes:

python3 /tmp/sp.py 'search index=vantage sourcetype="o365:management:activity"
  UserId="<victim>" Operation="MailItemsAccessed"
  | rex field=_raw "\"OperationCount\": (?P<OpCount>[0-9]+)"
  | rex field=_raw "\"ClientIPAddress\": \"(?P<ClientIP>[^\"]+)\""
  | table _time ClientIP OpCount | sort _time'

Several events fire back to back, and the last one carries a different IP, a Microsoft backend address, still part of the same attacker session, just processed server-side. Summing OperationCount across every event in that window, not just counting events, gives the real total of emails read.

Why this works

Each MailItemsAccessed event is a batch, not a single email, and some of that batch processing happens on Microsoft's own infrastructure under a different IP. Count the field, not the rows, and don't drop the proxy IP just because it isn't the attacker's.

5
Spot the cover-your-tracks inbox rule, and confirm it worked

Minutes later, a new inbox rule appears:

python3 /tmp/sp.py 'search index=vantage sourcetype="o365:management:activity"
  Operation="New-InboxRule" | table _time UserId _raw'

The rule's parameters show a subject-contains filter paired with DeleteMessage: True, silently deleting any incoming email that matches. Cross-referencing the message trace for the next matching email after the rule was created confirms it: a reply lands roughly eleven minutes later and never reaches the inbox, because the rule deletes it on arrival.

Why this works

Inbox rules that delete messages, especially ones created mid-session from an already-suspicious IP, are a high-fidelity detection signal. Confirming the rule actually fired (by finding the matching email it should have caught) turns "a rule exists" into "the rule worked and this is what it hid."

6
Catch the pivot to a second victim

The same compromised account is also used to pivot, sending a Teams message to a second employee with a file link attached:

python3 /tmp/sp.py 'search index=vantage sourcetype="o365:management:activity"
  UserId="<victim>" Operation="MessageCreatedHasLink" | table _time _raw'

The linked file's name carries a double extension, a document-looking name followed by a second, hidden copy of the same extension. Windows File Explorer hides the final extension by default, so the recipient sees what looks like an ordinary document and has no reason to hesitate.

Why this works

A compromised account isn't just a mailbox to rifle through, it's trusted infrastructure for reaching the next target. The double-extension trick works specifically because it exploits a Windows display default, not a technical vulnerability, so it's social engineering wearing a technical disguise.

7
Confirm the second compromise and trace the exfil target

A new sign-in to the second employee's account appears not long after the Teams message, from a different OS and a different IP than the first attack entirely, separate attacker infrastructure. Shortly after that sign-in, a FileDownloaded event shows a financial spreadsheet pulled from the Leadership SharePoint site:

python3 /tmp/sp.py 'search index=vantage sourcetype="o365:management:activity"
  UserId="<victim-2>" Operation="FileDownloaded"
  | table _time ClientIP SourceFileName | sort _time'

Pivoting to that same file's full history shows it was legitimately edited by its real owner earlier that same day, and that a sensitivity label (an org policy tag, not something a user sets manually) had already been applied to it, well before the attacker ever touched it.

Why this works

The timing gap between the Teams lure and the second sign-in is itself evidence, it's roughly how long it took the attacker to convert a social-engineering message into working credentials. And checking a file's history before the compromise is what proves the attacker grabbed something the organization already knew was sensitive, not an arbitrary file.

8
Catch the external share and its notification trail

Filtering sharing operations down to just the attacker's IP on the second account finds the exfiltration step: an external sharing link created for a separate document, sent to an address outside the organization entirely.

python3 /tmp/sp.py 'search index=vantage sourcetype="o365:management:activity"
  UserId="<victim-2>"
  (Operation="SharingInvitationCreated" OR Operation="SharingLinkUpdated")
  ClientIP="<attacker-ip>"
  | table _time Operation SourceFileName TargetUserOrGroupName | sort _time'

The target name carries an #ext# marker, Microsoft's notation for a guest account from outside the tenant. The message trace for that same timestamp confirms SharePoint actually sent the notification email, closing the loop from "a sharing event was logged" to "the file was really handed to someone outside the company."

Why this works

Correlating two independent log sources, the management-activity sharing event and the message-trace delivery record, for the same timestamp is what turns a single log line into proof the exfiltration actually completed, not just that someone clicked a button.

Full Attack Chain

Attacker A (new OS, new IP)
  → Successful sign-in to Account 1 (errorCode 0, after the 50140 decoy)
       → Mailbox rifled: dozens of emails read in under two minutes
       → Inbox rule created: silently deletes incoming replies matching a keyword
            → Confirmed working: a matching reply arrives and vanishes
       → Teams message sent to Account 2 with a double-extension lure file

Attacker B (different OS, different IP)
  → Successful sign-in to Account 2, minutes after the Teams lure
       → Sensitive financial file downloaded from the Leadership site
            → Confirmed pre-existing: legitimately edited and labeled earlier that day
       → External sharing link created for a second document
            → Sent to a guest address outside the organization
            → SharePoint notification confirms delivery

Takeaways

errorCode 50140 is not the sign-in

Microsoft fires two audit events per interactive login: a KMSI prompt, then the real grant. Always filter for the completed one when timing matters.

Inbox rules are a detection evasion tool

A delete rule created mid-session from a suspicious IP is a high-fidelity signal, especially one aimed at the exact kind of email that would expose the fraud.

Count the field, not the event

MailItemsAccessed batches multiple emails per event, and some of that batch gets processed under Microsoft's own IP, not the attacker's. Sum the right field across the whole window.

A compromised account is a pivot tool

The first account wasn't just rifled through, it was used to lure a second victim with a file name exploiting a Windows display default.

Sensitivity labels build an audit trail

They don't stop theft, but a label applied before the attacker ever touched the file proves exactly what the organization already knew was sensitive.
