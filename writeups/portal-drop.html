Portal Drop: reading the breach from logs to flag

A CRM portal got breached. All you start with is a raw access log and an EDR console, no hints, no pre-built story. Here's how I reconstructed the whole attack, step by step, and why each move made sense.

Room: Portal Drop Category: DFIR / Log Analysis Tools: grep, awk, base64, EDR console

The setup: a WAF alert fires on crm.trypatchme.thm, a web scan, then a suspicious file upload. The job: pull the truth out of the web access log and the EDR console, and decide if it's a false positive or a real breach.

Spoiler: it's real. Here's the trail.

The Investigation

1
Spot the brute force

The access log is plain Apache combined format: IP, timestamp, request, status code, user-agent. The fastest way to find a brute force in a pile of lines like this is to stop reading them one at a time and instead group by who and what happened:

# which IP keeps hitting login.php, and with what result?
grep "login.php" access.log | awk '{print $1, $9}' | sort | uniq -c | sort -rn

One IP jumped out immediately: 34.67.91.83, with 21 lines of 401 followed by a single 200. Twenty-one failures then one success, all from the same source, is about as clean a brute-force signature as log data ever gives you.

Why this works

Counting beats reading. A brute force is a pattern (volume plus failure ratio), not a single suspicious line. uniq -c turns thousands of rows into a handful you can eyeball.

2
Count every login, not just the attacker's

Separate question, same file: the room wants the site-wide totals, not just one IP's attempts. Every real user's logins count too.

grep "login.php" access.log | awk '$9==200' | wc -l   # successful
grep "login.php" access.log | awk '$9==401' | wc -l   # failed
Why this works

It's easy to anchor on "the attacker" and forget the question asked for the whole dataset. Always re-read exactly what's being asked before you scope your grep.

3
Watch behavior change after login

Filtering the whole log down to just 34.67.91.83 laid out the next moves in order. After the successful login: a couple of recon requests, then a POST /CRM/portal/upload.php, but logged under a different user-agent, python-requests/2.31.0, instead of the brute-forcer's PF-Scanner/1.0.

Right after, a new file appeared under /CRM/portal/uploads/: invoice.php, a name picked to blend into a CRM's normal traffic.

Why this works

A user-agent switch mid-session is a strong tell. It usually means the attacker swapped from an off-the-shelf scanner to a hand-written script for the exploitation step, which is exactly what let the EDR (and me) separate scanning from attacking.

4
Crack the webshell's command channel

Every call to invoice.php carried a q= parameter and an auth token. The q value didn't decode cleanly on the first pass, because it was base64 twice:

$ echo "ZDJodllXMXA" | base64 -d
d2hvYW1p          # still base64, decode again

$ echo "d2hvYW1p" | base64 -d
whoami            # the actual command

The second request's q unwound the same way, two layers deep, into a reverse shell one-liner reaching out to the attacker's box.

Why this works

Double (or N-layer) encoding is a cheap evasion trick against anyone just grepping for plaintext commands in a log. The fix is simple once you notice it. If a decoded string still looks like base64 (letters and digits, no spaces, no obvious words), decode it again.

5
Switch from logs to telemetry

Logs tell you what hit the server. They can't tell you what ran on it, or as whom. For that I moved to the EDR console and walked the process tree on the infected host:

systemd
  → apache2 (master)
    → apache2 (worker)
      → php-fpm (master)
        → php-fpm (worker)   # image: /usr/sbin/php-fpm7.4, user: www-data

That worker process is what actually executes anything the webshell asks for. The EDR confirmed it runs as the unprivileged web user, www-data, exactly where you'd expect a PHP app to run.

Why this works

A process tree answers "who's the parent of what" in one glance. It's the fastest way to prove a request-to-process link that a log file can only imply.

6
Let the EDR's own IOCs confirm the read

The same detection's IOC/Indicators tab listed the file path and process image as independently-flagged indicators. The EDR's detection engine had tagged the exact same two artifacts I'd just traced by hand from the log and the process tree.

Why this works

Triangulating matters. When the access log, the process tree, and the EDR's own IOC list all point to the same file and process, you can be confident it's not a coincidence or a logging artifact.

7
Name the technique

Dropping a script into a web-accessible folder so you can keep running commands through it later is textbook MITRE ATT&CK T1505.003: Server Software Component: Web Shell, filed under the Persistence tactic.

Why this works

Mapping an action to an ATT&CK ID isn't busywork. It's what lets this incident get compared, searched, and defended against using the same shared vocabulary every other SOC uses.

8
Chase the rest of the kill chain

Two detections remained. Medium Unusual User Behavior: System Discovery showed the attacker reading a sensitive CRM configuration file, likely holding database credentials. Low Hands-On-Keyboard Root Activity showed up on a second, different host, with traffic out to an external domain, confirming exfiltration.

Why this works

A detection appearing on a host you haven't seen yet is a lateral-movement flag by itself. The attacker didn't stop at the CRM box, they used it to reach somewhere else.

9
Close the loop

Every detection started life Not Acknowledged: logged, but untouched by an analyst. Working through each one's Actions/Response tab and formally responding to all four is what finally releases the room's completion flag.

Why this works

This is the actual job, condensed. A detection sitting unacknowledged is still an open risk. Finding the truth is half the work. The other half is closing it out.

What I Practiced

Log correlation

Turning thousands of raw lines into a pattern using grep, awk, sort, and uniq -c, instead of reading line by line.

Encoding-chain forensics

Recognizing and peeling back layered base64 to recover an attacker's actual commands.

EDR / process-tree triage

Reading parent → child process relationships to prove which binary executed attacker input, as whom.

ATT&CK mapping and response

Naming a technique by its MITRE ID, then working a detection through acknowledge → respond rather than stopping at "found it."
