Raz0rBlack: an NFS leak into AS-REP roasting and a hex-encoded flag

An open NFS export hands over a staff spreadsheet, that becomes a username list for AS-REP roasting, a forced password reset turns read-only SMB access into a usable account, and a trail of encoded credentials leads from a zipped archive to the domain's final secret.

Room: Raz0rBlack Category: Active Directory Tools: Kerbrute, Impacket, Hashcat, CrackMapExec

The setup: a domain controller with an open NFS export, a spreadsheet of staff names, and layers of encoded credentials scattered across shares. The job: turn a leaked file into a username list, a username into a hash, and a hash into full access.

The Investigation

1
Map the domain and mount an open NFS export

A service scan shows the usual AD fingerprint, Kerberos, LDAP, SMB, naming the domain outright. NFS being open on top of that is unusual enough to check:

showmount -e <target>
sudo mount -t nfs vers=2 <target>:/users ./smb

Mounted, it contains a staff spreadsheet (.xlsx), converted to CSV for easy reading with xlsx2csv.

Why this works

NFS being open at all on a Windows domain controller is already an anomaly worth chasing. A staff roster isn't a vulnerability by itself, but it's a ready-made username list for everything that follows.

2
Enumerate and AS-REP roast a pre-auth-exempt account

Feeding the names from the spreadsheet into kerbrute confirms valid accounts, and flags one with [NOT PREAUTH]. Requesting that account's hash needs no password at all:

kerbrute -users userlist.txt -dc raz0rblack.thm -domain raz0rblack.thm -t 100
GetNPUsers.py raz0rblack.thm/<user>

Hashcat cracks the resulting $krb5asrep$ hash against a standard wordlist in seconds.

Why this works

Same pattern as any AS-REP roasting target: a disabled pre-authentication flag means anyone can request a crackable ticket hash for that account without ever supplying a password.

3
Force a password reset to unlock read access

The cracked account's SMB login works, but crackmapexec reports STATUS_PASSWORD_MUST_CHANGE. smbpasswd satisfies that requirement directly, setting a new, known password:

smbpasswd -r <target> -U <user>

With the new password set, smbmap shows the account now has read access to a share previously inaccessible.

Why this works

A password-must-change flag isn't a wall, it's a prompt, and an attacker who already has valid (if expired) credentials can satisfy it exactly like a legitimate user would. Afterward, the account behaves as fully active.

4
Pull down and crack a password-protected archive

The newly readable share contains a chat log and a password-protected zip. Downloading the whole directory and converting the archive's encryption to a crackable hash format turns up the zip's password via a standard wordlist run, revealing a system registry hive and the domain's NTDS database inside.

Why this works

A password-protected archive is still only as strong as its password. Once it's local, cracking it offline is no different from cracking any other password hash, no rate limiting, no lockout.

5
Decode a stored credential and reach the domain's secret

A saved credential file (an exported PowerShell CliXml object) sitting in a user's home directory decodes cleanly once accessed as that same user, and the domain's root-level secret turns up in a second file as hex-encoded text, readable with a quick CyberChef decode.

Why this works

Exported PowerShell credentials are tied to the user and machine that created them, by design, but they decode trivially once an attacker is operating as that exact user. Hex encoding, like ROT13 or base64, is obfuscation, not protection, once you're looking at the right file.

Full Attack Chain

NFS export (open, no auth) → staff roster leaked
  → Kerbrute: valid usernames confirmed, one flagged NOT PREAUTH
       → GetNPUsers.py + hashcat: AS-REP hash cracked
            → smbpasswd: forced password reset unlocks SMB read access
                 → encrypted zip downloaded and cracked offline
                      → exported PS credential decoded as the right user
                           → hex-encoded secret decoded via CyberChef

Takeaways

An open NFS export on a Windows domain is always worth checking

It's not a default service for AD, so finding it open at all is itself a signal something was misconfigured.

A forced password change is satisfiable, not blocking

Cracked, expired credentials are still credentials, resetting the password is usually a single command away.

Layered encoding slows down automation, not a determined reader

Hex, base64, and password-protected archives each add a step, but none of them resist someone willing to decode one layer at a time.
