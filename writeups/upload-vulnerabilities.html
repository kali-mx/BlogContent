Upload Vulnerabilities: a GIF polyglot that got past a content filter

A file-upload filter checks more than its error message lets on. One extension-mangling trick gets caught immediately. A different approach, forging a GIF's magic bytes onto a working PHP shell, sails straight through.

Room: Upload Vulnerabilities Category: Web / File Upload Tools: gobuster, hexedit, curl

The setup: a series of small labs, each fronted by a different upload filter testing a different bypass technique. The job: work out what each filter actually checks, extension, content, or both, and craft an upload that gets past it.

No flag appears in these notes, the two filters themselves are the interesting part.

The Investigation

1
Find where uploads actually land

Before testing any bypass, it's worth knowing where a successful upload gets saved. Directory brute-forcing against the first lab turns up a hidden path:

gobuster dir -u annex.uploadvulns.thm -w directory-list-2.3-medium.txt -t 200 -z

/privacy comes back, and it's where uploaded files are actually stored and served from.

Why this works

An upload form rarely tells you the save path in its own UI. Finding it first means every later upload attempt can be checked for success by just requesting the resulting URL directly, instead of guessing.

2
Try mangling the extension, and watch it fail

A common first bypass attempt against extension filters is a double extension with mixed case, something like revshell.png.pHp, hoping a naive filter only checks the first extension or does a case-sensitive match on the second. This filter accepts the upload onto disk, but requesting it back just returns a broken-image error, the server never executes it as PHP.

Why this works

Accepting a file and executing it are two separate decisions. This filter's extension check runs case-insensitively against the real final extension regardless of what comes before it, so casing tricks and extra extensions don't help. A failed bypass here is still useful information: it rules out "this is just a sloppy extension check."

3
Switch to a filter that checks content, not just the name

A second lab, enumerated the same way, turns out to validate the uploaded file's actual bytes rather than (or in addition to) its extension:

gobuster dir -u magic.uploadvulns.thm -t 200 -w directory-list-2.3-medium.txt -z

This one checks for a recognizable file signature, commonly called "magic numbers", at the start of the upload before accepting it.

Why this works

Checking a file's content signature is a real step up from an extension check, it can't be fooled by renaming. But it's still only checking the first few bytes, not the whole file, which leaves an opening.

4
Forge the magic bytes onto a working shell

A GIF file's signature is the first six bytes, 47 49 46 38 37 61, which spells out the ASCII string GIF87a. Prepending those exact six characters to the top of a working PHP reverse shell, then confirming the raw bytes in a hex editor, turns the file into something that passes a GIF signature check while still being entirely valid, executable PHP from that point onward:

00000000  47 49 46 38 37 61 3c 3f  GIF87a<?
00000008  70 68 70 0a 2f 2f 20 70  php.// p

The filename keeps its real .php extension throughout, only the leading bytes change.

Why this works

This is a polyglot file: valid as a GIF for exactly six bytes, and valid PHP for everything after. A magic-number check that only inspects the header has no way to know the rest of the file doesn't match, and the web server doesn't care what the content looks like, only that the extension says PHP.

5
Upload it and trigger the shell

The upload form accepts the file without complaint. With a listener running, requesting the uploaded file directly executes it:

nc -lvnp 53
curl http://magic.uploadvulns.thm/graphics/yrevshell.php

The listener catches a connection back as www-data, a working shell from a file that started life pretending to be a picture.

Why this works

The content filter's job ends the moment it decides to accept the upload. Whether that file later gets executed as a script is a completely separate server configuration question, and on this box, the upload directory runs PHP just like anywhere else.

Takeaways

Extension filters and content filters are different controls

Renaming or re-casing a filename only defeats a filter that's actually looking at the filename. A filter enforcing the real extension server-side, regardless of what's stacked in front of it, isn't fooled by that trick at all.

A magic-number check isn't full content validation

Checking the first several bytes for a known file signature stops naive renaming attacks, but says nothing about what the rest of the file contains. A polyglot satisfies the check and carries a second, entirely different payload right behind it.

The real fix is execution, not detection

No upload filter, however good, fully closes this hole on its own. The upload directory executing PHP at all is the other half of the vulnerability, serving uploads from a location with script execution disabled would have stopped this chain regardless of what bypassed the content check.
